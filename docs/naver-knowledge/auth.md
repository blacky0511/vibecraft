# 네이버 인증 체계

> **최종 확인일: 2026-03-30**
>
> 이 문서는 네이버 로직 분석 에이전트가 인증 관련 진단 시 참조하는 지식 문서이다.
> 네이버는 인증 체계를 공지 없이 수시로 변경하므로, 구현 시 반드시 최신 동작을 확인해야 한다.

---

## 1. 로그인 흐름 (nid.naver.com)

네이버 로그인은 5단계로 구성된다. 각 단계에서 실패하면 이후 단계로 진행할 수 없다.

### 1단계: 로그인 폼 요청

```
GET https://nid.naver.com/nidlogin.login
```

- 로그인 폼 HTML이 반환된다.
- 이 HTML 안에 **RSA 공개키**(modulus, exponent)가 포함되어 있다.
- `dynamicKey`, `sessionKey`도 hidden input으로 포함된다.
- 이 값들은 **매 요청마다 바뀐다**. 캐싱하면 안 된다.

### 2단계: RSA 암호화

- 서버가 제공한 공개키로 아이디와 비밀번호를 암호화한다.
- 암호화 공식: `encData = RSA(sessionKey + "\n" + id + "\n" + password)`
- JavaScript의 `rsa.js` 또는 로그인 번들(예: `lnm.js`)에서 수행된다.
- `enctp` 필드가 암호화 방식을 나타낸다 (현재 값: `1` = RSA 기반).

### 3단계: bvsd 토큰 생성

- 페이지 로딩 후 사용자의 행동 데이터를 수집한다:
  - 마우스 이동 좌표 배열
  - 키보드 입력 타이밍 (keydown/keyup 간격)
  - 스크롤 이벤트
  - 포커스 전환 이벤트
  - 페이지 체류 시간
- JSON으로 직렬화한 뒤 base64 인코딩한다.
- 이 데이터가 너무 단순하면(예: 마우스 움직임 0건) **봇으로 판정**된다.

### 4단계: 로그인 요청 전송

```
POST https://nid.naver.com/nidlogin.login
```

전송 파라미터:

| 파라미터 | 설명 |
|----------|------|
| `enctp` | 암호화 타입 (현재: `1`) |
| `encData` | RSA 암호화된 로그인 데이터 |
| `bvsd` | 행동 검증 데이터 |
| `dynamicKey` | 동적 키 (1단계에서 획득) |
| `logintp` | 로그인 타입 |
| `svctype` | 서비스 타입 |
| `smart_LEVEL` | 보안 수준 |
| `locale` | `ko_KR` |

### 5단계: 응답 분기

로그인 요청의 결과는 다음 중 하나로 분기된다:

| 응답 | 의미 | 후속 처리 |
|------|------|-----------|
| 302 → callback URL | 로그인 성공 | NID_AUT, NID_SES 쿠키 발급 |
| 200 + captcha 필드 | 캡차 요구 | nCaptcha 풀이 필요 |
| 200 + `new_device=true` | 기기 인증 요구 | deviceName 등록 절차 필요 |
| 200 + `loginStatus=LOCK` | 계정 잠금 | 수동 해제 필요, 자동화 불가 |
| 403 또는 에러 페이지 리다이렉트 | IP 차단 | IP 변경 또는 대기 필요 |
| 200 + 앱 인증 요구 | QR/원터치 강제 | 신규 기기 + 고위험 상태, 수동 인증 필요 |

## 2. 쿠키 상세

### 전체 쿠키 테이블

| 쿠키 | 도메인 | 역할 | 만료 | 비고 |
|------|--------|------|------|------|
| `NID_AUT` | `.naver.com` | 로그인 인증 토큰 | 세션/영구 | **핵심 인증 쿠키**. 이것 없으면 비로그인 상태 |
| `NID_SES` | `.naver.com` | 세션 유지 | 세션 | NID_AUT와 함께 사용해야 유효 |
| `NID_JKL` | `.naver.com` | 기기 인증 | 장기 | Naver Guard 통과 시 발급. "기존 기기" 인식용 |
| `NNB` | `.naver.com` | 브라우저 식별 | 장기 | 네이버 전역 브라우저 ID. 봇 감지에 활용 |
| `nid_inf` | `.naver.com` | 부가 인증 정보 | 세션 | 인증 상태 보조 |
| `NACT` | `.naver.com` | 활동 추적 | 세션 | 사용자 행동 패턴 기록 |
| `PM_CK_loc` | `.naver.com` | 위치 정보 | 세션 | 지역 서비스용 |
| `nx_ssl` | `.naver.com` | SSL 세션 | 세션 | HTTPS 전환 추적 |
| `BMR` | `.naver.com` | 봇 관리 | 세션 | 봇 감지 시스템 관련 |

서비스별 추가 쿠키:
- `BlogUser` — 블로그 인증
- `CafeMember` — 카페 멤버 인증

### 쿠키 체인 순서 의존성

```
NID_AUT → NID_SES → NNB → 서비스별 쿠키 (BlogUser, CafeMember 등)
```

**순서가 중요하다.** NID_AUT 없이 서비스 쿠키만 보내면 세션이 무효화될 수 있다.
쿠키를 복원할 때는 반드시 이 순서를 지켜야 한다.

### 쿠키 도메인 스코프 변경 감지

- **기존**: `.naver.com` (전체 서브도메인 공유)
- **변경 추세**: 일부 쿠키가 서브도메인 한정으로 전환 중 (보안 강화)
- 도메인 스코프가 변경되면 기존에 동작하던 쿠키 공유가 깨질 수 있다.
- 진단 시 쿠키의 `Domain` 속성을 반드시 확인해야 한다.

### SameSite 정책

- **기본**: `Lax` (대부분의 쿠키)
- **변경 추세**: 일부 서비스에서 `Strict`로 전환 중
- `SameSite=Strict`인 경우 외부 사이트에서 네이버로의 요청에 쿠키가 포함되지 않는다.
- 자동화 도구에서 직접 API를 호출할 때는 `SameSite` 정책에 영향받지 않지만, iframe이나 리다이렉트 체인에서는 영향을 받을 수 있다.

## 3. 2차 인증 트리거 조건

다음 조건 중 **하나라도 해당**되면 2차 인증이 요구된다:

| # | 조건 | 설명 |
|---|------|------|
| 1 | 새 기기 접속 | NID_JKL 쿠키 없음, deviceId 미등록 |
| 2 | 해외 IP 접속 | GeoIP 국가 불일치 |
| 3 | 비정상 패턴 감지 | bvsd 점수 낮음 |
| 4 | 장기 미접속 | 약 30일 이상 미접속 후 재접속 |
| 5 | 비밀번호 변경 후 | 변경 후 첫 로그인 |
| 6 | 2단계 인증 활성화 | 보안 설정에서 활성화된 계정 |
| 7 | 동시 세션 감지 | 여러 IP에서 동시 세션 |
| 8 | 계정 신뢰도 낮음 | 신규 계정, 활동 이력 부족 |

### 2차 인증 방식

- 등록된 휴대폰 SMS 인증
- 네이버 앱 OTP 인증
- 이메일 인증 (보조 이메일)
- Naver Guard 앱 푸시 인증
- 네이버 앱 QR 코드 인증 (최근 강제 빈도 증가)
- 네이버 앱 원터치 인증

## 4. Device ID/Registration 시스템

- 네이버는 기기별 고유 `deviceId`를 발급하고 서버에서 관리한다.
- `NID_JKL` 쿠키 외에 별도의 `deviceId`가 서버에 등록된다.
- 자동화 시 `deviceId`를 **영구 저장하고 복원**해야 "기존 기기"로 인식된다.
- 새 `deviceId`로 접속하면 2차 인증 트리거 확률이 **급증**한다.
- 브라우저 프로필을 유지하거나, 쿠키와 함께 `deviceId`를 파일로 저장하는 것이 권장된다.

## 5. 계정 신뢰도 점수

네이버는 계정별로 내부 신뢰도 점수를 관리한다 (정확한 수치는 비공개).

신뢰도에 영향을 주는 요소:
- **높이는 요소**: 오래된 계정, 활발한 활동 이력, 정상적인 로그인 패턴, 기기 등록 이력
- **낮추는 요소**: 신규 계정, 활동 이력 없음, 봇 감지 이력, 다수 IP에서 접속, 스팸 신고 이력

신뢰도가 낮을수록:
- 2차 인증 빈도 증가
- Rate Limiting 한도 축소
- 스팸 필터 민감도 증가
- 봇 감지 임계값 낮아짐

## 6. OAuth 토큰 (공식 API vs 비공식 구분)

네이버는 공식 개발자 API(`openapi.naver.com`)를 위한 OAuth 2.0 인증을 제공한다. 이것은 로그인 자동화와는 별개의 시스템이다.

- **공식 API**: 네이버 개발자센터에서 애플리케이션을 등록하고, Client ID/Secret으로 OAuth 토큰을 발급받아 사용한다. 검색 API, 블로그 API 등 공식 엔드포인트에 접근한다. 일일 호출 한도가 있다 (예: 검색 25,000건/일).
- **비공식 접근**: 로그인 쿠키(NID_AUT, NID_SES 등)를 직접 사용하여 내부 API에 접근하는 방식이다. OAuth 토큰이 아닌 세션 쿠키 기반이며, 봇 감지에 민감하다.

진단 시 사용자가 "공식 API"를 쓰는지 "비공식(쿠키 기반)"을 쓰는지 먼저 구분해야 한다. 공식 API 문제는 토큰 만료/갱신 이슈가 대부분이고, 비공식은 쿠키 관리와 봇 감지가 핵심 이슈이다.

## 7. 세션 복원 시 환경 바인딩 주의사항

저장된 쿠키로 세션을 복원할 때, 다음 환경 요소가 **원래 세션과 동일**해야 한다:

| 요소 | 불일치 시 결과 |
|------|----------------|
| **IP 주소** | 세션 무효화 또는 2차 인증 트리거 |
| **User-Agent** | 봇 의심 → 세션 만료 강제 |
| **TLS 핑거프린트** | 봇 감지 → 403 차단 |

### 실무 권장사항

1. **IP 유지**: 세션 쿠키를 생성한 IP와 동일한 IP에서 복원한다. VPN/프록시를 쓴다면 동일한 출구 IP를 유지한다.
2. **UA 고정**: 쿠키 저장 시 User-Agent도 함께 저장하고, 복원 시 동일한 UA를 사용한다.
3. **TLS 일관성**: 동일한 브라우저/라이브러리를 사용한다. `requests`로 생성한 세션을 Playwright에서 복원하면 TLS 핑거프린트가 달라져 차단될 수 있다.
4. **환경 변경 시**: IP/UA/TLS가 바뀔 수밖에 없다면, 새로 로그인하는 것이 안전하다.

### 세션 단건 복원이 아닌 "전체 흐름"이 일치해야 한다

세션 환경 바인딩은 **세션 복원 시점**만의 문제가 아니다.
**로그인 → 작업 완료**까지 모든 단계에서 IP/UA/TLS/쿠키가 동일해야 한다.
중간 한 단계라도 환경이 바뀌면 네이버가 세션 탈취로 판정한다.

전체 워크플로우 통일성의 상세 가이드(도구 혼용, 프록시 로테이션, 병렬 실행 등의
위반 사례와 도구별 체크리스트)는 `docs/naver-knowledge/bot-detection.md`의
**12. 전체 워크플로우 IP/쿠키 통일성** 섹션을 참조한다.
