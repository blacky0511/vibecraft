# 네이버 검색 API 참조 지식

> **최종 확인일: 2026-03-30**
> 이 문서는 naver-logic-analyzer 에이전트가 검색 관련 문제를 진단할 때 참조하는 지식 베이스이다.

---

## 1. 공식 Search API (openapi.naver.com)

### 엔드포인트

| 검색 유형 | 엔드포인트 | 설명 |
|----------|-----------|------|
| 블로그 | `GET /v1/search/blog.json` | 블로그 검색 |
| 뉴스 | `GET /v1/search/news.json` | 뉴스 검색 |
| 카페글 | `GET /v1/search/cafearticle.json` | 카페 글 검색 |
| 웹문서 | `GET /v1/search/webkr.json` | 웹 문서 검색 |
| 이미지 | `GET /v1/search/image` | 이미지 검색 |
| 쇼핑 | `GET /v1/search/shop.json` | 쇼핑 검색 |
| 지식iN | `GET /v1/search/kin.json` | 지식iN 검색 |
| 백과사전 | `GET /v1/search/encyc.json` | 백과사전 검색 |
| 영화 | `GET /v1/search/movie.json` | 영화 검색 |

### 인증

```
요청 헤더:
  X-Naver-Client-Id: {발급받은 Client ID}
  X-Naver-Client-Secret: {발급받은 Client Secret}
```

- 네이버 개발자센터(developers.naver.com)에서 애플리케이션 등록 후 발급
- 하나의 애플리케이션에 Client ID + Client Secret 1쌍 발급

### Rate Limit

| 항목 | 제한 |
|------|------|
| 일일 호출 한도 | 25,000건/일 |
| 초당 호출 한도 | 명시적 제한 없으나, 과도한 호출 시 일시 차단 |
| 한도 초과 응답 | HTTP 429 또는 에러 코드 반환 |

### 공통 요청 파라미터

| 파라미터 | 필수 | 설명 |
|---------|------|------|
| `query` | O | 검색어 (UTF-8 인코딩) |
| `display` | X | 한 번에 표시할 결과 수 (기본 10, 최대 100) |
| `start` | X | 검색 시작 위치 (기본 1, 최대 1000) |
| `sort` | X | 정렬 기준 (`sim`: 유사도순, `date`: 날짜순) |

### 응답 구조 (JSON)

```json
{
  "lastBuildDate": "날짜",
  "total": 전체결과수,
  "start": 시작위치,
  "display": 표시수,
  "items": [
    {
      "title": "제목 (HTML 태그 포함)",
      "link": "URL",
      "description": "설명",
      "bloggername": "블로거명",
      "bloggerlink": "블로그 URL",
      "postdate": "작성일 (YYYYMMDD)"
    }
  ]
}
```

### 공식 API 한계

- 실제 웹 검색 결과와 순서/내용이 다를 수 있음
- VIEW 탭 결과는 공식 API로 조회 불가
- AI 검색(Cue:) 결과는 공식 API에 미포함
- 통합검색 화면과 동일한 결과를 얻을 수 없음
- `start` 최대 1000이므로 1000건 이후 결과 접근 불가

## 2. 비공식 웹 크롤링 (search.naver.com)

### 기본 URL

```
PC: https://search.naver.com/search.naver?query={검색어}
모바일: https://m.search.naver.com/search.naver?query={검색어}
```

### 탭별 URL 파라미터

| 탭 | `where` 값 | 설명 |
|----|-----------|------|
| 통합검색 | `nexearch` | 기본 통합 검색 |
| VIEW | `view` | 블로그+카페+포스트 통합 |
| 블로그 | `blog` | 블로그 전용 탭 |
| 카페 | `cafearticle` | 카페글 전용 탭 |
| 뉴스 | `news` | 뉴스 전용 탭 |
| 이미지 | `image` | 이미지 검색 |
| 쇼핑 | `shop` | 쇼핑 검색 |

### 주의사항

```
[봇 감지 민감]
- User-Agent 없이 요청 → 즉시 차단
- 동일 IP에서 분당 수십 건 이상 → 캡차 트리거
- requests 라이브러리 기본 UA("python-requests/x.x") → 즉시 차단
- headless 브라우저 navigator.webdriver 미패치 → 감지

[필수 헤더]
- User-Agent: 실제 브라우저 UA 사용
- Referer: https://www.naver.com/ 권장
- Accept-Language: ko-KR,ko;q=0.9
- Cookie: NNB 쿠키 존재 시 봇 감지 완화

[HTML 파싱 특성]
- 네이버 검색 결과 HTML은 수시로 클래스명/구조 변경
- React 기반 SPA 전환 진행 중 (일부 탭은 CSR)
- data-* 속성 기반 파싱이 class명보다 안정적
- 광고 영역과 자연검색 영역의 DOM 구조가 다름
```

### robots.txt 준수

```
# search.naver.com/robots.txt 주요 규칙
User-agent: *
Disallow: /search.naver  # 검색 결과 페이지 크롤링 비허용

→ 비공식 크롤링은 robots.txt 위반에 해당
→ 소규모/개인 용도: 회색 지대
→ 대규모/상업적 용도: 법적 리스크 존재 (업무방해 가능)
```

## 3. VIEW 탭 통합 (블로그 + 포스트 + 인플루언서)

### 개요

- 기존에 분리되어 있던 블로그/카페 탭이 VIEW 탭으로 통합되는 추세
- VIEW 탭에는 블로그, 네이버 포스트, 인플루언서 콘텐츠가 혼합 노출
- 검색 결과 순위가 블로그 탭과 VIEW 탭에서 다를 수 있음

### VIEW 탭 구조

```
VIEW 탭 검색 결과:
├── 인플루언서 영역 (상단, 있는 경우)
│   └── 인플루언서 프로필 + 대표 콘텐츠
├── 블로그 글 (blog.naver.com)
├── 네이버 포스트 (post.naver.com)
├── 카페 글 (cafe.naver.com)
└── 외부 블로그 (티스토리, 워드프레스 등, 일부 노출)
```

### 자동화 시 주의점

- VIEW 탭 URL: `where=view` 파라미터 사용
- 결과 내 콘텐츠 출처 구분 필요 (블로그/포스트/카페/외부)
- 인플루언서 영역은 별도 DOM 구조
- VIEW 탭 셀렉터는 블로그 탭과 다름

## 4. AI 검색 결과 (Cue:)

### 개요

- 네이버 통합검색 상단에 AI가 생성한 답변을 노출하는 영역
- 브랜드명: "Cue:" (2025년 하반기부터 도입)

### 자동화 관점 특성

```
[비동기 렌더링]
- Cue: 영역은 페이지 로드 후 별도 API 호출로 비동기 렌더링
- 초기 HTML에는 Cue: 영역 콘텐츠가 없음
- Playwright/Selenium 사용 시 Cue: 영역 로딩 대기 필요
- 대기 없이 파싱하면 Cue: 영역이 빈 상태로 수집됨

[파싱 대상 변경]
- Cue: 영역은 기존 검색 결과와 다른 DOM 구조
- 기존 자연검색 파싱 로직으로는 Cue: 영역 수집 불가
- Cue: 영역의 참고 출처 링크 구조도 별도 파싱 필요

[순위 영향]
- Cue: 영역이 통합검색 최상단을 차지
- 기존 자연검색 결과가 아래로 밀림
- 키워드 순위 계산 시 Cue: 영역 고려 여부 결정 필요
```

---

## 5. 키워드 순위 확인 방법

### 접근 방식

```
방법 1: 공식 API (제한적)
- openapi.naver.com/v1/search/blog.json 등으로 검색
- 반환된 items 배열에서 목표 URL의 인덱스 = 순위
- 단점: 실제 웹 검색 결과와 순서 차이 가능

방법 2: 웹 크롤링 (정확하지만 리스크)
- search.naver.com 에서 직접 HTML 파싱
- 탭별(통합/VIEW/블로그/카페)로 별도 크롤링 필요
- 봇 감지 리스크 존재

방법 3: 네이버 서치어드바이저 (공식, 본인 사이트만)
- searchadvisor.naver.com 에서 노출/클릭 데이터 확인 가능
- 타 사이트 순위는 확인 불가
```

### 순위 계산 로직

```
1. 검색 결과 목록 수집 (HTML 파싱 또는 API)
2. 각 결과에서 URL 추출
3. 목표 URL과 매칭 (정확 일치 또는 도메인+경로 일치)
4. 매칭된 결과의 인덱스 + 1 = 순위
5. 페이지네이션 고려: (페이지 번호 - 1) * 페이지당 결과수 + 인덱스
6. 탭별 순위를 각각 기록 (통합검색 3위, VIEW 탭 5위 등)
```

## 6. 모바일/PC 결과 차이

### 주요 차이점

| 항목 | PC | 모바일 |
|------|-----|--------|
| URL | search.naver.com | m.search.naver.com |
| 결과 수 | 페이지당 10~15건 | 무한 스크롤 방식 |
| 탭 구조 | 상단 탭 나열 | 스와이프 탭 |
| DOM 구조 | 데스크탑 전용 클래스 | 모바일 전용 클래스 |
| 순위 | PC 기준 순위 | 모바일 기준 순위 (다를 수 있음) |
| 광고 위치 | 상단+우측 | 상단+피드 사이 |
| Cue: 영역 | 있음 | 있음 (모바일 최적화 UI) |

### 자동화 시 주의

```
- PC와 모바일 검색 결과 순위가 다를 수 있음
- 키워드 순위 확인 시 PC/모바일 모두 체크 권장
- 모바일은 무한 스크롤이므로 스크롤 이벤트 트리거 필요
- User-Agent로 PC/모바일 분기:
  - PC UA: "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ..."
  - 모바일 UA: "Mozilla/5.0 (iPhone; CPU iPhone OS ..." 또는 Android UA
```

## 7. 광고 vs 자연검색 구분

### 구분 기준

```
[광고 영역]
- 통합검색 상단 "파워링크" 영역
- "광고" 라벨 표시 (법적 의무)
- 별도 DOM 영역에 렌더링
- 광고 영역 셀렉터: 시기별 변경됨 (클래스명 기반 파싱 불안정)

[자연검색 영역]
- 광고 라벨 없음
- 검색 알고리즘 기반 순위
- VIEW 탭, 블로그 탭 등 각 탭의 본문 영역

[구분 방법]
1. "광고" 라벨 텍스트 존재 여부 확인
2. DOM 구조상 광고 컨테이너와 자연검색 컨테이너 분리
3. data-* 속성으로 광고 여부 판별 (속성명은 수시 변경)
4. 링크 URL 패턴: 광고는 ad.search.naver.com 경유
```

## 8. 검색 진단 트리

에이전트가 검색 관련 문제를 진단할 때 아래 트리를 순서대로 따른다.

### 8-1. 검색 API 단계

```
[공식 API vs 크롤링 분기]
├── 사용자가 공식 API를 사용하는가?
│   ├── YES → 공식 API 진단 경로
│   │   ├── API 키(Client ID/Secret) 유효한가?
│   │   │   ├── NO → 개발자센터에서 키 재발급 안내
│   │   │   └── YES ↓
│   │   ├── Rate Limit(일 25,000건) 초과?
│   │   │   ├── YES → 호출 횟수 절감 또는 다중 키 로테이션
│   │   │   └── NO ↓
│   │   ├── 응답 HTTP 코드 정상(200)?
│   │   │   ├── NO → 에러 코드별 분기 (400: 파라미터, 401: 인증, 429: 한도)
│   │   │   └── YES ↓
│   │   ├── 응답 JSON 포맷 변경?
│   │   │   ├── YES → 필드명/구조 변경 확인 → 파싱 로직 수정
│   │   │   └── NO ↓
│   │   └── 검색 결과 품질 문제 (웹 결과와 차이)
│   │       └── 공식 API는 웹 검색과 결과가 다를 수 있음 → 정상
│   │
│   └── NO → 비공식 크롤링 진단 경로
│       ├── HTTP 403 또는 캡차 발생?
│       │   ├── YES → 봇 감지 트리거
│       │   │   ├── User-Agent 확인 (python-requests 기본값?)
│       │   │   ├── 요청 빈도 확인 (분당 건수)
│       │   │   ├── NNB 쿠키 유무 확인
│       │   │   ├── Referer 헤더 유무 확인
│       │   │   └── headless 브라우저 감지 패치 여부
│       │   └── NO ↓
│       ├── HTML 구조 변경?
│       │   ├── YES → 셀렉터 업데이트 필요
│       │   │   ├── 클래스명 변경 확인
│       │   │   ├── SPA 전환 여부 확인 (CSR로 변경 시 JS 렌더링 필요)
│       │   │   └── data-* 속성 기반 파싱으로 전환 권장
│       │   └── NO ↓
│       └── 파싱 결과 이상?
│           ├── 빈 결과 → 검색어 인코딩 확인 (UTF-8)
│           ├── 결과 수 감소 → 네이버 검색 알고리즘 변경 가능
│           └── 특정 탭만 이상 → 탭별 별도 확인
```

### 8-2. 순위 확인 단계

```
[순위 확인 분기]
├── 어떤 탭에서 순위를 확인하는가?
│   ├── 통합검색 (nexearch)
│   │   ├── Cue: 영역 로딩 대기 여부 확인
│   │   ├── 광고 영역 제외하고 순위 계산하는가?
│   │   └── VIEW/블로그/뉴스 등 섹션별 순위 구분
│   ├── VIEW 탭 (view)
│   │   ├── 블로그/포스트/카페 혼합 결과 정상 파싱?
│   │   ├── 인플루언서 영역 별도 처리?
│   │   └── 외부 블로그 포함 여부
│   ├── 블로그 탭 (blog)
│   ├── 카페 탭 (cafearticle)
│   └── 기타 탭
│
├── PC/모바일 모두 확인하는가?
│   ├── PC만 → 모바일 순위가 다를 수 있음 경고
│   ├── 모바일만 → PC 순위가 다를 수 있음 경고
│   └── 둘 다 → 각각 별도 파싱 필요
│
├── 순위 계산 로직 정상?
│   ├── 광고 결과를 순위에 포함하고 있지 않은가?
│   ├── 페이지네이션/무한스크롤 처리 정상?
│   └── URL 매칭 로직 정확? (정규식, 도메인+경로 등)
│
└── 순위가 변동되었는가?
    ├── 특정 시점부터 → 네이버 알고리즘 업데이트 가능
    ├── 점진적 하락 → 콘텐츠 품질/블로그 저품질 의심
    └── 갑자기 사라짐 → 검색 제외(패널티) 의심
```
