# 네이버 봇 감지 시스템

> **최종 확인일: 2026-03-30**
>
> 이 문서는 네이버 로직 분석 에이전트가 봇 감지 관련 진단 시 참조하는 지식 문서이다.
> 네이버는 봇 감지 시스템을 지속적으로 강화하고 있으며, 아래 내용은 관찰 시점 기준이다.

## 1. 감지 5계층

네이버의 봇 감지는 외부에서 내부 순서로 5계층으로 구성된다. 상위 계층에서 차단되면 하위 계층 검사까지 가지 않는다.

### 계층 1: 네트워크 수준

| 감지 항목 | 설명 |
|-----------|------|
| IP 레퓨테이션 | 알려진 데이터센터 IP, VPN IP, 프록시 IP 차단 |
| IP 속도 제한 | 동일 IP에서 분당 N건 이상 요청 시 429 반환 |
| IP 패턴 | 동일 IP에서 다수 계정 로그인 시도 시 차단 |
| TLS 핑거프린트 | JA3/JA4 해시로 자동화 도구 구분 (아래 상세 참조) |

### 계층 2: HTTP 수준

| 감지 항목 | 설명 |
|-----------|------|
| User-Agent 검증 | 실제 브라우저 UA와 일치하는지 (버전 번호까지). Chrome UA인데 Firefox 동작이면 탐지 |
| Referer 검증 | API 직접 호출 시 Referer 없으면 의심. Referer 도메인이 naver.com 계열인지 확인 |
| 부가 헤더 일관성 | Accept-Language, Accept-Encoding 등이 UA와 일관되는지 |
| WAF 차단 | 일반 403 (Nginx/Apache 기본 거부) 또는 WAF 커스텀 에러 페이지 (아래 상세 참조) |

### 계층 3: JavaScript 수준

- `navigator.webdriver`: `true`이면 자동화 환경으로 즉시 판정
- `window.chrome`: Chrome 브라우저면 존재해야 하는 객체
- `navigator.plugins`: 플러그인 목록 (headless는 보통 비어있음)
- `navigator.languages`: 언어 설정 일관성
- `window.outerHeight/outerWidth`: headless는 0일 수 있음

WebDriver 감지 우회를 위한 **패치 필요 항목 20개+** 는 아래 별도 섹션 참조.

### 계층 4: 행동 수준

| 감지 항목 | 봇 판정 기준 |
|-----------|-------------|
| 마우스 이동 | 클릭 전 마우스 이동이 없으면 봇 의심 |
| 타이핑 속도 | 0ms 간격으로 입력하면 봇 |
| 스크롤 패턴 | 프로그래밍적 `scrollTo` vs 자연스러운 스크롤 |
| 클릭 좌표 | 항상 정확히 요소 중앙 클릭이면 봇 의심 |
| 페이지 체류 시간 | 0초 체류 후 다음 페이지 이동이면 봇 |
| 요청 간격 | 정확히 N초 간격이면 봇 (자연스러운 랜덤 필요) |

### 계층 5: 핑거프린트 수준

| 핑거프린트 | 수집 방식 |
|------------|-----------|
| Canvas | 동일 텍스트를 canvas에 그려서 해시 비교 |
| WebGL | GPU 렌더러 정보 |
| AudioContext | 오디오 처리 결과 |
| 폰트 목록 | 시스템 폰트 열거 |
| 화면 해상도 | `screen.width/height`, `devicePixelRatio` |
| 터치 지원 | `maxTouchPoints` |
| 배터리 API | `navigator.getBattery()` |

## 2. TLS 핑거프린트 상세

### JA3/JA4 해시

TLS 핑거프린트는 TLS Client Hello 패킷의 특성(지원 암호화 스위트, 확장 목록, 타원 곡선 등)을 해시화한 것이다. 같은 라이브러리는 항상 같은 JA3/JA4 해시를 생성하므로, `requests`(urllib3) 같은 라이브러리는 실제 브라우저와 다른 해시를 가진다.

### HTTP/2 프로토콜 핑거프린트

- HTTP/2 설정(SETTINGS 프레임, WINDOW_UPDATE, PRIORITY)도 핑거프린트에 포함된다.
- Chrome, Firefox, Safari는 각각 다른 HTTP/2 설정을 보낸다.
- `requests`는 HTTP/1.1만 사용하므로 즉시 구분된다.

### 대응 도구 비교

| 도구 | TLS 핑거프린트 | HTTP/2 | 브라우저 일치도 | 비고 |
|------|---------------|--------|----------------|------|
| `requests` | Python urllib3 해시 | 미지원 (HTTP/1.1만) | 매우 낮음 | 봇 감지 민감 API에서 즉시 차단 |
| `httpx` | Python 기본 해시 | 지원 가능 | 낮음 | requests보다 나으나 여전히 탐지됨 |
| `curl_cffi` | Chrome/Firefox 해시 위장 | 지원 | 높음 | impersonate 옵션으로 브라우저 모방 |
| `tls-client` | 브라우저 해시 위장 | 지원 | 높음 | Go 기반, 다양한 브라우저 프로필 |
| Playwright/Puppeteer | 실제 브라우저 해시 | 실제 브라우저 | 완벽 | 실제 Chromium/Firefox 사용 |
| Selenium + undetected-chromedriver | 실제 브라우저 해시 | 실제 브라우저 | 높음 | WebDriver 패치 포함 |

## 3. bvsd 상세 구조

> **이것은 특정 시점의 관찰 결과이며, 네이버는 이 구조를 공지 없이 수시로 변경한다.**
> **구현 시 반드시 로그인 페이지의 JS 번들에서 실시간 추출해야 한다. 이 문서의 내용을 하드코딩하면 안 된다.**

### 토큰 구조

```json
{
  "uuid": "{고유 식별자}",
  "encData": "{이중 인코딩된 행동 데이터}",
  "deviceId": "{기기 식별자}",
  "deviceModel": "{기기 모델명}"
}
```

### 이중 인코딩

```
1차: 행동 데이터 JSON → base64 인코딩
2차: 1차 결과를 포함한 전체 구조 → base64 인코딩
```

### uuid 필드

- 매 로그인 시도마다 생성되는 고유 식별자
- 서버에서 이 uuid로 해당 세션의 bvsd 데이터를 추적한다

### deviceId 필드

- 기기별 고유 식별자
- `NID_JKL` 쿠키, Device ID/Registration 시스템과 연동된다 (auth.md 참조)
- 영구 저장하고 복원해야 "기존 기기"로 인식된다

### 타임스탬프 간격 검증

서버는 bvsd 내 각 이벤트의 타임스탬프 간격을 검증한다:

| 패턴 | 판정 |
|------|------|
| 정확히 동일한 간격 (예: 모든 이벤트가 100ms 간격) | 봇 |
| 간격이 0ms | 봇 |
| 이벤트 순서 인과성 위반 (예: mouseup이 mousedown보다 먼저) | 봇 |
| 자연스러운 불규칙 간격 (50~300ms 범위 내 랜덤) | 정상 |

## 4. encData 포맷

> **이것은 특정 시점의 관찰 결과이며, 네이버는 이 포맷을 공지 없이 수시로 변경한다.**
> **구현 시 반드시 로그인 페이지의 JS 번들(lnm.js 또는 현재 번들명)에서 실시간 추출해야 한다.**
> **이 문서의 내용을 하드코딩하면 네이버 변경 시 즉시 로그인에 실패한다.**

### 구조

```
encData 구성:
- 길이 접두사: 1바이트 hex로 각 필드의 길이를 표기
- 값: sessionKey, id, password 순서로 이어붙임
- 전체를 RSA 공개키로 암호화
```

### enctp 필드

- 현재 값: `1` (RSA 기반)
- `enctp` 값이 바뀌면 암호화 방식 자체가 변경된다
- 반드시 로그인 페이지에서 실시간으로 확인해야 한다

## 5. nCaptcha 상세

### 캡차 타입

| 타입 | 설명 | 빈도 |
|------|------|------|
| 이미지 선택형 | "다음 중 {대상}을 모두 선택하세요" | 가장 흔함 |
| 드래그형 | 퍼즐 조각을 맞추는 방식 | 중간 |
| 텍스트 입력형 | 왜곡된 문자 입력 | 레거시, 점점 줄어듦 |

### 트리거 조건

- bvsd 점수가 임계값 미만
- 동일 IP에서 반복 로그인 실패
- 봇 감지 스코어가 높을 때
- 특정 시간대에 비정상적 트래픽 급증

### nCaptcha API 흐름

```
1. GET https://captcha.naver.com/api/v1/captcha?type=image
   → captchaKey, imageUrl 반환

2. POST https://captcha.naver.com/api/v1/verify
   → captchaKey, answer 전송
   → 성공 시 captchaToken 반환

3. captchaToken을 로그인 요청에 포함하여 재시도
```

### 자동화 대응

| 방법 | 설명 | 권장 여부 |
|------|------|-----------|
| 자동화 즉시 중단 | nCaptcha 발생 시 사용자에게 수동 입력 알림 (텔레그램 등) | 권장 |
| 캡차 풀이 서비스 (2Captcha 등) | 외부 서비스로 캡차 풀이 위임 | **법적 리스크 경고**: 정보통신망법 위반 가능 |
| bvsd 품질 향상 | 근본 대응 - bvsd 데이터를 자연스럽게 생성하여 캡차 트리거 자체를 회피 | 최우선 권장 |

## 6. WebDriver 감지 우회 패치 목록 (20개+)

headless 또는 자동화 브라우저 사용 시, 다음 항목을 모두 패치해야 네이버의 JavaScript 수준 감지를 통과할 수 있다.

### 필수 패치 (감지 시 즉시 차단)

| # | 항목 | 설명 |
|---|------|------|
| 1 | `navigator.webdriver` | `false`로 설정. `Object.defineProperty`로 오버라이드 |
| 2 | `window.chrome` | Chrome이면 반드시 존재해야 하는 객체. `runtime`, `loadTimes`, `csi` 포함 |
| 3 | `chrome.runtime` | 빈 객체라도 존재해야 함 |
| 4 | `chrome.loadTimes` | 함수로 정의 |
| 5 | `chrome.csi` | 함수로 정의 |
| 6 | `navigator.plugins` | 최소 3개 이상의 플러그인 목록 (PDF Viewer 등) |
| 7 | `navigator.languages` | `['ko-KR', 'ko', 'en-US', 'en']` 등 자연스러운 배열 |

### 권장 패치 (탐지 정밀도 향상 시 필요)

| # | 항목 | 설명 |
|---|------|------|
| 8 | Permissions API | Notification, Geolocation 권한 쿼리 결과 |
| 9 | WebGL vendor/renderer | GPU 정보 (`ANGLE (...)` 등) |
| 10 | CDP 감지 | `Runtime.evaluate` 흔적 제거 |
| 11 | iframe contentWindow | 접근 패턴이 자연스러워야 함 |
| 12 | Error.stack | "puppeteer", "playwright" 경로가 노출되지 않도록 |
| 13 | `performance.now()` | 정밀도 차이 보정 |
| 14 | `Intl.DateTimeFormat` | `resolvedOptions` 결과 일관성 |
| 15 | `navigator.connection` | 네트워크 정보 객체 존재 |
| 16 | `navigator.hardwareConcurrency` | 코어 수 값 일관성 (보통 4~16) |
| 17 | `screen.availTop/availLeft` | 값이 0이면 headless 의심 |
| 18 | 마우스 이벤트 `isTrusted` | 프로그래밍적 이벤트는 `isTrusted=false` |
| 19 | `window.outerHeight/outerWidth` | 0이면 headless |
| 20 | `navigator.maxTouchPoints` | 데스크톱이면 0, 모바일이면 1 이상 |

### 추가 고려 사항

- `undetected-chromedriver` 또는 Playwright의 `stealth` 플러그인을 사용하면 대부분 자동 패치된다.
- 패치 목록은 네이버 감지 코드 업데이트에 따라 계속 늘어날 수 있다.
- 패치 항목이 많아질수록 유지보수 비용이 증가하므로, 실제 브라우저 프로필을 사용하는 것이 장기적으로 안정적이다.

## 7. WAF 차단 패턴 구분

네이버의 차단 응답은 두 가지 유형으로 나뉜다. 유형에 따라 대응이 다르다.

### 일반 403

- Nginx/Apache 기본 거부 응답
- 단순 IP 차단 또는 경로 접근 제한
- 대기 후 재시도하면 해제될 수 있음

### WAF 커스텀 에러 페이지

- 특정 HTML 패턴이 포함된 에러 페이지
- 커스텀 헤더가 포함될 수 있음
- 봇 감지에 의한 차단으로, 단순 대기로는 해제되지 않을 수 있음
- IP 변경 또는 요청 패턴 변경이 필요

### 구분 방법

```
일반 403:
- 응답 본문이 짧음 (기본 에러 텍스트)
- 표준 HTTP 헤더만 포함

WAF 커스텀:
- 응답 본문에 JavaScript 챌린지 또는 특정 HTML 구조 포함
- 커스텀 헤더 (X-WAF-*, 등) 포함 가능
- 리다이렉트 체인이 포함될 수 있음
```

## 8. Rate Limiting 다층 구조

네이버의 Rate Limiting은 단일 한도가 아닌 다층 구조로 적용된다.

| 계층 | 설명 |
|------|------|
| 서비스별 | 블로그 API / 카페 API / 플레이스 API 각각 별도 한도 |
| API별 | 같은 서비스 내에서도 엔드포인트마다 다른 한도 |
| 계정별 | 계정 신뢰도에 따라 한도 차등 적용 |
| IP별 | 동일 IP의 총 요청 수 제한 |

### 시간 창 방식

- **Sliding Window** 방식 (고정 1분 창이 아님)
- 최근 N초 동안의 요청 수를 실시간으로 계산한다
- 예: "최근 60초 동안 30건 초과" 같은 방식이므로, 정확히 1분 단위로 리셋되지 않는다

### 한도 초과 시 동작

- 429 응답 반환
- `Retry-After` 헤더가 포함될 수 있음 (있으면 해당 시간만큼 대기)
- 반복 초과 시 차단 기간이 점진적으로 늘어남

## 9. 에디터 세션 토큰 3종

블로그/카페에서 글을 작성할 때 필요한 토큰이 3종류가 있으며, 각각 발급 시점과 만료가 다르다.

| 토큰 | 추출 위치 | 용도 | 만료 |
|------|-----------|------|------|
| CSRF 토큰 | `<meta name="_csrf">` | 모든 쓰기 API에 필수 | 페이지 로드마다 갱신 |
| 에디터 세션 토큰 | 에디터 iframe 로드 시 발급 | 에디터 API 전용 | 약 30분 |
| 이미지 업로드 토큰 | 이미지 업로드 API 전용 | 이미지 업로드 | 약 10분 |

### 주의사항

- 3개 토큰의 만료 시점이 모두 다르므로, 장시간 작업 시 중간에 토큰이 만료될 수 있다.
- CSRF 토큰은 페이지를 새로 로드하면 갱신된다.
- 에디터 세션 토큰은 에디터에 진입할 때마다 갱신해야 한다.
- 이미지 업로드 토큰은 업로드 요청 전에 유효한지 확인해야 한다.

## 10. 공통 안티-패턴 (이렇게 하면 차단됨)

아래 패턴은 네이버에서 **즉시 또는 빠르게 차단**되는 행동들이다.

| # | 안티-패턴 | 결과 |
|---|-----------|------|
| 1 | `requests`로 API 호출하면서 쿠키/헤더 없이 요청 | 즉시 403 |
| 2 | User-Agent 없이 또는 `python-requests/2.x` 그대로 요청 | 즉시 차단 |
| 3 | 동일 IP에서 분당 100건 이상 요청 | 429 → 반복 시 IP 차단 |
| 4 | 로그인 세션 없이 글쓰기 API 직접 호출 | 401/403 |
| 5 | bvsd 없이 로그인 시도 | 즉시 캡차 트리거 |
| 6 | Referer 없이 에디터 API 호출 | 403 |
| 7 | 동일 내용의 글을 여러 블로그/카페에 반복 게시 | 스팸 판정 → 저품질 |
| 8 | headless에서 `navigator.webdriver` 패치 안 함 | JS 감지 → 차단 |
| 9 | 프록시 없이 하나의 IP로 다수 계정 운영 | 계정 연쇄 잠금 |
| 10 | 예측 가능한 패턴 (정확히 5초 간격, 항상 같은 시간대) | 행동 패턴 감지 |
| 11 | TLS 핑거프린트 대응 없이 `requests`로 봇 감지 민감 API 호출 | TLS 감지 → 차단 |
| 12 | NNB 쿠키 없이 서비스 API 호출 | 브라우저 식별 누락 → 의심 |

## 11. 상태 코드별 retry 정책

자동화 코드에서 HTTP 응답 상태 코드에 따라 다르게 처리해야 한다.

| 상태 코드 | 의미 | 정책 | 상세 |
|-----------|------|------|------|
| **200** | 정상 | 계속 진행 | 단, 응답 본문에 에러가 포함될 수 있으므로 본문도 확인 |
| **302** | 리다이렉트 | 따라가기 | 로그인 성공, 페이지 전환 등 |
| **400** | 잘못된 요청 | **중단** | 파라미터 오류. 재시도해도 같은 결과 |
| **401** | 인증 필요 | **재로그인** | 세션 만료. 쿠키 갱신 후 재시도 |
| **403** | 접근 금지 | **중단 + 분석** | 봇 차단 가능성. 단순 재시도 금지. WAF 패턴 확인 후 대응 결정 |
| **429** | 속도 제한 | **대기 후 재시도** | `Retry-After` 헤더 확인. 없으면 지수 백오프 (30초 → 60초 → 120초) |
| **500** | 서버 오류 | **재시도** (최대 3회) | 네이버 서버 일시 장애. 30초 간격으로 최대 3회 재시도 |
| **502/503** | 서버 과부하 | **재시도** (최대 3회) | 500과 동일하게 처리 |
| **기타** | 예상 외 | **로깅 후 중단** | 응답 전체를 로그로 남기고 수동 확인 |

### 403 응답 시 절대 하면 안 되는 것

- 즉시 재시도: 차단이 강화된다
- 같은 IP/같은 패턴으로 반복: 차단 기간이 늘어난다
- 무시하고 계속 요청: IP 영구 차단으로 이어질 수 있다

### 429 응답 시 지수 백오프 예시

```
1차 대기: 30초
2차 대기: 60초
3차 대기: 120초
4차 이상: 300초 (최대)
+ 각 대기 시간에 랜덤 지터(0~10초) 추가
```
