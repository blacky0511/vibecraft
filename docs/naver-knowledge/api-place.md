# 네이버 플레이스 API 체계 + 진단 트리

> 최종 확인일: 2026-03-30

---

## 1. 플레이스 API 체계

### 1-1. 검색 API

| 엔드포인트 | 메서드 | 용도 | 비고 |
|-----------|--------|------|------|
| `map.naver.com/v5/api/search` | GET | 키워드 기반 장소 검색 | 버전 접두사(v5) 변경 가능 |
| `map.naver.com/p/api/search` | GET | 장소 검색 (신규 경로) | GraphQL 전환 중 |
| `pcmap.place.naver.com/place/{placeId}` | GET | 장소 상세 (PC) | SSR 페이지 |
| `m.place.naver.com/place/{placeId}` | GET | 장소 상세 (모바일) | SSR 페이지 |

**검색 파라미터 (주요):**
- `query`: 검색 키워드
- `type`: 검색 유형 (place, address 등)
- `coords`: 중심 좌표 (위도,경도)
- `bounds`: 검색 범위 (사각형 좌표)
- `page`: 페이지 번호
- `displayCount`: 한 페이지 결과 수

### 1-2. 장소 상세 API

| 엔드포인트 | 메서드 | 용도 |
|-----------|--------|------|
| `map.naver.com/v5/api/sites/summary/{placeId}` | GET | 장소 요약 정보 |
| GraphQL 엔드포인트 | POST | 장소 상세 (전환 중) |
| SSR 페이지 (`__NEXT_DATA__`) | GET | 서버 렌더링 데이터 |

### 1-3. 리뷰 API

| 엔드포인트 | 메서드 | 용도 |
|-----------|--------|------|
| `map.naver.com/v5/api/sites/{placeId}/reviews` | GET | 방문자 리뷰 목록 |
| `pcmap.place.naver.com/restaurant/{placeId}/review` | GET | 리뷰 페이지 (PC) |
| 블로그 리뷰 연동 API | GET | 블로그 글 기반 리뷰 |

### 1-4. 예약 API

| 엔드포인트 | 메서드 | 용도 |
|-----------|--------|------|
| `booking.naver.com/booking/{placeId}` | GET | 예약 페이지 |
| `booking.naver.com/api/v1/booking` | POST | 예약 생성 |

## 2. PC/모바일 분기

네이버 플레이스는 PC와 모바일에서 서로 다른 URL 구조, API 엔드포인트, 응답 형식을 사용한다.

### 2-1. URL 분기

| 환경 | 도메인 | 특징 |
|------|--------|------|
| PC | `pcmap.place.naver.com` | 풀 기능, 넓은 레이아웃 |
| 모바일 | `m.place.naver.com` | 경량화, 터치 최적화 |
| 네이버 지도 내 | `map.naver.com` | 지도 연동 플레이스 |

### 2-2. 자동화 시 분기 전략

```
목적별 권장 접근:
├── 검색 결과 수집 → PC API (결과 양이 많음)
├── 장소 상세 정보 → __NEXT_DATA__ 파싱 (PC/모바일 모두 가능)
├── 리뷰 수집 → 모바일 API (응답이 간결함)
├── 예약 → booking.naver.com (별도 도메인)
└── 지도 좌표 기반 → map.naver.com API
```

**User-Agent 매칭:**
- PC API 호출 시 데스크톱 User-Agent 필수
- 모바일 API 호출 시 모바일 User-Agent 필수
- UA와 API 엔드포인트 불일치 시 403 또는 리다이렉트

## 3. GraphQL 전환

네이버 플레이스는 REST API에서 GraphQL로 점진적으로 전환 중이다.

### 3-1. GraphQL 구조

```
POST map.naver.com/graphql (또는 유사 엔드포인트)

요청 본문:
{
  "operationName": "getPlaceDetail",
  "variables": {
    "placeId": "1234567890"
  },
  "query": "query getPlaceDetail($placeId: String!) { ... }"
}
```

### 3-2. 자동화 영향

| 항목 | REST API | GraphQL |
|------|----------|---------|
| 엔드포인트 | 기능별 별도 URL | 단일 엔드포인트 |
| 파라미터 | URL 쿼리스트링 | JSON body (query + variables) |
| 응답 | 전체 데이터 | 요청한 필드만 반환 |
| 변경 감지 | URL 변경으로 감지 쉬움 | 스키마 변경이므로 감지 어려움 |
| 파싱 | JSON 경로 고정 | query에 따라 응답 구조 변동 |

### 3-3. 전환 대응 전략

```
1. 기존 REST API가 아직 동작하는지 주기적 확인
2. REST API 404/변경 감지 시 → GraphQL 엔드포인트로 전환
3. GraphQL 스키마는 브라우저 네트워크 탭에서 실제 요청 캡처로 파악
4. operationName, query 문자열은 프론트엔드 JS 번들에서 추출 가능
5. REST → GraphQL 전환 시 파싱 로직 전면 수정 필요
```

## 4. __NEXT_DATA__ 파싱

네이버 플레이스 페이지는 Next.js 기반 SSR로 구축되어 있다. `__NEXT_DATA__` 스크립트 태그에서 서버 렌더링 데이터를 직접 추출할 수 있다.

### 4-1. 데이터 위치

```html
<script id="__NEXT_DATA__" type="application/json">
{
  "props": {
    "pageProps": {
      "initialState": {
        "place": {
          "detailInfo": { ... },
          "reviewInfo": { ... },
          "menuInfo": { ... },
          ...
        }
      }
    }
  }
}
</script>
```

### 4-2. 추출 가능 데이터

| 데이터 | 경로 (대략적) | 설명 |
|--------|-------------|------|
| 장소 기본 정보 | `props.pageProps.initialState.place.detailInfo` | 이름, 주소, 전화번호, 카테고리 |
| 영업 시간 | `detailInfo.businessHours` | 요일별 영업 시간 |
| 메뉴 정보 | `menuInfo` | 메뉴 목록, 가격 |
| 리뷰 요약 | `reviewInfo` | 리뷰 수, 평균 별점 |
| 사진 | `photoInfo` | 대표 사진, 사용자 사진 |
| 예약 가능 여부 | `bookingInfo` | 예약 가능 여부, 예약 URL |

### 4-3. 파싱 장점과 주의점

**장점:**
- 별도 API 호출 없이 한 번의 페이지 로드로 모든 데이터 획득
- JSON 형식이므로 파싱 쉬움
- JavaScript 실행 불필요 (requests/curl_cffi로 충분)

**주의점:**
- `__NEXT_DATA__` 구조가 네이버 업데이트 시 변경될 수 있음
- 일부 데이터는 클라이언트 사이드 렌더링으로만 로드 (CSR → __NEXT_DATA__에 미포함)
- 대량 요청 시 봇 감지 트리거 (Rate Limit)
- 모바일과 PC 페이지의 `__NEXT_DATA__` 구조가 다를 수 있음

## 5. 방문자/영수증/예약 리뷰 세분화

네이버 플레이스의 리뷰는 3가지 유형으로 나뉘며, 각각 검증 방식과 자동화 난이도가 다르다.

### 5-1. 리뷰 유형 비교

| 유형 | 검증 방식 | 자동화 난이도 | 신뢰도 |
|------|----------|-------------|--------|
| 방문자 리뷰 | GPS 위치 인증 (모바일) | 매우 높음 | 높음 |
| 영수증 리뷰 | OCR API로 영수증 인증 (7일 이내) | 높음 | 매우 높음 |
| 예약 리뷰 | booking.naver.com 예약 완료 후 작성 | 높음 | 매우 높음 |

### 5-2. 방문자 리뷰

```
인증 흐름:
1. 네이버 앱에서 장소 근처(반경 약 100m) GPS 인증
2. "방문" 버튼 터치 → 방문 인증 완료
3. 인증 후 리뷰 작성 가능 (일정 기간 내)

자동화 어려움:
- GPS 좌표 조작은 기술적으로 가능하지만 탐지됨
- 네이버 앱 전용 기능 (웹에서 불가)
- 모바일 앱 자동화 필요 (Appium 등)
```

### 5-3. 영수증 리뷰

```
인증 흐름:
1. 영수증 사진 촬영/업로드
2. 네이버 OCR API로 영수증 파싱
3. 장소명, 날짜, 금액 매칭 확인
4. 7일 이내 영수증만 유효
5. 인증 성공 시 리뷰 작성 가능

자동화 어려움:
- 실제 영수증 필요
- OCR 검증을 통과해야 함
- 7일 이내 제한
```

### 5-4. 예약 리뷰

```
인증 흐름:
1. booking.naver.com에서 예약 완료
2. 실제 이용 완료 (no-show가 아닌 경우)
3. 이용 완료 후 리뷰 작성 가능

자동화 어려움:
- 실제 예약 + 이용 완료 필요
- 예약 시스템 자체의 봇 감지
- 결제 정보 필요
```

## 6. 블로그 리뷰 연동

### 6-1. 연동 메커니즘

네이버 블로그에 작성한 글이 플레이스 리뷰로 자동 연결되는 시스템이다.

```
연동 조건:
1. 블로그 글에 장소 태그 추가 (place tag)
   또는
2. 블로그 글에 영수증 인증 첨부
   또는
3. 네이버 예약 후 블로그 리뷰 작성

연동 흐름:
블로그 글 발행 → 장소 태그/영수증 감지 → 플레이스 리뷰에 자동 연결
```

### 6-2. 연동 변경 리스크

- 연동 조건이 변경되면 기존에 연동되던 블로그 리뷰가 플레이스에서 사라질 수 있음
- 장소 태그 방식의 변경 (UI/API 변경)
- 블로그 저품질 판정 시 연동된 리뷰도 영향 받을 수 있음

### 6-3. 자동화 시 고려사항

- 블로그 글 자동 발행 + 장소 태그 자동 추가 → 플레이스 리뷰 자동 생성 효과
- 이 방식은 리뷰 자동 생성과 실질적으로 동일 → 법적 리스크 높음 (아래 9장 참조)
- 블로그 글의 품질이 낮으면 연동 자체가 안 될 수 있음

## 7. 스마트플레이스 광고 구분

### 7-1. 광고 유형

| 유형 | 표시 위치 | 식별 방법 |
|------|----------|----------|
| 플레이스 광고 | 검색 결과 상단/하단 | "광고" 라벨, 별도 CSS 클래스 |
| 브랜드 검색 | 검색 결과 최상단 | 브랜드 영역 별도 표시 |
| 자연 노출 | 검색 결과 본문 | 광고 라벨 없음 |

### 7-2. 자동화 시 광고 구분

```
검색 결과 파싱 시:
├── 광고 영역 식별
│   ├── CSS 클래스/셀렉터로 구분 (ad, sponsored 등)
│   ├── 데이터 속성 확인 (data-ad-type 등)
│   └── 검색 API 응답의 isAd, adType 필드
├── 자연 노출 영역만 추출
│   └── 광고 필터링 후 순위 계산
└── 광고/자연 구분이 중요한 이유
    ├── 순위 모니터링 시 광고를 제외해야 정확한 순위
    ├── 광고 순위는 입찰가에 따라 변동
    └── 자연 순위가 실제 SEO 성과 지표
```

### 7-3. 광고 셀렉터 변경 주의

- 네이버는 광고 셀렉터를 주기적으로 변경
- 광고 차단 도구(adblock) 우회를 위해 클래스명 난독화
- 자동화 코드에서 광고 구분 셀렉터를 하드코딩하면 변경 시 깨짐
- 가능하면 검색 API 응답의 구조화된 필드로 구분

## 8. 플레이스 진단 트리

### 8-1. 검색 단계

```
키워드 검색 API 접근 가능?
├── NO → URL 변경 확인
│   ├── 버전 변경: v5 → v6 등
│   ├── 도메인 변경: map.naver.com → 다른 도메인
│   ├── GraphQL 전환으로 REST API 폐지
│   └── 403/429 → 봇 감지 또는 Rate Limit
└── YES ↓

검색 결과 반환? → 파싱 정상?
├── 결과 없음 → 키워드/좌표 확인
├── 파싱 실패 → 응답 스키마 변경 확인
│   ├── JSON 필드명 변경
│   ├── 중첩 구조 변경
│   └── 새 필드 추가로 기존 파싱 깨짐
└── 정상 ↓

장소 상세 정보 API
├── __NEXT_DATA__ 파싱
│   ├── 데이터 구조 변경 확인
│   ├── 일부 데이터 CSR 전환 (SSR에서 제거됨)
│   └── 모바일/PC 구조 차이
├── GraphQL API
│   ├── operationName 변경 확인
│   ├── query 스키마 변경 확인
│   └── 인증 요구사항 변경
└── REST API (레거시)
    └── 여전히 동작하는지 확인

스마트플레이스 광고 구분
├── 광고 영역 셀렉터 변경 확인
│   ├── CSS 클래스명 변경
│   ├── 데이터 속성 변경
│   └── HTML 구조 변경
├── 유료 광고 결과: 별도 영역/라벨 표시
├── 자연 노출: 일반 검색 결과
└── API 응답의 광고 필드 확인 (isAd, adType)

페이지네이션 / 필터링
├── 페이지네이션 파라미터 변경 (page, start, display)
├── 필터 옵션 변경 (정렬, 카테고리, 거리)
└── 최대 결과 수 제한
```

### 8-2. 리뷰/예약 단계

```
리뷰 유형 세분화
├── 방문자 리뷰
│   ├── GPS 위치 인증 기반 (모바일 전용)
│   ├── 자동화 난이도: 매우 높음
│   └── 위치 조작 탐지 시 → 계정 제재
├── 영수증 리뷰
│   ├── OCR API로 영수증 인증 (7일 이내)
│   ├── 자동화 난이도: 높음
│   └── 실제 영수증 필요
├── 예약 리뷰
│   ├── booking.naver.com 예약 완료 후 작성 가능
│   ├── 자동화 난이도: 높음
│   └── 실제 예약 + 이용 완료 필요
└── 각 유형별 검증 방식이 다르므로 자동화 접근법도 다름

블로그 리뷰 연동
├── 블로그에 작성한 글이 플레이스 리뷰에 자동 연결
├── 장소 태그 또는 영수증 인증 시 연동
├── 연동 조건 변경 시 리뷰가 플레이스에서 사라질 수 있음
└── 블로그 자동 발행 + 장소 태그 = 리뷰 자동 생성과 동일 (법적 리스크)

리뷰 스팸 필터
├── 동일 IP 다수 리뷰 → IP 차단
├── 유사 내용 반복 → 스팸 판정
├── 단시간 대량 리뷰 → 계정 제재
└── 리뷰 자동 생성은 불법 (아래 9장 참조)

예약 API (booking.naver.com)
├── 예약 가능 시간 조회
│   ├── 장소별 예약 가능 시간대 API
│   └── 실시간 재고 확인
├── 예약 생성
│   ├── 로그인 필수 (NID 인증)
│   ├── 결제 정보 필요 (경우에 따라)
│   └── 봇 감지 엄격 (대량 예약 방지)
├── 예약 확인/취소
│   └── 예약 번호 기반 조회/취소 API
└── 예약 후 리뷰 작성 가능 여부
    └── 이용 완료 상태 확인
```

## 9. 법적 리스크 참조

플레이스 자동화는 리뷰와 관련하여 법적 리스크가 특히 높다.

### 9-1. 행위별 법적 분류

| 행위 | 분류 | 관련 법률 | 비고 |
|------|------|----------|------|
| 플레이스 검색 결과 수집 (소량) | 합법 (Green) | - | 공개 정보 열람 |
| 장소 정보 수집 (공개 데이터) | 합법 (Green) | - | 공개 정보 |
| 대량 검색/크롤링 | 회색 (Yellow) | 네이버 이용약관, robots.txt | 서버 부하 유발 시 위험 |
| 경쟁 업체 순위 모니터링 | 회색 (Yellow) | - | 빈도 제한 준수 시 허용 |
| 가짜 리뷰 자동 생성 | **불법 (Red)** | 공정거래법, 표시광고법 | **과태료 최대 2억원, 시정 명령** |
| 리뷰 조작 (별점 조작) | **불법 (Red)** | 공정거래법, 표시광고법 | **과태료 최대 2억원** |
| 리뷰 대행 서비스 | **불법 (Red)** | 공정거래법 | 사업자도 의뢰자도 처벌 |
| GPS 위치 조작 | 불법 (Red) | 정보통신망법 48조 | 정보통신망 침해 |
| 영수증 위조 | 불법 (Red) | 형법 (사문서위조) | 5년 이하 징역 |

### 9-2. 공정거래위원회 규제

2020년 이후 공정거래위원회는 온라인 리뷰 조작에 대한 규제를 대폭 강화했다.

```
주요 규제 내용:
1. 대가성 리뷰 미표기 시 표시광고법 위반
   - "해당 리뷰는 대가를 받고 작성되었습니다" 표기 의무
   - 미표기 시 과태료 최대 2억원

2. 가짜 리뷰 작성/의뢰
   - 실제 이용하지 않은 리뷰 작성 = 허위 표시 광고
   - 리뷰 대행 업체 + 의뢰한 사업자 모두 처벌

3. 경쟁 업체 비방 리뷰
   - 경쟁 업체에 악의적 리뷰 = 부정경쟁행위

4. 리뷰 삭제 강요/대행
   - 부정적 리뷰 삭제 대행도 규제 대상
```

### 9-3. 진단 시 법적 리스크 판단 기준

```
플레이스 자동화 진단 시 반드시 확인:
1. 리뷰 자동화가 포함되어 있는가?
   ├── YES → 법적 리스크 경고 필수
   │   ├── 리뷰 작성 자동화 → 불법 가능성 매우 높음
   │   ├── 리뷰 수집/분석만 → 합법 (데이터 분석 목적)
   │   └── 리뷰 답변 자동화 → 회색 (본인 업체인 경우 허용적)
   └── NO → 일반 진단 진행

2. 대가성 리뷰 관련인가?
   ├── YES → 표시광고법 위반 경고
   └── NO → 계속

3. GPS 위치 조작이 포함되는가?
   ├── YES → 정보통신망법 위반 경고
   └── NO → 계속
```

> 진단 보고서에는 반드시 현재 자동화의 법적 분류를 포함해야 한다.
> 리뷰 자동화가 포함된 경우 불법(Red) 가능성을 최우선으로 경고한다.
> 특히 공정거래위원회의 리뷰 조작 단속이 강화되고 있으므로, 리뷰 관련 자동화는 극도로 주의해야 한다.
