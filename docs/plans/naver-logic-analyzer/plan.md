# naver-logic-analyzer 에이전트 상세 설계 계획서 (v2)

> CTO 3명 피드백 전면 반영 버전

## 1. 개요

### 목적
네이버 서비스 자동화 과정에서 발생하는 문제를 체계적으로 진단하고, 해결 계획을 수립하는 전문 에이전트.
직접 코드를 수정하지 않고, **진단 + 계획**만 수행한다. 실제 구현은 다른 에이전트(backend-builder, debugger 등)에게 위임한다.

### 역할 포지션
```
사용자: "네이버 블로그 자동 포스팅이 안 돼요"
         ↓
naver-diagnosis 스킬: 사용자 입력 파악 → 이력 확인 → 에이전트 호출
         ↓
naver-logic-analyzer: 5렌즈 통합 분석 → 원인 확정 → 해결 계획 수립
         ↓
backend-builder / debugger: 계획에 따라 코드 수정/구현
```

### 왜 별도 에이전트인가
- 네이버는 범용 디버깅(debugger.md)으로 해결하기 어려운 **고유 메커니즘**(bvsd, encData, nCaptcha 등)이 존재
- "차단"과 "변경"을 구분하는 분기 로직이 네이버에 특화되어 있음
- 서비스별(블로그/카페/플레이스/검색/트래픽/스마트스토어) 진단 트리가 완전히 다름
- 진단 이력 축적으로 네이버 변경 패턴을 학습하는 장기 가치 존재

## 3. 5렌즈 통합 분석 프레임워크

하나의 전문가가 5개 관점을 적용하여 문제를 다각도로 분석한다.
**단, 모든 렌즈를 항상 실행하지 않는다.** 차단/변경 분류에 따라 빠른 경로로 우선 분석한다.

<!-- [피드백 #4 반영] 빠른 경로 도입 — 분류별 2-3개 렌즈 우선, 수렴 안 되면 나머지 추가 -->

### 3-0. 빠른 경로 (Fast Path)

1단계 증상 수집 직후 차단/변경을 1차 분류하고, 해당 분류에 맞는 렌즈만 우선 실행한다.

```
차단 의심: 보안 → 네트워크 → 자동화 (3개 우선)
  └── 수렴 실패 시 → API + 브라우저 추가

변경 의심: API → 브라우저 → 자동화 (3개 우선)
  └── 수렴 실패 시 → 보안 + 네트워크 추가

복합/불명확: 전체 5개 렌즈 실행

에스컬레이션: 우선 렌즈 3개로 원인이 수렴되지 않으면
  → 나머지 렌즈 추가 실행 (최대 5개)
```

### 3-1. 네트워크 렌즈 (Network)

> HTTP 통신 계층에서 문제를 찾는다.

**분석 대상:**
- HTTP 요청/응답 헤더 전문 (특히 `Set-Cookie`, `X-Naver-*`, `Content-Type`)
- 응답 상태 코드 (200/302/403/429/500)
- 요청 페이로드 (POST body, form data, multipart)
- 쿠키 체인 (NID_AUT → NID_SES → NNB → 서비스별 쿠키)
- SSL/TLS 핸드셰이크 (인증서 핀닝 여부)
- 리다이렉트 체인 (302 → 302 → 200 경로 추적)
- DNS 해석 (nid.naver.com, blog.naver.com 등 도메인별)
- Keep-Alive / Connection 헤더
- Rate Limit 헤더 (`X-RateLimit-*`, `Retry-After`)
- WAF 차단 응답 구분 (일반 403 vs WAF 커스텀 에러 페이지)

**네이버 특화 확인:**
- `NID_AUT` 쿠키 도메인/경로/만료시간
- `NID_SES` 세션 쿠키 유효성
- `NID_JKL` 기기 인증 쿠키 존재 여부
- `NNB` 쿠키 (네이버 전역 브라우저 식별)
- `JSESSIONID` (일부 서비스)
- `nhn.realestate.session.key` (부동산 등 서브서비스)
- CORS preflight 요청 처리 여부
- 쿠키 도메인 스코프 변경 감지 (.naver.com → 서브도메인)
- SameSite 정책 (Lax → Strict 전환 추세)

### 3-2. 브라우저 렌즈 (Browser)

> DOM 구조, JavaScript 실행, 렌더링 환경에서 문제를 찾는다.

**분석 대상:**
- DOM 구조 변경 (셀렉터 변경, 요소 추가/제거)
- JavaScript 번들 로딩 순서 (DOMContentLoaded vs load)
- iframe 구조 (네이버 에디터는 다중 iframe)
- Shadow DOM 사용 여부
- 동적 렌더링 (React/Vue SPA vs SSR)
- WebDriver 감지 코드 (`navigator.webdriver`, `window.chrome` 등)
- Canvas/WebGL 핑거프린트 수집 코드
- Service Worker 등록 여부
- CSP(Content Security Policy) 헤더

**네이버 특화 확인:**
- SmartEditor ONE의 iframe 구조 (`se2_iframe`, `mainFrame`)
- SmartEditor 3 (구에디터) 분기 — 일부 블로그에서 아직 사용
- 에디터 로딩 완료 시점 판별 (에디터 Ready 이벤트)
- 네이버 로그인 페이지의 동적 폼 구조 (로그인 폼이 JS로 렌더링)
- `__cmpFrameId` 등 네이버 커스텀 속성
- `gnb` (Global Navigation Bar) 로딩 여부로 페이지 정상 로드 판별

### 3-3. 보안 렌즈 (Security)

> 봇 감지, 캡차, 인증 강화 메커니즘에서 문제를 찾는다.

**분석 대상:**
- 봇 감지 시스템 트리거 여부
- nCaptcha 발생 조건 및 타입
- bvsd(행동 검증) 데이터 구조
- encData(RSA 암호화) 생성 과정
- dynamicKey 발급 및 사용
- IP 블랙리스트/그레이리스트
- User-Agent 검증 수준
- 브라우저 핑거프린트 일치도
- 접속 패턴 이상 감지 (속도, 빈도, 규칙성)
- Naver Guard(기기 인증) 트리거 조건
- TLS 핑거프린트 (3-3-1 참조)
- 계정 신뢰도 점수 (계정 나이, 활동 이력 등)

**네이버 특화 확인:**
- `bvsd` 토큰: 마우스 이동 궤적, 키보드 입력 타이밍, 스크롤 패턴을 JSON으로 수집 → base64 인코딩
- `encData`: nid.naver.com에서 RSA 공개키를 받아 → 아이디+비밀번호를 암호화 → POST 전송
- `dynamicKey`: 로그인 폼 HTML 내 `<input type="hidden">` 으로 매번 새로 발급
- `captchaKey`: nCaptcha 트리거 시 발급되는 키
- `challenge`: 캡차 이미지/문제 데이터
- 2차 인증: OTP, 이메일 인증, 휴대폰 인증, 네이버 앱 QR/원터치 로그인 분기

#### 3-3-1. TLS 핑거프린트 상세

TLS 핑거프린트는 봇 감지의 핵심 계층으로, HTTP 헤더나 JS 실행 이전 단계에서 자동화 도구를 식별한다.

**JA3/JA4 해시:**
- TLS Client Hello 메시지의 필드(TLS 버전, Cipher Suites, Extensions, Elliptic Curves, Point Formats)를 조합하여 고유 해시 생성
- Chrome, Firefox, Safari, Python requests, Playwright, Puppeteer 각각 고유 JA3 해시를 가짐
- Python `requests`의 JA3는 Chrome과 완전히 다름 — 서버에서 즉시 구분 가능
- Playwright/Puppeteer의 JA3도 실제 Chrome과 미묘한 차이 존재

**HTTP/2 핑거프린트 (Akamai h2 fingerprint):**
- HTTP/2 SETTINGS 프레임의 파라미터 순서, 값, WINDOW_UPDATE 크기 등으로 식별
- 브라우저마다 고유한 h2 핑거프린트 보유
- 자동화 도구가 h2 핑거프린트를 완벽히 모방하기 어려움

**대응 도구:**
| 도구 | 방식 | JA3 모방 | h2 모방 | 적합 상황 |
|------|------|---------|---------|---------|
| curl_cffi | libcurl + 브라우저 TLS impersonation | O | O | requests 대체, 가장 쉬움 |
| tls-client | Go TLS + Python 바인딩 | O | O | 고성능, Go 의존성 |
| httpx + h2 | httpx + hyper-h2 | 부분 | O | 기존 httpx 사용 시 |
| cloudscraper | requests + 클라우드플레어 우회 | 부분 | X | CF 보호 사이트 한정 |
| Playwright + 실제 Chromium | 실제 브라우저 | O (네이티브) | O (네이티브) | 완벽하지만 느림 |

**자동화 렌즈 판단 기준에 추가:**
- 현재 HTTP 클라이언트의 JA3 해시가 실제 브라우저와 일치하는지
- h2 핑거프린트가 노출되는지
- TLS 핑거프린트 우회 도구 사용 여부

### 3-4. API 렌즈 (API)

> 네이버 내부 API의 구조, 버전, 파라미터 변경을 분석한다.

**분석 대상:**
- 엔드포인트 URL 변경 (`/api/v1/` → `/api/v2/`)
- 요청 파라미터 변경 (필수 파라미터 추가/삭제/이름 변경)
- 응답 스키마 변경 (필드 추가/삭제/타입 변경)
- 인증 방식 변경 (쿠키 → OAuth → Bearer 토큰)
- Content-Type 변경 (`application/x-www-form-urlencoded` → `application/json`)
- API 버전 deprecation 공지
- 공식 API vs 비공식 API 구분 (한 문단으로 간략화)
- GraphQL 도입 여부
- API Gateway 변경 (WAF 추가 등)

<!-- [피드백 #13 반영] OAuth 섹션을 "공식 API vs 비공식 API 구분" 한 문단으로 축소 -->

**공식 API vs 비공식 API:**
공식 API(`openapi.naver.com`)는 API 키 인증, 정해진 rate limit, 안정적 스키마를 제공하지만 블로그 글쓰기, 카페 글쓰기 등 대부분의 자동화 대상은 공식 API가 없다. 비공식 API(웹 페이지 내부 호출 API)는 기능이 풍부하지만 언제든 변경될 수 있고, 쿠키 인증 + CSRF 토큰이 필요하며, 봇 감지에 민감하다. 진단 시 현재 사용 중인 것이 공식/비공식 중 무엇인지 먼저 확인한다.

**네이버 특화 확인:**
- 블로그 에디터 API: `/postWrite.naver` → `/editor/save.json` 같은 변경 이력
- 플레이스 API: `map.naver.com/v5/api/search` 등 버전 접두사 변경
- 카페 API: 멤버 인증 토큰 방식 변경
- 검색 API: 공식(`openapi.naver.com`) vs 비공식(`search.naver.com`) 구분
- 모바일/PC API 분기: `m.` 서브도메인 vs 데스크톱 API 차이
- 스마트스토어 API: `commerce.naver.com` API 체계

### 3-5. 자동화 렌즈 (Automation)

> 자동화 구현 전략과 도구 선택의 적합성을 판단한다.

**분석 대상:**
- 현재 자동화 방식 (requests / selenium / playwright / scrapy / puppeteer / curl_cffi)
- 방식과 대상의 적합성 (JS 렌더링 필요 여부, 인터랙션 필요 여부)
- TLS 핑거프린트 적합성 (requests의 JA3 문제 → curl_cffi 전환 필요성)
- 타이밍 이슈 (대기 시간, 로딩 완료 감지)
- 에러 핸들링 전략 (재시도, 폴백, 서킷 브레이커)
- 동시성 처리 (멀티스레드, 비동기, 프록시 로테이션)
- 세션 관리 방식 (쿠키 저장/복원, 로그인 유지)
- 실행 환경 (로컬 / 서버 / Docker / Lambda)

**판단 기준:**
```
requests/curl_cffi 적합:
  - API 직접 호출 가능
  - JS 렌더링 불필요
  - 쿠키/헤더만으로 인증 가능
  - 높은 처리 속도 필요
  - curl_cffi: TLS 핑거프린트 우회 필요 시 requests 대체

selenium 적합:
  - JS 렌더링 필수
  - 복잡한 인터랙션 (드래그, 파일 업로드)
  - 기존 코드가 selenium 기반
  - 안정적인 실행 우선

playwright 적합:
  - JS 렌더링 필수 + 현대적 API
  - 멀티 브라우저 지원 필요
  - 네트워크 인터셉트 필요
  - headless 안정성 중요
  - 새 프로젝트 시작

하이브리드 적합:
  - 로그인은 curl_cffi, 에디터는 playwright
  - API 호출은 curl_cffi, 봇 감지 우회는 playwright
```

### 4-1. 네이버 인증 체계 (→ docs/naver-knowledge/auth.md)

#### 로그인 흐름 (nid.naver.com)

```
[1] GET https://nid.naver.com/nidlogin.login
    → 로그인 폼 HTML 반환
    → 이 HTML에 RSA 공개키(modulus, exponent)가 포함
    → dynamicKey, sessionKey도 hidden input으로 포함

[2] RSA 암호화
    → 서버가 제공한 공개키로 아이디+비밀번호 암호화
    → encData = RSA(sessionKey + "\n" + id + "\n" + password)
    → JavaScript의 rsa.js 또는 로그인 번들에서 수행

[3] bvsd 토큰 생성
    → 페이지 로딩 후 사용자 행동 데이터 수집:
      - 마우스 이동 좌표 배열
      - 키보드 입력 타이밍 (keydown/keyup 간격)
      - 스크롤 이벤트
      - 포커스 전환 이벤트
      - 페이지 체류 시간
    → JSON으로 직렬화 → base64 인코딩
    → 이 데이터가 너무 단순하면(마우스 움직임 0건 등) 봇으로 판정

[4] POST https://nid.naver.com/nidlogin.login
    → enctp: 1
    → encData: {RSA 암호화된 데이터}
    → bvsd: {행동 검증 데이터}
    → dynamicKey: {동적 키}
    → logintp: {로그인 타입}
    → svctype: {서비스 타입}
    → smart_LEVEL: {보안 수준}
    → locale: ko_KR

[5] 응답 분기
    → 성공: 302 → callback URL + NID_AUT, NID_SES 쿠키 발급
    → 캡차: 200 + captcha 관련 필드 반환
    → 기기 인증: 200 + new_device=true + deviceName 요청
    → 계정 잠금: 200 + loginStatus=LOCK
    → IP 차단: 403 또는 특정 에러 페이지로 리다이렉트
    → QR/원터치 강제: 200 + 네이버 앱 인증 요구 (신규 기기 + 고위험)
```

#### 쿠키 상세

| 쿠키 | 도메인 | 역할 | 만료 | 비고 |
|------|--------|------|------|------|
| NID_AUT | .naver.com | 로그인 인증 토큰 | 세션/영구 | 핵심 인증 쿠키, 이것 없으면 비로그인 |
| NID_SES | .naver.com | 세션 유지 | 세션 | NID_AUT와 함께 사용 |
| NID_JKL | .naver.com | 기기 인증 | 장기 | Naver Guard 통과 시 발급 |
| NNB | .naver.com | 브라우저 식별 | 장기 | 네이버 전역 브라우저 ID, 봇 감지에 활용 |
| nid_inf | .naver.com | 부가 인증 정보 | 세션 | 인증 상태 보조 |

**쿠키 체인 순서 의존성:**
```
NID_AUT → NID_SES → NNB → 서비스별 쿠키 (BlogUser, CafeMember 등)
순서가 중요: NID_AUT 없이 서비스 쿠키를 보내면 세션 무효화 가능
```

**쿠키 도메인 스코프 변경 감지:**
- 기존: `.naver.com` (전체 서브도메인 공유)
- 변경 추세: 일부 쿠키가 서브도메인 한정으로 전환 (보안 강화)
- SameSite 정책: Lax가 기본, 일부 서비스에서 Strict 전환 중

**Device ID/Registration 시스템:**
- 네이버는 기기별 고유 deviceId를 발급/관리
- `NID_JKL` 쿠키 외에 별도 deviceId가 서버에 등록
- 자동화 시 deviceId를 영구 저장하고 복원해야 "기존 기기" 인식
- 새 deviceId로 접속 시 2차 인증 트리거 확률 급증

#### 2차 인증 트리거 조건

```
트리거 조건 (하나라도 해당되면 2차 인증 요구):
1. 새 기기에서 접속 (NID_JKL 쿠키 없음, deviceId 미등록)
2. 해외 IP에서 접속 (GeoIP 국가 불일치)
3. 비정상 패턴 감지 (bvsd 점수 낮음)
4. 일정 기간(약 30일) 미접속 후 재접속
5. 비밀번호 변경 후 첫 로그인
6. 보안 설정에서 "2단계 인증" 활성화된 계정
7. 여러 IP에서 동시 세션 감지
8. 계정 신뢰도 점수 낮음 (신규 계정, 활동 이력 적음)

2차 인증 방식:
- 등록된 휴대폰 SMS 인증
- 네이버 앱 OTP 인증
- 이메일 인증 (보조 이메일)
- Naver Guard 앱 푸시 인증
- 네이버 앱 QR 코드 인증 (최근 강제 빈도 증가)
- 네이버 앱 원터치 인증
```

### 4-2. 네이버 봇 감지 시스템 (→ docs/naver-knowledge/bot-detection.md)

<!-- [피드백 #7 반영] bvsd 상세, encData 포맷, WebDriver 패치 목록 등 보강 -->

#### 감지 계층 (외부 → 내부 순서)

```
[계층 1: 네트워크 수준]
- IP 레퓨테이션: 알려진 데이터센터 IP, VPN IP, 프록시 IP 차단
- IP 속도 제한: 동일 IP에서 분당 N건 이상 요청 시 429 반환
- IP 패턴: 동일 IP에서 다수 계정 로그인 시도 시 차단
- TLS 핑거프린트: JA3/JA4 해시로 자동화 도구 구분 (3-3-1 참조)

[계층 2: HTTP 수준]
- User-Agent 검증:
  - 실제 브라우저 UA와 일치하는지 (버전 번호까지)
  - UA와 실제 브라우저 동작이 일치하는지 (Chrome UA인데 Firefox 동작)
- Referer 검증:
  - API 직접 호출 시 Referer 없으면 의심
  - Referer 도메인이 naver.com 계열인지
- Accept-Language, Accept-Encoding 등 부가 헤더 일관성
- WAF 차단 패턴:
  - 일반 403: Nginx/Apache 기본 거부
  - WAF 커스텀 에러 페이지: 특정 HTML 패턴, 커스텀 헤더 포함

[계층 3: JavaScript 수준]
- navigator.webdriver: true이면 자동화 환경
- window.chrome: Chrome이면 존재해야 하는 객체
- navigator.plugins: 플러그인 목록 (headless는 보통 비어있음)
- navigator.languages: 언어 설정 일관성
- window.outerHeight/outerWidth: headless는 0일 수 있음
- 추가 패치 필요 목록 (20개+):
  - chrome.runtime, chrome.loadTimes, chrome.csi
  - Permissions API (Notification, Geolocation)
  - WebGL vendor/renderer 정보
  - CDP(Chrome DevTools Protocol) 감지: Runtime.evaluate 흔적
  - iframe contentWindow 접근 패턴
  - Error.stack에 "puppeteer", "playwright" 경로 노출
  - performance.now() 정밀도 차이
  - Intl.DateTimeFormat resolvedOptions
  - navigator.connection 네트워크 정보
  - navigator.hardwareConcurrency 값 일관성
  - screen.availTop/availLeft 값
  - 마우스 이벤트 isTrusted 속성

[계층 4: 행동 수준]
- 마우스 이동: 클릭 전 마우스 이동이 없으면 봇 의심
- 타이핑 속도: 0ms 간격으로 입력하면 봇
- 스크롤 패턴: 자연스러운 스크롤 vs 프로그래밍적 scrollTo
- 클릭 좌표: 항상 정확히 요소 중앙 클릭이면 봇 의심
- 페이지 체류 시간: 0초 체류 후 다음 페이지 이동이면 봇
- 요청 간격: 정확히 N초 간격이면 봇 (자연스러운 랜덤 필요)

[계층 5: 핑거프린트 수준]
- Canvas 핑거프린트: 동일 텍스트를 canvas에 그려서 해시 비교
- WebGL 핑거프린트: GPU 렌더러 정보
- AudioContext 핑거프린트: 오디오 처리 결과
- 폰트 목록: 시스템 폰트 열거
- 화면 해상도: screen.width/height, devicePixelRatio
- 터치 지원: maxTouchPoints
- 배터리 API: navigator.getBattery()
```

**Rate Limiting 다층 구조:**
```
서비스별: 블로그 API / 카페 API / 플레이스 API 각각 별도 한도
API별: 같은 서비스 내에서도 엔드포인트마다 다른 한도
계정별: 계정 신뢰도에 따라 한도 차등 적용
IP별: 동일 IP의 총 요청 수 제한
시간 창: sliding window 방식 (고정 1분 창이 아님)
```

#### bvsd 상세 구조

```
bvsd 토큰 구조:
{
  "uuid": "{고유 식별자}",
  "encData": "{이중 인코딩된 행동 데이터}",
  "deviceId": "{기기 식별자}",
  "deviceModel": "{기기 모델명}",
  ...
}

이중 인코딩:
1차: 행동 데이터 JSON → base64
2차: 1차 결과를 포함한 전체 구조 → base64

타임스탬프 간격 검증:
- 각 이벤트의 타임스탬프 간격이 자연스러운지 검증
- 정확히 동일한 간격 → 봇 판정
- 간격이 0ms → 봇 판정
- 이벤트 순서의 인과성 검증 (mousedown → mouseup 순서 등)
```

#### encData 정확한 포맷

> **⚠️ 중요 경고**: 아래 서술은 **특정 시점의 관찰 결과**이며, 네이버는 이 포맷을 공지 없이 수시로 변경한다.
> **구현 시 반드시 로그인 페이지의 JS 번들(lnm.js 또는 현재 번들명)에서 실시간 추출해야 한다.**
> 이 계획서의 내용을 하드코딩하면 네이버 변경 시 즉시 로그인 실패한다.

```
encData 구조:
- 길이 접두사: 1바이트 hex로 각 필드의 길이 표기
- 값: sessionKey, id, password 순서로 이어붙임
- 전체를 RSA 공개키로 암호화

enctp 필드:
- 현재 값: 1 (RSA 기반)
- 버전 변경 가능성: enctp 값이 바뀌면 암호화 방식 자체가 변경됨
- 반드시 로그인 페이지에서 실시간으로 확인해야 함
```

#### nCaptcha 상세

```
nCaptcha 타입:
1. 이미지 선택형: "다음 중 {대상}을 모두 선택하세요" (가장 흔함)
2. 드래그형: 퍼즐 조각을 맞추는 방식
3. 텍스트 입력형: 왜곡된 문자 입력 (레거시, 점점 줄어듦)

트리거 조건:
- bvsd 점수가 임계값 미만
- 동일 IP에서 반복 로그인 실패
- 봇 감지 스코어가 높을 때
- 특정 시간대에 비정상적 트래픽 급증

nCaptcha API 흐름:
  GET https://captcha.naver.com/api/v1/captcha?type=image
    → captchaKey, imageUrl 반환
  POST https://captcha.naver.com/api/v1/verify
    → captchaKey, answer 전송
    → 성공 시 captchaToken 반환 → 로그인 요청에 포함

자동화 대응:
- nCaptcha 발생 시 자동화 즉시 중단
- 사용자에게 수동 캡차 입력 알림 (텔레그램 봇 등)
- 캡차 풀이 서비스(2Captcha 등): ⚠️ 법적 리스크 경고 필수 (4-5 법적 리스크 참조)
- 근본 대응: bvsd 데이터 품질 향상으로 캡차 트리거 회피
```

#### 에디터 세션 토큰 3종

```
1. CSRF 토큰: <meta name="_csrf"> 에서 추출, 모든 쓰기 API에 필수
2. 에디터 세션 토큰: 에디터 iframe 로드 시 발급, 에디터 API 전용
3. 이미지 업로드 토큰: 이미지 업로드 API 전용, 별도 만료

각각 만료 시점이 다르므로:
- CSRF: 페이지 로드마다 갱신
- 에디터: 에디터 진입마다 갱신 (약 30분 만료)
- 이미지: 업로드 요청마다 확인 (약 10분 만료)
```

### 4-3. 네이버 서비스별 API 체계 (→ docs/naver-knowledge/api-{서비스}.md)

각 서비스 API의 상세 내용은 참조 파일에 수록한다. 여기서는 구조만 요약한다.

#### 블로그 (→ api-blog.md)
- SmartEditor ONE (React 기반, 다중 iframe) + SmartEditor 3 (구에디터) 분기
- 글 작성: `POST /RabbitWrite.naver` 또는 `/editor/mainContent.json`
- 이미지 업로드: `POST /editor/uploadContent.json`
- CSRF 토큰 필수, Referer 필수, NID_AUT + NID_SES + BlogUser 쿠키 필요
- 스팸 필터: 동일 내용 반복, 금지어, 링크 과다, 신규 블로그 제한
- 블로그 저품질 판정 (패널티): 검색 노출 제한, 비공개 전환
- HTML 콘텐츠 필터링: 특정 태그/속성 자동 제거

#### 카페 (→ api-cafe.md)
- 접근 권한: 카페 가입 → 멤버 등급 → 게시판별 권한
- 글쓰기: `POST /ca-fe/cafes/{cafeId}/articles`
- CSRF + useSafeContent(XSS 방지) 필수
- 카페 금지어 필터: 카페별 자체 금지어 목록 존재
- 가입 후 N일 글쓰기 제한: 카페별 설정 상이
- IP 기반 카페 차단: 동일 IP에서 다수 카페 활동 시

#### 플레이스 (→ api-place.md)
- 검색: `GET map.naver.com/v5/api/search`, GraphQL 전환 중
- `__NEXT_DATA__`에서 SSR 데이터 추출 가능
- 리뷰 세분화: 방문자 리뷰 / 영수증 리뷰 / 예약 리뷰 (각각 검증 방식 다름)
- 블로그 리뷰 연동: 블로그 글이 플레이스 리뷰로 자동 연결
- 스마트플레이스 광고: 유료 광고 vs 자연 노출 구분 필요

#### 검색 (→ api-search.md)
- 공식: `GET openapi.naver.com/v1/search/{type}.json` (일일 25,000건)
- 비공식: `GET search.naver.com/search.naver` (봇 감지 민감)
- VIEW 탭 통합: 블로그+카페 통합 검색 결과 탭
- AI 검색 (Cue:): 네이버 AI 검색 영역 (자동화 대상으로서의 의미)
- 모바일/PC 결과 차이, 탭별 셀렉터 차이

#### 트래픽 (→ api-traffic.md)
- wcs.naver.net/wcslog.js: 네이버 애널리틱스 추적 코드
- 체류 시간, 이탈률, 리퍼러 검증
- 접속 패턴 분석 (IP/UA/간격/쿠키 연속성)

### 4-4. 공통 안티-패턴 (이렇게 하면 차단됨)

```
[절대 하지 말 것]
1. requests로 API 호출하면서 쿠키/헤더 없이 요청
2. User-Agent 없이 또는 "python-requests/2.x" 그대로 요청
3. 동일 IP에서 분당 100건 이상 요청
4. 로그인 세션 없이 글쓰기 API 직접 호출
5. bvsd 없이 로그인 시도 (즉시 캡차 트리거)
6. Referer 없이 에디터 API 호출
7. 동일 내용의 글을 여러 블로그/카페에 반복 게시
8. headless 브라우저에서 navigator.webdriver 패치 안 한 채로 접근
9. 프록시 없이 하나의 IP로 다수 계정 운영
10. 예측 가능한 패턴 (정확히 5초 간격, 항상 같은 시간대 등)
11. TLS 핑거프린트 대응 없이 requests로 봇 감지 민감 API 호출
12. NNB 쿠키 없이 서비스 API 호출 (브라우저 식별 누락)
```

### 전체 구조

기본 절차는 **systematic-debugging 스킬의 6단계 2-Phase 구조를 따른다.**
차이점은 다음과 같다:

| 항목 | systematic-debugging | naver-logic-analyzer |
|------|---------------------|---------------------|
| 분석 렌즈 | 기계적/흐름/엣지 3개 | 네트워크/브라우저/보안/API/자동화 5개 |
| 렌즈 실행 | 항상 3개 전부 | 빠른 경로: 2-3개 우선, 필요 시 5개 |
| 전문 지식 | 범용 디버깅 | 네이버 고유 메커니즘 (4장 참조) |
| Phase 2 | 직접 코드 수정 | 다른 에이전트에게 위임 |
| 코드 수집 | 직접 수집 | code-analyzer 결과를 입력으로 받음 |

```
Phase 1: 진단 (분석만, 코드 변경 없음)
  1단계: 증상 수집 + 초기 질문 프로토콜
  2단계: 차단/변경 1차 분류 → 빠른 경로로 렌즈 분석
  3단계: 하드 게이트 (증거 수렴 + 원인 확정)
      ↓ (게이트 통과)
Phase 2: 계획 (코드 작성 없음, 다른 에이전트가 실행)
  4단계: 해결 전략 수립
  5단계: 구현 계획 작성
  6단계: 리스크 맵 작성 (법적 리스크 포함)
```

### 5-1. 1단계: 증상 수집 + 초기 질문 프로토콜

**입력:** 사용자 또는 다른 에이전트의 문제 보고

**수집 항목:**
```
필수 정보:
1. 서비스: 블로그 / 카페 / 플레이스 / 검색 / 트래픽 / 스마트스토어
2. 자동화 방식: requests / selenium / playwright / curl_cffi / API 직접 / 기타
3. 막히는 단계: 로그인 / 접근 / API 호출 / 데이터 파싱 / 기타
4. 에러 증상:
   - HTTP 상태 코드
   - 에러 메시지 전문
   - 화면 캡처 또는 HTML 응답 일부
   - 콘솔 로그 (있으면)
5. 기존 코드: 파일 경로 또는 코드 스니펫
6. 최근 변경사항:
   - 코드를 변경했는가? (뭘 변경했는가?)
   - 네이버 업데이트 공지가 있었는가?
   - 이전에는 동작했는가? (언제까지?)
7. 재현성: 항상 / 간헐적 / 특정 조건

선택 정보:
8. 실행 환경: 로컬 / 서버 / Docker
9. IP 환경: 가정용 / 데이터센터 / VPN / 프록시
10. 계정 상태: 정상 / 휴면 / 제한
11. 이전 진단 이력: docs/naver-diagnosis/ 확인
```

### 5-2. 2단계: 차단/변경 분류 + 빠른 경로 렌즈 분석

<!-- [피드백 #4 반영] 빠른 경로를 2단계에 통합 -->

**입력:** 1단계의 증상 수집 결과

**분석 절차:**
1. 1단계에서 수집한 증상으로 **차단/변경/복합 1차 분류** 수행 (7장 참조)
2. 분류에 따른 빠른 경로로 우선 렌즈 2-3개 실행 (3-0 참조)
3. 각 렌즈에서 최소 1개 원인 후보 도출
4. 수렴 확인 → 수렴 실패 시 나머지 렌즈 추가 실행
5. 렌즈 수렴 결과 도출 (3-6 참조)

<!-- [피드백 #8 반영] 간헐적 실패 전용 분기 추가 -->

**간헐적 실패 전용 분기:**
재현성이 "간헐적"인 경우, 추가로 다음을 확인한다:
```
간헐적 실패 원인 후보:
- A/B 테스트: 네이버가 서버 사이드에서 기능을 A/B 테스트 중 → 요청마다 다른 응답
- CDN 차이: 지역/시간대별 다른 CDN 노드에서 다른 버전 제공
- 로드밸런서: 백엔드 서버마다 배포 버전이 다름 (롤링 업데이트 중)
- 타이밍: 네트워크 지연, 서버 부하에 따른 타임아웃
- Rate Limit: sliding window에 걸렸다 풀렸다 반복
- 네이버 점검 시간대: 새벽 2~6시 일시적 장애 vs 영구 변경 구분
```

**출력:** 3장의 각 렌즈 출력 형식 + 수렴 결과 (3-6 참조)

### 5-3. 3단계: 하드 게이트

<!-- [피드백 #5 반영] 실행 기반 증거 요건 완화 -->
<!-- [피드백 #9 반영] 렌즈 수렴 조건을 원인 명확도 기반으로 변경 -->

**Phase 2 진입 조건:**

```
하드 게이트 체크리스트:
□ 실행한 렌즈에서 각각 최소 1개 원인 후보를 도출했는가?
□ 원인 명확도에 따른 수렴 조건을 충족했는가?
  - 명확: 1개 렌즈로 확정 (예: 404 → URL 변경)
  - 복합: 2개 이상 렌즈 수렴
  - 불명확: 3개 이상 렌즈 수렴 또는 추가 조사 필요
□ "차단"인지 "변경"인지 명확하게 분류했는가?
□ "내가 놓친 렌즈 관점은 없는가?" 자기 반문을 했는가?
□ 증거 3개를 정의하고 2개 이상 확인했는가?
□ 증거 중 1개 이상이 다음 중 하나인가?
  - 실행 기반 증거 (실제 curl/Playwright 요청으로 확인)
  - 사용자 제공 실행 결과 (사용자가 직접 실행한 결과 로그)
□ "이것이 원인이다"라고 단언할 수 있는가?
```

**permissionMode별 증거 수집 전략:**
```
acceptEdits 모드 (권장):
  → 에이전트가 직접 curl, Playwright로 요청을 보내 증거 수집 가능
  → 실행 기반 증거를 자체적으로 확보

plan 모드 (제한적):
  → 실행 불가능하므로 "사용자 제공 실행 결과"로 대체
  → 사용자에게 "이 명령어를 실행해서 결과를 알려주세요"라고 요청
  → 코드 읽기 + 사용자 제공 결과로 하드 게이트 통과
```

**증거 유형:**

| 유형 | 예시 | 실행 기반? |
|------|------|---------|
| 네트워크 로그 | 실제 HTTP 요청 → 403 응답 확인 | O |
| 코드 읽기 | 소스 코드에서 헤더 누락 확인 | X |
| 대조 실험 | 헤더 추가 후 재요청 → 200 확인 | O |
| API 문서 비교 | 공식 문서와 현재 코드 파라미터 비교 | X |
| 브라우저 테스트 | 수동으로 브라우저에서 동일 작업 수행 | O |
| 사용자 제공 결과 | 사용자가 직접 실행한 로그/스크린샷 | O (대체) |

**출력:**
```
## 하드 게이트 판정

### 분류
- 유형: 차단 / 변경 / 복합

### 렌즈 수렴
- 확정 원인: {원인}
- 수렴 렌즈: {N}/{실행한 렌즈 수}
- 명확도: {명확/복합/불명확}

### 자기 의심
- 놓친 관점: {있음(내용)/없음}
- 대안 가설: {기각 사유와 함께}

### 증거 검증
| # | 예상 증거 | 확인 방법 | 유형 | 결과 |
|---|----------|----------|------|------|
| 1 | {증거1} | {방법} | 실행 기반/코드 읽기/사용자 제공 | 확인됨/기각됨 |

- 증거 충족: {N}/3 (실행 기반 또는 사용자 제공: {N}개)
```

**FAIL 시:**
- 1단계로 복귀하여 추가 정보 수집
- 사용자에게 실행 기반 증거 수집 요청 (실제 요청/응답 로그)
- 복귀 3회 이상 시: 사용자에게 추가 정보 요청 / 다른 접근법 제안

## 7. 차단 vs 변경 분기 로직

<!-- [피드백 #4 반영] 7장과 3장의 모순 제거. 7장은 분류 기준만, 3-0에서 빠른 경로 실행 -->

### 1차 분류 (1단계 증상 수집 직후)

```
[차단 신호] — 네이버가 의도적으로 접근을 막는 경우
- HTTP 403 Forbidden
- nCaptcha 발생
- "비정상적인 접근입니다" 메시지
- IP 차단 메시지
- 계정 잠금 (loginStatus=LOCK)
- 429 Too Many Requests
- "보안을 위해 추가 인증이 필요합니다" 메시지
- 로그인 후 즉시 로그아웃 (세션 강제 종료)
- 접속 차단 페이지로 리다이렉트
- WAF 커스텀 에러 페이지

[변경 신호] — 네이버가 API/구조를 변경한 경우
- HTTP 404 Not Found (엔드포인트 URL 변경)
- 파라미터 에러 (필수 파라미터 추가/삭제)
- 응답 스키마 변경 (필드 이름/구조 변경)
- 새 필드 추가 (기존 필드는 유지)
- HTML 셀렉터 변경 (class명, id 변경)
- JS 번들 URL 변경
- 인증 방식 변경 (쿠키 → Bearer 토큰)
- 에디터 버전 업그레이드

[복합 신호] — 차단 + 변경 동시
- API URL 변경 + 이전 URL에서 403 반환
- 인증 방식 변경 + 이전 방식으로 접근 시 차단
- 봇 감지 강화 + 감지 기준 변경
```

### 분류 후 행동

1차 분류 결과에 따라 **3-0 빠른 경로**로 진행한다.

```
차단 → 보안 → 네트워크 → 자동화 (3개 우선)
변경 → API → 브라우저 → 자동화 (3개 우선)
복합 → 전체 5개 렌즈 실행
```

### 분기별 해결 방향

```
차단:
  1. 차단 원인 특정 (IP? 패턴? 캡차?)
  2. 우회 가능 여부 판단 + 법적 리스크 확인 (4-5)
  3. 우회 전략 수립 (프록시, bvsd 개선, 타이밍 조절)
  4. 근본 대응 (차단 트리거 회피)

변경:
  1. 변경 내용 특정 (URL? 파라미터? 스키마?)
  2. 새 구조 분석 (DevTools, 네트워크 로그)
  3. 코드 업데이트 계획
  4. 향후 변경 대비 (추상화 계층)

복합:
  1. 차단 해제 우선 (접근 자체가 안 되면 변경 분석 불가)
  2. 변경 분석
  3. 양쪽 모두 대응하는 통합 계획
```

## 8. 초기 질문 프로토콜

에이전트가 진단을 시작할 때 **자동으로** 수행하는 정보 수집 절차.

### 자동 수집 (코드가 있는 경우)

code-analyzer 결과가 있으면 우선 사용. 없으면 직접 파일을 읽어서 다음을 파악:

```python
autoDetect = {
  "library": "",       # import 문에서 추출 (requests, selenium, playwright, curl_cffi)
  "targetUrl": "",     # 코드 내 URL 문자열에서 추출
  "headers": {},       # 헤더 설정에서 추출
  "cookies": "",       # 쿠키 관리 방식 (session, jar, manual)
  "errorHandling": "", # try-except/catch 구조
  "timing": "",        # sleep/wait 패턴
  "proxy": "",         # 프록시 설정 여부
  "auth": "",          # 로그인 관련 코드 여부
  "tlsFingerprint": "", # TLS 핑거프린트 대응 여부 (curl_cffi, tls-client 등)
}
```

### 사용자 질문 (자동 수집으로 부족한 경우)

최소한의 질문만 하되, 정확한 진단에 필수적인 것만 묻는다:

```
[필수 질문 — 항상 묻는다]
Q1: 어떤 서비스에서 문제가 발생하나요? (블로그/카페/플레이스/검색/트래픽/스마트스토어)
Q2: 어느 단계에서 막히나요? (로그인/접근/API 호출/데이터 파싱/기타)
Q3: 에러 메시지나 HTTP 상태 코드가 있나요?
Q4: 이전에는 정상 동작했나요? 언제부터 안 되나요?

[선택 질문 — 필요할 때만]
Q5: 실행 환경이 어떻게 되나요? (로컬/서버/Docker)
Q6: IP 환경이 어떻게 되나요? (가정용/데이터센터/VPN/프록시)
Q7: 네이버 계정 상태가 어떤가요? (정상/휴면/제한)
Q8: 항상 실패하나요, 간헐적으로 실패하나요?
```

### 프로토콜 실행 규칙

```
1. 코드가 있으면 → code-analyzer 결과 또는 자동 수집 먼저 → 부족한 것만 질문
2. 코드가 없으면 → 필수 질문 전체 + 코드 제공 요청
3. 이전 진단 이력이 있으면 → 이력 참조하여 "이전과 달라진 점" 중심으로 질문
4. 긴급 상황 (서비스 중단) → 질문 최소화, 빠른 진단 모드
```

## 10. 리스크 맵 (3단계 + 법적)

### [즉시 위험] — 지금 당장 막힐 수 있는 것

```
감지 기준:
- 요청 빈도가 rate limit의 80% 이상
- IP 블랙리스트 근접 (경고 응답 수신)
- 캡차 빈도 증가 (이전 대비 2배 이상)
- 세션 만료 시간 단축 (이전 대비 50% 이하)
- 429 응답 빈도 증가

대응:
- 즉시 요청 빈도 감소
- 프록시 로테이션 활성화
- 대기 시간 증가
- 백업 계정/IP 준비
```

### [중기 위험] — 1-3개월 내 변경 예상

```
감지 기준:
- 네이버 개발자 블로그/공지에서 API 변경 예고
- deprecation 경고 헤더 수신
- 새 API 버전 병행 운영 감지 (v5와 v6 동시 존재)
- 인증 방식 강화 추세 (2차 인증 빈도 증가)
- 봇 감지 알고리즘 업데이트 감지 (새로운 핑거프린트 수집)
- TLS 핑거프린트 검증 강화 징후

대응:
- 새 API 버전 사전 연구
- 인증 강화에 대비한 코드 유연성 확보
- 핑거프린트 우회 코드 최신화 (TLS + JS)
- 대안 방식 사전 테스트
```

### [구조 위험] — 근본적으로 불안정한 설계

```
감지 기준:
- 비공식 API 100% 의존 (공식 API 대안 없음)
- 역공학 기반 토큰 생성 (네이버 JS 코드 역분석)
- 하드코딩된 엔드포인트 URL / 셀렉터
- 단일 IP/계정 의존 (백업 없음)
- 에러 핸들링/로깅/모니터링 없음
- TLS 핑거프린트 대응 없이 requests 사용

개선 방향:
- 엔드포인트 URL을 설정 파일로 분리
- 셀렉터를 추상화 계층으로 관리
- 다중 IP/계정 지원
- 서킷 브레이커 패턴 적용
- 구조화된 로깅 + 알림 시스템
- requests → curl_cffi 전환 검토
```

### [법적 위험] — 4-5장 연계

모든 진단 보고서에 법적 리스크 평가를 포함한다.

## 12-1. 실전 시나리오 가이드

진단 트리로 커버하기 어려운 실전 상황별 대응 가이드.

### 간헐적 실패

```
원인 후보 체크리스트:
□ A/B 테스트 (서버 사이드 기능 테스트 → 요청마다 다른 응답)
□ CDN 차이 (지역/시간대별 다른 CDN 노드)
□ 로드밸런서 (백엔드 서버 롤링 업데이트 중)
□ 타이밍 (네트워크 지연, 서버 부하)
□ Rate Limit sliding window (한도에 근접 → 걸렸다 풀렸다)
□ 네이버 점검 시간대 (새벽 2~6시) 일시적 장애

구분법:
- 동일 요청 10회 반복 → 성공률 계산
- 시간대별 성공률 비교 (낮 vs 새벽)
```

## 13. 스킬 설계 (naver-diagnosis)

### 스킬 개요

| 항목 | 값 |
|------|-----|
| 이름 | naver-diagnosis |
| 위치 | skills/naver-diagnosis/SKILL.md |
| 역할 | 사용자 입력 파악 → 이력 확인 → 에이전트 호출 → 결과 저장 → 위임 연결 |

### auto-detect 트리거 패턴

```
한국어 키워드:
- 네이버, 블로그, 카페, 플레이스, 지도, 스마트스토어
- 로그인, 봇 감지, 캡차, 차단, 403, 429
- 자동 포스팅, 자동 글쓰기, 크롤링, 스크래핑
- 순위 확인, 키워드 검색, 노출
- bvsd, encData, nCaptcha
- 세션 만료, 쿠키, 인증

영어 키워드:
- naver, blog, cafe, place, smartstore
- bot detection, captcha, blocked, banned
- scraping, crawling, automation
- login, session, cookie

구어체:
- "네이버 안 돼", "블로그 막혔어", "카페 글쓰기 에러"
- "플레이스 검색 안 됨", "로그인이 자꾸 풀려"
- "스마트스토어 상품 등록 실패"
```

### smart-pdca와의 관계

```
네이버 자동화 문제는 도메인 특화 진단이 필요하므로 smart-pdca를 우회한다.

일반 작업 흐름:
  auto-detect → smart-pdca(S/M/L 판단) → 크기별 워크플로우

네이버 작업 흐름:
  auto-detect → naver-diagnosis 스킬 (smart-pdca 우회)
    → 스킬 내부에서 자체 크기 판단:
      - 단순 (URL 변경 등): 간이 진단 → 바로 위임
      - 복합 (차단+변경 동시): 전체 진단 → 계획 확인 → 위임

우회 이유:
  - smart-pdca의 S/M/L 기준은 "코드 변경량" 기반이지만,
    네이버 진단의 크기는 "원인 복잡도" 기반이라 판단 기준이 다름
  - 네이버 고유 지식(참조 문서)이 필요하여 범용 R(Research)와 다름
```

### RPDCA 매핑

```
Phase 1 = R(Research) + P(Plan):
  - 스킬이 이력 확인 (R)
  - naver-logic-analyzer 에이전트가 5렌즈 분석 + 해결 계획 수립 (R+P)

Phase 2 = P(Plan) 확정:
  - 사용자에게 해결 계획 확인 요청
  - 방안 A/B 중 선택

위임 실행 = D(Do):
  - executing-plans 스킬: 구현 계획이 Task 목록인 경우
  - debugger 스킬: 기존 코드 버그 수정인 경우

검증 = C(Check) + A(Act):
  - 위임 실행 후 vibecraft의 기존 verification/gap-detector가 자동 실행
  - naver-diagnosis 스킬이 별도로 Check-Act를 구현하지 않음
```

### 스킬 vs 에이전트 책임 분리

```
스킬 = 라우터 (분석 로직 없음)
에이전트 = 분석 엔진 (증상 수집 + 5렌즈 + 하드 게이트 + 계획)

원칙: 스킬은 "어디로 보낼지"만 판단하고, "왜 안 되는지"는 에이전트가 판단한다.
증상 수집(초기 질문)은 에이전트의 1단계에서만 수행한다. 스킬은 수집하지 않는다.
```

### 스킬이 하는 일

```
[1] 라우팅 판단 (증상 수집 아님)
    - 사용자 입력에서 키워드로 서비스 추정 (블로그/카페/플레이스/검색/트래픽/스마트스토어)
    - 네이버 관련 문제인지 아닌지만 판단
    - 긴급도 판단 (서비스 중단 여부)
    ※ 구체적 증상 수집, 차단/변경 분류, 에러 분석은 에이전트가 수행

[2] 이력 확인
    - docs/naver-diagnosis/ 폴더 확인
    - 동일 서비스의 최근 진단 이력이 있으면 로드
    - 이전 이력과 현재 증상 비교

[3] 에이전트 호출
    - naver-logic-analyzer 에이전트를 서비스 정보 + 이력과 함께 호출
    - "docs/naver-knowledge/api-{서비스}.md를 먼저 읽어라" 지시 포함
    - code-analyzer 결과가 있으면 함께 전달

[4] 결과 저장
    - 진단 결과를 docs/naver-diagnosis/{날짜}-{서비스}-{증상}.md로 저장
    - 간이/전체 보고서 형식 자동 선택

[5] 위임 연결
    - 해결 계획의 유형에 따라 적절한 스킬로 위임:
      - executing-plans: Task 목록이 있는 구현 계획
      - debug (systematic-debugging): 기존 코드 버그 수정
    - 위임 시 진단 보고서 + 참조 지식 파일 경로 함께 전달
    - 위임 후 verification/gap-detector는 vibecraft 기본 흐름이 자동 처리
```

### executing-plans / debugger로 위임 연결 방법

```
executing-plans 위임:
  1. 5단계 구현 계획의 Task 목록을 plan.md 형식으로 변환
  2. docs/plans/naver-fix-{날짜}/ 폴더에 plan.md 저장
  3. "plan.md가 준비됐으니 실행해" 형태로 executing-plans 트리거

debugger 위임:
  1. 진단 보고서의 확정 원인 + 대상 파일 경로 전달
  2. "이 원인으로 이 파일을 수정해야 한다" 형태로 debug 트리거
  3. debugger가 참조할 네이버 지식 파일 경로 함께 전달
```
