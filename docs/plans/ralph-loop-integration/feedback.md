# ralph-loop 통합 계획서 피드백

**대상 문서**: `docs/plans/ralph-loop-integration/plan.md`  
**작성일**: 2026-03-18  
**목적**: 구현 전 계획서의 충돌 지점, 보완 필요 사항, 우선 정리해야 할 계약을 문서로 남긴다.

---

## 요약

계획서의 방향 자체는 좋다. 특히 `ralph-loop`를 실제 사용 시나리오로 끌어와서
"수정 → 검증 → 실패 → 재수정"의 반복을 자동화하려는 목표는 분명하다.

다만 현재 문서는 아이디어는 선명하지만, **상태 계약과 진입 규칙이 일부 충돌**한다.
바로 구현에 들어가면 `auto-detect`, `smart-pdca`, `executing-plans`가
서로 다른 규칙을 따를 가능성이 있다.

핵심은 다음 3가지다:

1. `ralph-loop`를 **독립 모드**로 볼지, **실행 플래그**로 볼지 하나로 통일
2. 시나리오 C의 **문서 계약 예외 규칙** 확정
3. `ralph-loop` 완료 후 **기존 리뷰 파이프라인 유지 범위** 결정

---

## 주요 피드백

### 1. 높음 — `ralph-loop`의 위치 정의가 충돌함

계획서 앞부분에서는 `S/M/L 외 별도 모드`처럼 서술하고,
상세 설계에서는 `S/M/L과 직교하는 실행 방식`이라고 정의한다.

이 두 표현은 구현 기준이 다르다.

- 별도 모드로 보면 `auto-detect` 우선순위 표, 모드 판별 규칙, 활성 스킬 맵까지 수정해야 한다
- 실행 플래그로 보면 기존 모드/크기 판단은 유지하고, Do 또는 verification 실패 시점에만 분기하면 된다

현재 문맥상 더 자연스러운 해석은 **"독립 모드가 아니라 실행 플래그"** 쪽이다.

### 권장 수정

- `R-2: smart-pdca에 ralph-loop 경로 추가 (S/M/L 외 별도 모드)` 문구를 수정
- 문서 전체에서 `ralph-loop 모드`와 `ralphLoop: true 플래그`를 혼용하지 않도록 통일
- 기준 문장 예시:

```md
ralph-loop은 독립 모드가 아니라, 기존 모드(새 기능/디버깅 등)와
크기(S/M/L) 위에 얹히는 반복 실행 방식이다.
```

---

### 2. 높음 — 시나리오 C의 직접 진입 경로가 현재 RPDCA 문서 계약과 충돌함

시나리오 C는 `"타입 에러 전부 고쳐줘"` 같은 요청에서 바로 `ralph-loop`로 진입한다.
그런데 현재 `executing-plans`는 M/L 작업에서 아래 문서를 전제로 한다.

- `research.md`
- `plan.md`
- `plan-review.md`

즉 지금 계약대로라면 시나리오 C는 실행 전 검증에서 막힐 가능성이 높다.

### 권장 수정

시나리오 C에 대해 아래 셋 중 하나를 문서에 명시해야 한다.

1. **예외 경로 허용**  
   일괄 수정형 `ralph-loop`는 `research.md`, `plan-review.md` 없이 바로 진입 가능

2. **간소 문서 생성**  
   최소 `plan.md` 1개를 빠르게 만든 뒤 `ralph-loop` 진입

3. **S 예외 취급**  
   문서 계약을 생략하는 별도 단축 경로로 취급

가장 무난한 건 **간소 `plan.md`를 생성하고 진입**하는 방식이다.
완전 무문서 진입보다 추적성과 종료 보고가 좋다.

---

### 3. 중간 — `ralph-loop` 완료 후 리뷰 파이프라인 스킵은 새 기능 시나리오에서 위험함

계획서에는 `ralph-loop 완료 후 기존 리뷰 파이프라인은 스킵`이라고 적혀 있다.
하지만 `ralph-loop`는 실패 항목을 줄이는 데 강하고,
`gap-detector`는 계획 대비 누락을 잡는 데 강하다.

즉 역할이 다르다.

- `ralph-loop`는 "에러 0개"를 만들 수 있음
- `gap-detector`는 "계획한 기능이 빠졌는지" 확인함

특히 시나리오 B(새 기능 구현 후 오류 수정)에서는 리뷰 파이프라인 전체 스킵이
품질 회귀를 만들 수 있다.

### 권장 수정

시나리오별로 분리하는 게 좋다.

- 디버깅 후 `ralph-loop`: `verification` 재실행 중심
- 새 기능 후 `ralph-loop`: 최소 `gap-detector`는 다시 실행
- 대형 작업(L): 기존 리뷰 파이프라인 유지 권장

권장 문장 예시:

```md
ralph-loop는 검증 실패 항목을 해결하는 보조 루프이며,
새 기능/L 작업에서는 기존 리뷰 파이프라인을 대체하지 않는다.
필요 시 verification 이후 gap-detector를 재실행한다.
```

---

### 4. 중간 — `auto-detect` 수정 범위가 아직 추상적임

계획서는 `auto-detect에 ralph-loop 라우팅 추가`라고 적지만,
실제 파일 구조상 중요한 수정 지점은 더 많다.

- 우선순위 표
- 모드 판별 규칙
- Ralph Loop 제안 섹션
- 모드별 활성 스킬 맵
- 신뢰도 기반 행동 흐름

즉 단순히 제안 문구 하나 추가하는 수준으로는 부족하다.

### 권장 수정

Step 1에 아래를 명시하는 것이 좋다.

- 어떤 표를 수정하는지
- 직접 요청 `"ralph-loop으로 해줘"`를 어떤 규칙으로 처리하는지
- 새 기능/디버깅 모드와 충돌 시 무엇을 우선하는지

추천 방향:

- `ralph-loop` 자체를 새로운 우선순위 모드로 넣지 말고
- 기존 모드 판별 후 `실행 방식 제안` 레이어에서 처리

즉 `auto-detect`의 역할은:

1. 기존 모드 판별
2. `ralph-loop` 적합 여부 판단
3. 적합하면 제안
4. 수락 시 `smart-pdca`에 `ralphLoop: true` 전달

---

### 5. 중간 — `lib/team` 무수정 전제는 조금 낙관적임

문서에서는 `lib/team/ 코드 변경 없음`이라고 단정한다.
하지만 Step 5에서 요구하는 건 꽤 구체적이다.

- 실패 항목 구조화
- 그룹핑 전략
- iteration 재측정
- 보고서 출력
- 진전 판정

현재 확인되는 엔진 기능은 다음 정도다.

- `config.ralphLoop` 설정 존재
- `buildIterationReport()` 존재

반면 실패 항목 파서나 그룹핑 전략이 실제로 엔진 레벨에 충분한지는
계획서만으로 확정하기 어렵다.

### 권장 수정

다음처럼 표현을 완화하는 것이 안전하다.

```md
1차 구현은 스킬 레벨에서 우선 처리한다.
다만 실패 항목 파싱/그룹핑이 반복되거나 스킬 문서만으로 유지가 어려우면
2차로 lib/team 확장을 검토한다.
```

즉, 이번 범위에서는 **"무수정 확정"**보다 **"우선 무수정, 필요 시 확장"**이 맞다.

## 보완 권장안

### 우선 수정해야 할 것

1. `ralph-loop`의 개념을 `실행 플래그`로 통일
2. 시나리오 C의 문서 계약 예외 규칙 확정
3. `ralph-loop` 이후 리뷰 파이프라인 유지 범위 확정

### 그다음 정리할 것

4. `auto-detect` 수정 범위를 표/규칙 단위로 구체화
5. `lib/team 무수정` 표현을 조건부로 완화

---

## 제안하는 문서 방향

이 계획서는 아래 원칙으로 다듬으면 훨씬 단단해진다.

- `ralph-loop`는 **새 모드가 아니라 실행 방식**
- 기존 모드(새 기능, 디버깅, 분석)는 그대로 유지
- 기존 RPDCA 흐름 안에서 `verification 실패` 또는 `사용자 직접 요청` 시점에만 진입
- 대형 기능 작업에서는 `ralph-loop`가 리뷰 파이프라인을 대체하지 않음
- 일괄 수정형 시나리오는 예외 계약을 별도로 정의

---

## 최종 평가

현재 계획서는 **방향은 좋고 구현 가치도 높다**.
특히 사용자가 반복적으로 "다시 실행해봐", "또 고쳐줘"를 요청하는 흐름을 줄이는 데
실질적인 도움이 될 가능성이 크다.

다만 지금 상태 그대로 구현하면 다음 문제가 먼저 터질 수 있다.

- `ralph-loop` 진입 조건 해석이 파일마다 달라짐
- 시나리오 C가 실행 전 문서 검증에서 막힘
- 새 기능 완료 후 품질 체크가 약해짐

따라서 구현 전에는 **상태 계약부터 정리하는 보수 작업**이 우선이다.

한 줄 요약:

> 이 계획은 충분히 밀 가치가 있지만, 지금은 "좋은 아이디어" 단계이고,
> 실제 구현 전에 `진입 규칙`, `문서 계약`, `후속 검증 범위`를 먼저 잠가야 한다.
