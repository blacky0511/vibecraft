# 리팩토링 레이더 (Refactoring Radar)

## 역할

코드를 작성/수정하면서 "이 정도면 정리할 때가 됐다"를 자동으로 감지한다.

## 감지 기준

### 코드 스멜 (정리가 필요한 신호)

| 신호 | 기준 | 제안 |
|------|------|------|
| 긴 함수 | 50줄 초과 | 기능별로 분리 |
| 깊은 중첩 | 들여쓰기 4단계 이상 | 조기 반환(early return) 패턴 적용 |
| 중복 코드 | 같은 로직 3곳 이상 반복 | 공통 함수로 추출 |
| 큰 파일 | 300줄 초과 | 모듈 분리 |
| 많은 파라미터 | 함수 인자 5개 이상 | 객체로 묶기 |
| 매직 넘버 | 의미 불명의 숫자/문자열 | 상수로 분리 |
| 폴더 과밀 | 한 폴더에 파일 15개 이상 | 하위 폴더로 정리 |

### 감지 타이밍

- 코드를 작성/수정한 직후
- 파일을 읽을 때 기존 코드에서 발견한 경우

## 안내 방식

**강제하지 않는다.** 작업 완료 후 부드럽게 제안한다.

```
💡 리팩토링 제안 (참고용):

utils/api.ts의 fetchData() 함수가 67줄입니다.
→ 에러 처리 / 데이터 변환 / 호출 로직으로 분리하면
  나중에 수정할 때 편합니다.

지금 정리할까요, 나중에 할까요?
```

### "나중에" 선택 시 — 기술 부채 기록

사용자가 "나중에"를 선택하면 `docs/tech-debt.md`에 자동 기록한다.

**기록 조건:**
- AI 또는 사용자가 "일단", "나중에", "임시로" 라고 말한 경우
- 하드코딩된 값을 넣은 경우
- TODO 주석을 코드에 남긴 경우
- 에러 처리 또는 테스트를 생략한 경우

**기록 형식** (`docs/tech-debt.md`):

| # | 내용 | 파일 | 발생일 | 심각도 | 상태 |
|---|------|------|--------|--------|------|
| 1 | 내용 | 경로 | 날짜 | 상/중/하 | 대기 |

**심각도 기준:**
- 상: 보안 위험 또는 데이터 손실 가능
- 중: 유지보수 어려움 또는 성능 저하
- 하: 코드 품질/가독성 문제

**리마인드:**
- 작업 시작 시 밀린 기술 부채가 있으면 알림
- 관련 파일 수정 시 해당 부채 항목 알림

## 스킵 조건

- 프로토타입/실험 코드 (사용자가 "일단 돌아가게만" 요청한 경우)
- simple-tweak 모드
- 급한 버그 수정 중
