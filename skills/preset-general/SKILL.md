# 일반(범용) 프리셋 (preset-general)

## 역할

Spring Boot, Next.js, Python 등 특정 스택이 감지되지 않을 때 기본으로 활성화된다.
이 스킬은 어떤 프로젝트에도 적용할 수 있는 범용 개발 원칙을 제공한다.

---

## 자동 활성화 조건

아래 상황에서 이 스킬이 활성화된다.

- `preset-spring`, `preset-nextjs`, `preset-python` 중 어느 것도 감지되지 않을 때
- 사용자가 "기타", "일반", "범용" 등의 키워드를 언급할 때
- 프로젝트 구조 파악이 어려운 경우

---

## 1. 가장 중요한 원칙: 기존 코드를 따른다

**새 코드를 작성하기 전에 반드시 기존 코드를 먼저 파악한다.**

아래 순서로 프로젝트의 규칙을 파악한다.

```
[1순위] 프로젝트 루트의 CLAUDE.md
  → 가장 우선시한다. 여기에 명시된 규칙이 모든 것을 override한다.

[2순위] README.md
  → 기술 스택, 빌드 방법, 프로젝트 규칙이 적혀있는 경우가 많다.

[3순위] 기존 코드 스타일
  → 이미 작성된 코드의 들여쓰기, 네이밍, 주석 방식을 그대로 따른다.

[4순위] 이 스킬의 기본 규칙
  → 위 항목에서 정보를 찾지 못했을 때만 아래 규칙을 적용한다.
```

---

## 2. 코딩 스타일 파악 체크리스트

새 파일을 작성하거나 기존 파일을 수정하기 전에 아래를 확인한다.

### 들여쓰기
- 기존 파일에서 스페이스 2칸, 4칸, 탭 중 무엇을 사용하는지 확인한다.
- 기존 코드와 동일한 방식을 사용한다.

### 네이밍 컨벤션
- 기존 변수/함수명이 `camelCase`인지 `snake_case`인지 확인한다.
- 기존 파일명이 `kebab-case`인지 `PascalCase`인지 `snake_case`인지 확인한다.
- 기존 방식을 그대로 따른다.

### 주석 방식
- 기존 코드에 주석이 있으면 같은 언어(한국어/영어)와 같은 형식으로 작성한다.

### 파일 구조
- 기존 디렉토리 구조를 파악하고, 새 파일은 기존 구조에 맞는 위치에 생성한다.

---

## 3. 의존성 추가 규칙

새 라이브러리나 패키지를 추가하기 전에 반드시 사용자에게 확인한다.

확인 시 아래 내용을 함께 설명한다.

- 어떤 라이브러리를 추가할 것인지
- 왜 필요한지 (기존 라이브러리로 해결할 수 없는 이유)
- 어떻게 설치하는지 (터미널 명령어)
- 라이선스 및 유지보수 상태 (간략하게)

```
"이 기능을 위해 {라이브러리명} 라이브러리가 필요합니다.
이유: {이유}
설치 명령어: {명령어}
진행해도 될까요?"
```

## 4. 테스트 프레임워크 규칙

이미 사용 중인 테스트 프레임워크를 따른다.

| 확인 방법 | 예시 |
|---------|------|
| `package.json` | `"jest"`, `"vitest"`, `"mocha"` 등 확인 |
| `requirements.txt` | `pytest`, `unittest` 등 확인 |
| `build.gradle` | `testImplementation 'junit'` 등 확인 |
| 기존 테스트 파일 | `*.test.js`, `test_*.py`, `*Test.java` 등 존재 여부 확인 |

테스트 프레임워크가 없는 경우, 새로 도입하기 전에 사용자에게 제안하고 확인을 받는다.

## 5. 버전 관리 규칙

### 파일 수정 전 확인
- 중요한 파일을 수정하기 전에 현재 상태를 Git에 커밋할 것을 권장한다.
- 되돌릴 수 없는 작업(파일 삭제, 대규모 리팩토링)은 사용자에게 먼저 알린다.

### .gitignore 기본 항목
기술 스택에 맞게 `.gitignore`에 아래 항목이 있는지 확인한다.

```
# 환경변수 파일 (민감 정보)
.env
.env.local
.env.*.local

# 의존성 폴더
node_modules/
venv/
.venv/

# 빌드 결과물
dist/
build/
target/
*.class

# IDE 설정
.idea/
.vscode/
*.iml

# OS 파일
.DS_Store
Thumbs.db
```

## 6. 코드 품질 기본 원칙

기술 스택과 무관하게 항상 지켜야 할 원칙.

### 가독성 우선
- 영리한 코드(clever code)보다 읽기 쉬운 코드를 선택한다.
- 변수명과 함수명은 역할을 명확하게 표현한다. 약어를 남발하지 않는다.
- 한 함수/메서드는 하나의 역할만 담당한다. (단일 책임 원칙)

### 중복 제거
- 같은 코드가 2회 이상 반복되면 함수로 분리하는 것을 고려한다.
- 매직 넘버(의미 없는 숫자)는 이름 있는 상수로 바꾼다.

```python
# 나쁜 예
if status == 3:  # 3이 무엇을 의미하는지 알 수 없다
    ...

# 좋은 예
ORDER_STATUS_SHIPPED = 3
if status == ORDER_STATUS_SHIPPED:
    ...
```

### 에러 처리
- 에러가 발생할 수 있는 부분은 적절한 예외 처리를 추가한다.
- 에러 메시지는 사용자 또는 개발자가 원인을 파악할 수 있도록 구체적으로 작성한다.
- 에러를 조용히 무시하지 않는다. 최소한 로그라도 남긴다.

### 보안 기본 수칙
- 비밀번호, API 키, 토큰은 코드에 직접 넣지 않는다. 환경변수로 관리한다.
- 사용자 입력값은 항상 검증(validation)한다.
- SQL 쿼리는 파라미터 바인딩을 사용한다. 문자열 직접 조합(SQL injection 위험)을 피한다.

## 7. 작업 시작 전 AI의 행동 규칙

기술 스택이 명확하지 않은 프로젝트에서 작업을 시작할 때 AI는 아래 순서로 행동한다.

```
[1단계] 프로젝트 파악
  → CLAUDE.md, README.md, package.json / pyproject.toml / build.gradle 확인
  → 기술 스택, 빌드 방법, 실행 방법 파악

[2단계] 구조 파악
  → 주요 디렉토리와 파일 구조 확인
  → 기존 코드 스타일 파악 (들여쓰기, 네이밍 등)

[3단계] 작업 계획 공유
  → 무엇을 어떻게 할지 사용자에게 먼저 설명한다.
  → 불명확한 부분은 바로 코드를 작성하지 말고 사용자에게 질문한다.

[4단계] 작업 수행
  → 기존 규칙과 스타일을 유지하며 코드를 작성한다.
```
