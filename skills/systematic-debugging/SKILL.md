# 체계적 디버깅

## 역할

에러나 버그가 발생했을 때, 추측 없이 6단계(2-Phase) 절차를 따라 원인을 찾고 수정한다.
**분석이 끝나기 전에 절대 코드를 수정하지 않는다.**

---

## 크기 판단 (스킬 내부에서 즉시)

이 스킬이 호출되면 먼저 버그의 크기를 판단한다:

| 크기 | 기준 | 절차 |
|------|------|------|
| S | 에러 메시지 명확 + 원인 1곳 | 에러 확인 → 바로 수정 → 결과 확인 |
| M | 원인 불확실 + 2~3파일 관련 | 렌즈 1~2로 분석 → 수정 → verification |
| L | 재현 어려움 + 5파일+ 연쇄 | 3렌즈 전체 + 영향 분석 → 수정 계획 → 수정 → verification |

### S 크기: 빠른 수정
1. 에러 메시지/스택트레이스 확인
2. 원인 분석
3. **수정 전 자체 검증** (아래 "수정 전 검증 게이트" 참고)
4. 검증 통과 후 수정
5. 수정 결과 확인 (실행 또는 테스트)

### M/L 크기: 아래의 전체 프로세스 실행

---

## 6단계 디버깅 프로세스 (2-Phase, 렌즈 기반)

```
┌─────────────────────────────────────────┐
│  Phase 1: 분석 (코드 수정 절대 금지)      │
│  — 3가지 렌즈로 같은 버그를 다른 각도에서 본다 │
│                                          │
│  1단계: 기계적 분석 (Mechanical)           │
│  2단계: 흐름 추적 (Flow) [S: 간소화]       │
│  3단계: 엣지 분석 (Edge)                  │
│                                          │
├────── 하드 게이트 (종합 + 증거 확정) ──────│
│  ⛔ 원인 미확정 시 Phase 2 진입 금지       │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  Phase 2: 수정 (확정된 원인에 대해서만)    │
│                                          │
│  4단계: 수정                              │
│  5단계: 검증                              │
│  6단계: 최종 확인                          │
└─────────────────────────────────────────┘
```

---

## Phase 1: 분석 (코드 수정 절대 금지)

> **이 Phase에서는 어떤 이유로든 코드를 수정하면 안 된다.**
> 로그 추가, 임시 코드 삽입도 금지. 오직 읽기와 분석만 수행한다.

### 사용자 추측 처리 규칙

사용자가 원인을 추측으로 제시한 경우 ("~인 것 같은데", "아마 ~일 거야"):
- 그것은 **"확인된 정보"가 아니라 "가설 중 하나"**로 취급한다
- 다른 후보들과 동등하게 나열하며, 하드 게이트에서 증거로 검증될 때까지 채택하지 않는다
- **S 크기라도 사용자가 추측을 제시한 경우, 2단계(흐름 추적)를 간소화하지 않고 전체 수행한다**

---

### 1단계 — 기계적 분석 (Mechanical)

> **렌즈**: 에러 메시지, 스택트레이스, 타입, 문법 — 기계가 알려주는 정보에 집중한다.

**정보 수집:**

사용자에게 아래를 확인한다 (이미 제공된 정보는 스킵):
- 에러 메시지 전문 (전체 텍스트 복사 요청)
- 스택트레이스
- 언제부터 발생했는지 (어떤 작업 후부터인지)
- 재현 조건 (항상? 특정 조건에서만?)

**분석 항목:**

1. **에러 메시지 해독**: 에러 종류, 메시지가 말하는 정확한 의미
2. **스택트레이스 추적**: 에러 발생 파일/줄 번호, 호출 체인
3. **타입/문법 확인**: 타입 불일치, 오타, 잘못된 import, 누락된 인자
4. **컴파일/빌드 에러**: 컴파일 타임에 잡히는 문제 여부
5. **최근 변경 확인**: `git diff`, `git log`로 최근 변경과 에러의 상관관계

**1단계 출력 형식:**

```
## 1단계: 기계적 분석

### 증상 요약
- 에러 종류: {에러 타입}
- 에러 메시지: {전문}
- 발생 위치: {파일:줄번호}
- 재현 조건: {조건}

### 기계적 관점에서 발견한 것
1. {발견 1} — {스택트레이스/타입/문법 근거}
2. {발견 2} — {근거}
3. {발견 3} — {근거}

### 이 렌즈의 원인 후보 (최소 1개)
1. {기계적 분석 기반 후보 1}
2. {후보 2 — 있으면 기술}
```

---

### 2단계 — 흐름 추적 (Flow)

> **렌즈**: 데이터와 실행 흐름 — 입력이 에러 지점까지 어떻게 도달하는지 추적한다.
> **S 크기는 간소화**: 핵심 흐름만 확인. 단, 사용자 추측이 있으면 전체 수행.

**분석 항목:**

1. **입력 → 처리 → 에러 지점**: 데이터가 어떤 경로를 타고 에러 지점에 도달하는지
2. **정상 케이스와 비교**: 같은 코드가 정상적으로 동작하는 경우와의 차이
3. **조건 분기 추적**: 에러 지점까지의 if/else, switch, 삼항 연산자 분기 확인
4. **비동기 흐름**: async/await, 콜백, Promise 체인에서의 순서 문제
5. **상태 변화 추적**: 변수/상태가 어느 시점에 예상과 달라지는지

**2단계 출력 형식:**

```
## 2단계: 흐름 추적

### 데이터 흐름
- 입력: {시작점} → 처리: {경유 함수/파일} → 에러: {에러 지점}

### 흐름에서 발견한 것
1. {발견 1} — {흐름의 어느 지점에서 문제가 발생하는지}
2. {발견 2} — {정상 케이스와의 차이}

### 이 렌즈의 원인 후보 (최소 1개)
1. {흐름 분석 기반 후보 1}
2. {후보 2 — 있으면 기술}

### 1단계 결론 검증
- 1단계 후보와 일치: {예/아니오}
```

---

### 3단계 — 엣지 분석 (Edge)

> **렌즈**: 극단적 상황 — null, 빈값, 동시성, 환경 차이 등 정상 흐름에서는 드러나지 않는 문제를 찾는다.

**분석 항목:**

1. **null/undefined/빈값**: 변수가 null이거나 빈 문자열/빈 배열일 때의 동작
2. **경계값**: 0, 음수, 최대값, 배열 범위 초과
3. **동시성/타이밍**: 경쟁 조건, 비동기 순서 의존, 상태 업데이트 타이밍
4. **환경 차이**: OS(Windows/macOS), 런타임 버전, 의존성 버전 차이
5. **입력 변형**: 특수문자, 유니코드, 예상보다 긴 문자열, 타입이 다른 값

**3단계 출력 형식:**

```
## 3단계: 엣지 분석

### 엣지 케이스에서 발견한 것
1. {발견 1} — {어떤 극단 상황에서 문제가 되는지}
2. {발견 2} — {근거}

### 3개 렌즈 종합
- 1단계(기계적): {핵심 발견}
- 2단계(흐름): {핵심 발견}
- 3단계(엣지): {핵심 발견}

### 이 렌즈의 원인 후보 (최소 1개)
1. {엣지 분석 기반 후보 1}
2. {후보 2 — 있으면 기술}

### 원인 후보 수렴
- 전체 후보 목록: {1단계 후보들 + 2단계 후보들 + 3단계 후보들}
- 수렴된 원인: {3개 렌즈에서 공통으로 가리키는 원인}
- 수렴 못 한 경우: {각 렌즈가 다른 원인을 가리키면 기술}
```

## 하드 게이트: Phase 1 → Phase 2

3개 렌즈의 분석을 종합하고, 자기 의심을 거쳐, 증거로 확정한다.

**Phase 2에 진입하려면 아래 조건을 모두 충족해야 한다:**

- [ ] **렌즈별 후보**: 각 렌즈에서 최소 1개 이상의 원인 후보를 도출했는가? (3개 렌즈 × 최소 1개 = 최소 3개 후보)
- [ ] **수렴**: 3개 렌즈의 후보들이 1개 원인으로 수렴하는가?
- [ ] **자기 의심**: "내가 놓친 관점은 없는가?" 스스로 반문했는가?
- [ ] **증거 확인**: 증거 3개를 정의하고 2개 이상 확인했는가?
- [ ] **실행 기반 증거**: 확인된 증거 중 최소 1개는 실행 기반인가?
- [ ] **단언**: "이것이 원인이다"라고 단언할 수 있는가?

### 실행 기반 증거란?

코드를 **실제로 동작시켜서** 확인하는 것:
- 테스트 실행 (npm test, pytest 등)
- 버그 재현 시도 (앱 실행 후 동일 조건으로 확인)
- 빌드 확인 (컴파일 에러 여부)
- REPL/콘솔에서 해당 로직 실행

아래는 실행 기반이 **아니다** (코드 읽기에 해당):
- 소스 코드 읽기
- git diff / git blame / git log
- 설정 파일 확인

**실행 기반 확인이 불가능한 환경**(테스트 없음, 빌드 불가)에서는 사용자에게 재현 결과를 직접 확인 요청한다.

### 하드 게이트 출력 형식

```
## 하드 게이트 판정

### 렌즈 수렴
- 수렴 여부: {1개로 수렴됨 / 수렴 안 됨}
- 확정 원인: {원인}

### 자기 의심
- 놓친 관점: {있음 — 내용 / 없음}

### 증거 검증
| # | 예상 증거 | 확인 방법 | 유형 | 결과 |
|---|----------|----------|------|------|
| 1 | {증거1} | {방법} | 코드 읽기/실행 기반 | 확인됨/기각됨 |
| 2 | {증거2} | {방법} | 코드 읽기/실행 기반 | 확인됨/기각됨 |
| 3 | {증거3} | {방법} | 코드 읽기/실행 기반 | 확인됨/기각됨 |

- 증거 충족: {N}/3 (실행 기반: {N}개)

### Phase 2 진입 판정
→ ✅ 원인 확정됨 — Phase 2 진입
   또는
→ ⛔ 원인 미확정 — 1단계로 복귀하여 추가 정보 수집
```

**충족하지 못하면:**
- 1단계로 복귀하여 추가 정보를 수집한다
- 사용자에게 추가 정보를 요청한다
- 절대 "일단 고쳐보고 확인하자"로 넘어가지 않는다

### 복귀 루프 탈출 조건

하드 게이트 → 1단계 복귀가 **3회 이상** 반복되면, 무한 루프를 방지하기 위해 전략을 전환한다:

| 복귀 횟수 | 행동 |
|----------|------|
| 1~2회 | 정상 복귀 — 추가 정보 수집 후 재분석 |
| 3회 | 전략 전환 — 사용자에게 아래 선택지를 제시: |

**3회 복귀 시 선택지:**
1. "추가 정보를 제공해주시면 다시 분석하겠습니다" (정보 부족 시)
2. "로그를 삽입하여 런타임 동작을 추적하겠습니다" (재현 가능 시)
3. "다른 접근법(환경 재구성, 의존성 업데이트 등)을 시도하겠습니다" (환경 문제 의심 시)

## Phase 1.5: 수정 계획 + 영향 분석 (M/L만)

> S 크기는 이 단계를 스킵하고 바로 Phase 2로 진입한다.
> M/L 크기는 수정 전에 반드시 이 단계를 거친다.

### mini fix-plan 작성

하드 게이트를 통과한 뒤, 코드를 수정하기 **전에** 수정 계획을 먼저 세운다.

**작성 항목:**
1. 확정된 원인
2. 수정 전략 (한 문장)
3. 수정 항목 목록 (파일:줄번호 + 변경 내용)
4. 회귀 테스트 계획

### 영향 분석 (수정 전 필수)

수정 대상 함수/파일을 **사용하는 모든 곳**을 Grep으로 전수 조사한다.

**확인 항목:**

| 확인 | 방법 | 목적 |
|------|------|------|
| 수정 대상 함수의 호출부 | Grep | 반환값/파라미터 변경 시 깨지는 곳 파악 |
| 수정 대상 파일을 import하는 파일 | Grep | 의존성 체인 파악 |
| 관련 테스트 파일 | Glob | 기존 테스트가 깨질지 예측 |
| 공유 상태 (전역 변수, DB, 캐시) | 코드 읽기 | 수정이 다른 흐름의 상태를 오염시키는지 |

### 충돌 위험 판단

| 위험도 | 조건 | 행동 |
|--------|------|------|
| 🟢 안전 | 수정이 인터페이스(입출력)를 바꾸지 않음 | 그대로 진행 |
| 🟡 주의 | 인터페이스가 바뀌지만 사용처가 적음 | 사용처도 함께 수정 항목에 추가 |
| 🔴 위험 | 인터페이스가 바뀌고 사용처가 많음 | **사용자에게 알리고 확인 후 진행** |

### 🔴 위험 시 사용자 알림

```
수정이 기존 기능에 영향을 줄 수 있습니다.

🔴 위험: {수정 대상}의 {변경 내용}
- 영향: {사용처 목록}
- 함께 수정 필요: {파일 목록}

이대로 진행할까요? 아니면 수정 범위를 좁힐까요?
```

### mini fix-plan 출력 형식

```markdown
## 수정 계획

**확정 원인**: {하드 게이트에서 확정된 원인}
**수정 전략**: {한 문장}

### 수정 항목
1. `{파일:줄번호}` — {변경 내용}
2. `{파일:줄번호}` — {변경 내용}
3. `{테스트 파일}` — 회귀 테스트 추가

### 영향 분석
| 수정 대상 | 사용처 | 영향 예상 | 위험도 | 대응 |
|----------|--------|---------|--------|------|
| {함수명} | {파일:줄} | {영향} | 🟢/🟡/🔴 | {대응} |

### 충돌 위험: 🟢 안전 / 🟡 주의 / 🔴 위험
```

## Phase 2: 수정 (확정된 원인에 대해서만)

### ⛔ 수정 전 검증 게이트 (모든 크기 공통)

> **원인을 찾았다고 바로 수정하지 않는다.**
> 수정 전에 반드시 아래 검증 중 **최소 1개**를 수행하여 근거를 확보한다.

**검증 방법 (상황에 맞는 것을 선택):**

| 방법 | 언제 사용 | 예시 |
|------|----------|------|
| **Bash로 테스트 실행** | 테스트가 있을 때 | `npm test`, `pytest` 등으로 현재 실패를 확인 |
| **Bash로 에러 재현** | 실행 가능한 코드 | `node script.js`, `curl` 등으로 에러를 직접 재현 |
| **Playwright MCP로 검증** | 웹 UI 관련 버그 | 브라우저에서 실제 동작을 확인하여 증상 재현 |
| **코드 역추적 확인** | 로직 버그 | Grep/Read로 원인 함수의 호출처를 전부 확인하여 영향 범위 파악 |
| **관련 코드 교차 확인** | 수정 확신이 높을 때 | 수정 대상 파일 + 연관 파일을 다시 Read하여 수정이 맞는지 재확인 |

**검증 결과를 명시한 후에만 수정을 시작한다:**

```
검증: npm test 실행 → 3개 실패 확인 (auth.test.ts:15, 23, 41)
실패 원인이 분석한 {원인}과 일치함을 확인.
수정을 진행합니다.
```

```
검증: Playwright로 로그인 페이지 접속 → 버튼 클릭 → 404 응답 확인.
분석한 라우팅 설정 누락이 원인임을 재현으로 확인.
수정을 진행합니다.
```

```
검증: fetchUser 함수의 호출처 3곳(UserList.tsx:12, Profile.tsx:8, Admin.tsx:25)을
Read로 확인. 수정 시 UserList.tsx만 영향받음을 확인.
수정을 진행합니다.
```

**검증 없이 "아마 이게 원인일 것이다"로 수정하는 것은 금지.**

### 4단계 — 수정

> **목표**: 확정된 원인에 대해 최소한의 코드 변경을 수행한다.
> **M/L**: mini fix-plan의 수정 항목을 순서대로 실행한다.

수정 원칙:
1. **최소한의 수정**: 문제 해결에 필요한 것만 바꾼다. 관련 없는 코드는 건드리지 않는다.
2. **한 번에 하나만 변경**: 여러 가지를 동시에 바꾸면 어느 것이 해결했는지 알 수 없다.
3. **수정 전 코드 상태 재확인**: 수정 대상 파일을 다시 읽어서 현재 상태를 확인한 후 수정한다.
4. **영향 분석 대응 반영** (M/L): 🟡 주의 항목의 사용처도 함께 수정한다.

**4단계 출력 형식:**

```
## 4단계: 수정

### 수정 대상
- 파일: {파일:줄번호}
- 확정된 원인: {하드 게이트에서 확정된 원인}

### 변경 내용
- 변경 전: {코드}
- 변경 후: {코드}
- 수정 이유: {왜 이렇게 바꾸는지}

### 영향 분석 대응 (M/L)
- 🟡 {사용처 파일}: {함께 수정한 내용}
```

---

### 5단계 — 검증

> **목표**: 수정이 원래 버그를 실제로 해결했는지 확인한다.

확인 방법 (하나 이상 수행):
1. **테스트 실행**: 관련 테스트가 있으면 실행하여 통과 확인
2. **수동 재현**: 1단계에서 파악한 재현 조건으로 버그가 사라졌는지 확인
3. **빌드 확인**: 프로젝트가 정상적으로 빌드되는지 확인

**5단계 출력 형식:**

```
## 5단계: 검증

### 원래 버그 해결 확인
- 검증 방법: {테스트 실행 / 수동 재현 / 빌드 확인}
- 결과: ✅ 해결됨 / ❌ 미해결

### 미해결 시 복귀 판단 기준
→ 에러 메시지가 수정 전과 **동일** → 1단계로 복귀 (원인 자체가 잘못 확정됨, Phase 1 재시작)
→ 에러 메시지가 수정 전과 **다름** → 4단계로 복귀 (원인은 맞았으나 수정 방향이 잘못됨)
```

---

### 6단계 — 최종 확인

> **목표**: 수정이 다른 곳을 망가뜨리지 않았는지 확인하고, 디버깅 잔해를 정리한다.

1. **영향 분석 대조** (M/L): Phase 1.5에서 파악한 사용처/영향 범위를 다시 확인한다. 영향 분석에서 🟡/🔴로 표시했던 곳이 실제로 깨지지 않았는지 검증한다.
2. **부작용 확인**: 수정한 함수/파일을 사용하는 다른 코드에 영향이 없는지 확인
3. **동일 패턴 확인**: 같은 버그가 다른 곳에도 있는지 프로젝트 전체에서 검색
4. **디버깅 잔해 정리**: `code-simplifier` 에이전트를 호출하여 임시 로그, 주석 처리된 코드 등 정리
5. **최종 검증**: `vibecraft:verification` 스킬을 호출하여 최종 게이트 통과

**6단계 출력 형식:**

```
## 6단계: 최종 확인

### 영향 분석 대조 (M/L)
| 수정 대상 | 사용처 | 영향 분석 예측 | 실제 결과 |
|----------|--------|-------------|----------|
| {함수명} | {파일:줄} | 🟢 안전 | ✅ 이상 없음 |
| {함수명} | {파일:줄} | 🟡 주의 | ✅ 함께 수정 완료 |

### 부작용 점검
- 영향받는 파일: {목록 또는 "없음"}
- 부작용 발견: {있음/없음}

### 동일 패턴
- 동일 패턴 발견: {파일 목록 또는 "없음"}
- 추가 수정 필요: {예/아니오}

### 정리
- code-simplifier 실행: {완료/스킵}
- verification 통과: ✅ / ❌

### 최종 결론
→ ✅ 디버깅 완료 / ❌ 추가 작업 필요
```

## 6단계 이후: ralph-loop 자동 전환

verification 결과 아래 조건에 해당하면 ralph-loop 전환을 제안한다:

| 조건 | 행동 |
|------|------|
| 테스트 실패 0개 | 완료 (ralph-loop 불필요) |
| 테스트 실패 1개 | 직접 수정 후 재검증 (ralph-loop 불필요) |
| 테스트 실패 2개 이상 | ralph-loop 제안: "관련 테스트 N개가 실패합니다. ralph-loop으로 자동 수정할까요?" |
| 수정이 다른 테스트를 깨뜨림 | ralph-loop 강력 제안: "수정이 기존 테스트 N개를 깨뜨렸습니다. ralph-loop이 효율적입니다." |

**ralph-loop 전환 시:**
- 검증 명령어: 해당 테스트 스위트 명령어 (예: `npm test`, `pytest tests/`)
- 성공 조건: 실패 0개
- executing-plans에 `ralphLoop: true` 전달 → team-orchestration ralph-loop 모드

## 서브에이전트 위임 규칙

디버깅 작업 크기에 따라 실행 방식이 달라진다.

| 크기 | 실행 방식 | 단계 |
|------|----------|------|
| S | 메인에서 직접 실행 | 1→2(간소화)→3→게이트→4→5 |
| M | **debugger 에이전트 1개를 백그라운드로 실행** | 1→2→3→게이트→4→5→6 전체 |
| L | **debugger 에이전트 1개를 백그라운드로 실행** | 1→2→3→게이트→4→5→6 + 오류 시뮬레이션 |

**예외**: S 크기라도 사용자가 추측을 제시한 경우 2단계를 간소화하지 않고 전체 수행한다.

### 왜 1개의 서브에이전트인가?

6단계는 **순차적**이다. 이전 단계의 결과가 다음 단계의 입력이 된다.
여러 서브에이전트로 나누면 이전 단계의 분석 맥락이 사라진다.
따라서 **1개의 debugger 에이전트**가 백그라운드에서 6단계를 모두 수행한다.

### 서브에이전트 실행 절차

1. 에러 정보(메시지, 스택트레이스, 관련 파일)를 수집한다
2. debugger 에이전트를 **백그라운드**로 실행하며, 6단계 전체 수행을 지시한다
3. 에이전트가 완료되면 결과(디버깅 보고서)를 받아 사용자에게 요약 전달한다

---

## 핵심 규칙

1. **Phase 1에서 코드를 수정하지 않는다.** 분석만 한다.
2. **하드 게이트를 건너뛰지 않는다.** 원인이 확정되지 않으면 수정에 들어가지 않는다.
3. 추측으로 수정하지 않는다. **"아마 이거일 거야"는 금지.** 증거로 확인한다.
4. **사용자의 추측도 가설이다.** 사용자가 원인을 제시해도 증거로 검증될 때까지 채택하지 않는다.
5. 한 번에 하나만 변경한다. 여러 개를 동시에 바꾸면 무엇이 고쳐졌는지 알 수 없다.
6. 수정 후 `code-simplifier`로 디버깅 잔해를 정리한다.
7. 정리 후 반드시 `vibecraft:verification` 스킬로 검증한다.
8. CLAUDE.md AI 행동 규칙을 따른다: 테스트 먼저, 증거 필수, 수정 전 코드 재확인.
9. **사용자가 재분석을 요청하면** ("다시 분석해봐", "재분석해", "제대로 분석해") **이전 분석 결론을 의심한다는 전제 하에 Phase 1(1단계)부터 재시작한다.** 이전 결과를 참고하되, 이전 결론을 그대로 재사용하지 않는다.

| 항목 | 5단계 (검증) | 오류 시뮬레이션 (verification 내부) |
|------|-------------|----------------------------------|

| 적용 | S/M/L 모두 | L만 (디버깅), M/L (새 기능) |

## RPDCA 디버깅 연동

디버깅에서도 작업 크기에 따라 RPDCA 흐름을 적용한다.
디버깅의 R(Research)은 "코드베이스 파악"이 아니라 **"버그 원인 추적"**이다.

### RPDCA 매핑

| RPDCA | 디버깅에서의 의미 | 6단계 매핑 |
|-------|----------------|-----------|
| R (Research) | 에러 로그 수집 + 관련 코드 추적 + 재현 확인 | Phase 1 (1~3단계 + 하드 게이트) |
| P (Plan) | mini fix-plan + 영향 분석 (M/L) | Phase 1.5 |
| D (Do) | 최소한의 수정 실행 | 4단계 수정 |
| C (Check) | 버그 재현 테스트 + 영향 분석 대조 + 사이드 이펙트 확인 | 5~6단계 검증 + 최종 확인 |
| A (Act) | 재발 방지 (회귀 테스트 추가) | 6단계 이후 |

### 크기별 적용

| 크기 | 디버깅 워크플로우 |
|------|----------------|
| S | 1→2(간소화)→3→게이트→4→5 (Phase 1.5 스킵) |
| M | research → 1→2→3→게이트→**Phase 1.5(fix-plan+영향분석)**→4→5→6(영향 대조) → **실패 시 ralph-loop 제안** |
| L | research → 1→2→3→게이트→**Phase 1.5(fix-plan+영향분석)**→4→5→6(영향 대조) + 오류 시뮬레이션 → **실패 시 ralph-loop 제안** |

### S 크기
원인이 명확한 단순 버그. 2단계(흐름 추적)를 간소화하되 스킵하지는 않는다.
Phase 1.5(mini fix-plan)는 스킵한다.
**예외**: 사용자가 원인을 추측으로 제시한 경우 2단계를 전체 수행한다.

### M 크기
원인이 불명확하거나 여러 파일에 걸친 버그.
1. research 스킬 호출 → `docs/plans/{feature}/research.md` 생성 (디버그 관점)
2. Phase 1 전체 수행 (debugger 에이전트, opus)
3. Phase 1.5: mini fix-plan + 영향 분석 (수정 대상 사용처 전수 조사)
4. Phase 2: 수정 → 검증 → 최종 확인 (영향 분석 대조 포함)
5. verification

### L 크기
시스템적 버그, 데이터 정합성 문제 등 광범위한 영향.
1. research 스킬 호출 → research.md (영향 범위 포함)
2. Phase 1 전체 수행 (debugger 에이전트, opus)
3. Phase 1.5: mini fix-plan + 영향 분석 (🔴 위험 시 사용자 확인)
4. Phase 2: 수정 → 검증 → 최종 확인 (영향 분석 대조 포함)
5. verification (오류 시뮬레이션 포함) + 회귀 테스트 추가
