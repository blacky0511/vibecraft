# 코드 리뷰 요청

## 역할

코드를 리뷰 받아야 할 때, 리뷰어가 맥락 없이도 빠르게 이해할 수 있도록
변경 사항 요약, 주의점, 리뷰 포인트를 구조화하여 정리한다.
정리가 완료되면 `code-reviewer` 에이전트를 호출하여 실제 리뷰를 수행한다.

---

## 리뷰 요청 전 준비 단계

아래 항목을 사용자에게 확인한다. 이미 파악할 수 있는 항목은 생략하고 진행한다.

- 어떤 기능/버그를 작업한 건가요?
- 어떤 파일이 변경되었나요?
- 특별히 봐줬으면 하는 부분이 있나요?
- 우려되는 점이나 불확실한 부분이 있나요?

---

## 리뷰 요청서 작성 형식

정보 수집이 완료되면 아래 형식으로 리뷰 요청서를 작성한다.

```
## 코드 리뷰 요청서

### 작업 개요
- 작업 목적: (무엇을 위한 작업인지)
- 작업 범위: (어떤 기능/모듈/파일을 변경했는지)
- 관련 이슈: (있을 경우 이슈 번호 또는 링크)

### 변경 사항 요약
| 파일 | 변경 내용 | 변경 이유 |
|------|----------|----------|
| 파일명 | 무엇을 바꿨는지 | 왜 바꿨는지 |

### 주요 변경 포인트
1. (핵심 로직 변경 설명)
2. (구조/패턴 변경이 있으면 그 이유 포함)
3. (기존 동작과 달라진 부분)

### 리뷰 요청 포인트
> 리뷰어가 특히 집중해서 봐줬으면 하는 부분

- [ ] (항목 1: 예 — 이 로직이 엣지 케이스를 다 처리하는지)
- [ ] (항목 2: 예 — 성능상 문제가 없는지)
- [ ] (항목 3: 예 — 네이밍이 직관적인지)

### 우려 사항 / 불확실한 부분
- (본인이 확신하지 못하는 부분, 대안을 고민했다면 그 내용도 포함)

### 테스트 여부
- [ ] 로컬 테스트 완료
- [ ] 자동화 테스트 작성/수정
- [ ] 직접 실행하여 동작 확인
```

---

## code-reviewer 에이전트 호출

리뷰 요청서 작성 후, `code-reviewer` 에이전트를 호출하여 실제 코드 리뷰를 수행한다.

에이전트 호출 시 다음 컨텍스트를 함께 전달한다:
- 작성된 리뷰 요청서 전문
- 변경된 파일 목록과 diff
- 프로젝트의 기술 스택 및 코딩 규칙

---

## 좋은 리뷰 요청의 원칙

- **맥락 제공**: 리뷰어가 "왜 이렇게 바꿨지?"를 묻지 않도록 충분한 배경을 제공한다.
- **범위 한정**: 한 번에 너무 많은 변경을 리뷰 요청하지 않는다. 500줄 이상이면 분리를 고려한다.
- **질문 명확화**: "이 부분이 맞는지 모르겠어요"처럼 불확실한 부분을 명시적으로 표시한다.
- **방어적 태도 금지**: 리뷰 요청서에 "이렇게 하는 게 맞다고 생각합니다"처럼 방어적 표현을 사용하지 않는다.

---

## 리뷰 요청 후 다음 단계

리뷰 요청서 제출 후에는 `code-review-receive` 스킬을 사용하여 피드백을 처리한다.

```
리뷰 피드백을 받으셨나요?
→ /vibecraft:code-review-receive 스킬로 피드백을 처리할 수 있습니다.
```
