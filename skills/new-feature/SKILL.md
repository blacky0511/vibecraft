# 새 기능 추가 (new-feature)

## 역할

사용자가 새로운 기능을 요청했을 때 호출되는 오케스트레이션 스킬.
작업 크기를 판단하고, 크기에 따라 다른 강도의 워크플로우를 실행한다.

---

## 전체 흐름 개요

```
auto-detect → new-feature (현재 스킬)
                  │
                  ▼
             smart-pdca (작업 크기 판단)
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
       S          M          L
  (소규모)   (중간규모)   (대규모)
```

---

## S (소규모) 워크플로우

**조건**: 파일 1~2개 수정 예상, 단순 기능 추가

**사용자 확인 횟수**: 0회 (확인 없이 바로 진행)

**흐름**:

```
1. 요청 파악
   └── 수정할 파일과 변경 내용을 파악한다

2. 구현 (iron-law 적용)
   ├── S이므로 TDD는 선택 적용
   └── 메인 에이전트가 직접 코드 작성

3. verification (검증 게이트)
   ├── 동작 확인
   └── 최소 증거 1개 제시

4. 완료 보고
   └── 변경된 파일과 내용을 간략히 안내
```

**S 해당 예시**:
- "버튼 하나 추가해줘"
- "메뉴에 항목 넣어줘"
- "환경변수 하나 추가해줘"

---

## M (중간규모) 워크플로우

**조건**: 파일 3~5개 수정 예상, 기존 기능 확장 또는 새 중간 기능 추가

**사용자 확인 횟수**: 1회 (간략 계획 확인 후 실행)

**흐름**:

```
1. brainstorming (간략)
   ├── 요구사항이 불명확하면 핵심 질문 1~2개만 확인
   └── 명확하면 스킵하고 바로 계획으로 이동

2. 간략 계획 작성 → [사용자 확인 1회]
   ├── 수정 파일 목록 (3~5개)
   ├── 각 파일별 변경 내용 요약
   └── "이대로 진행할까요?" 확인 후 실행

3. 구현 (iron-law 적용)
   ├── TDD 필수 — 테스트 먼저 작성
   └── 서브에이전트 1~2개 병렬 실행 (executing-plans 스킬 호출)

4. verification (검증 게이트)
   ├── 테스트 통과 확인
   ├── 동작 확인
   └── 달성률 90% 이상 확인

5. 완료 보고
   └── 구현된 기능 목록과 테스트 결과 안내
```

**M 해당 예시**:
- "댓글 기능 추가해줘"
- "필터 기능 만들어줘"
- "알림 기능 넣어줘"
- "페이지네이션 추가해줘"

**M 간략 계획 예시**:

```
계획 확인:
1. CommentList.tsx — 댓글 목록 컴포넌트 추가
2. CommentForm.tsx — 댓글 작성 폼 컴포넌트 추가
3. comment.service.ts — 댓글 CRUD API 연동
4. post.page.tsx — 기존 게시글 페이지에 댓글 섹션 통합

이대로 진행할까요?
```

---

## L (대규모) 워크플로우

**조건**: 파일 6개 이상 수정 예상, 새 기능 전체 구현 또는 대규모 작업

**사용자 확인 횟수**: 2회 (계획서 확인 1회 + 설계서 확인 1회)

**흐름**:

```
1. brainstorming (상세)
   ├── 요구사항 구체화 질문 (3~5개)
   ├── 기술 스택, 제약 조건, 우선순위 확인
   └── 확정된 요구사항 정리 후 다음 단계로

2. writing-plans (계획서 작성) → [사용자 확인 1회]
   ├── templates/plan.md 양식으로 계획서 작성
   ├── 구현 범위, 파일 목록, 단계별 순서 포함
   └── 계획서 확인 후 설계 단계로 이동

3. 상세 설계 → [사용자 확인 2회]
   ├── templates/design.md 양식으로 설계서 작성
   ├── 컴포넌트 구조, API 설계, DB 스키마 등 포함
   └── 설계서 확인 후 구현 단계로 이동 (이후 자동 진행)

4. team-orchestration (CTO 팀 구성)
   ├── 기능 특성에 맞는 역할별 서브에이전트 배정
   ├── 예: frontend-agent, backend-agent, test-writer-agent
   └── 각 에이전트의 담당 파일과 책임 명확히 분리

5. 구현 (iron-law 적용)
   ├── TDD 필수 — 각 에이전트가 테스트 먼저 작성
   └── 서브에이전트 다수 병렬 실행 (executing-plans 스킬 호출)

6. review-pipeline (3단계 리뷰)
   ├── 1단계: code-simplifier — 불필요한 복잡성 제거
   ├── 2단계: external-reviewer — 코드 품질 및 패턴 검토
   └── 3단계: gap-detector — 계획 대비 누락 항목 확인

7. verification (검증 게이트)
   ├── 전체 테스트 통과 확인
   ├── 리뷰 파이프라인 통과 확인
   └── 달성률 90% 이상 확인

8. 완료 보고
   └── 구현된 기능 전체 목록, 테스트 결과, 리뷰 결과 안내
```

**L 해당 예시**:
- "소셜 로그인 기능 만들어줘"
- "결제 기능 추가해줘"
- "실시간 채팅 넣어줘"
- "관리자 대시보드 만들어줘"

---

## 사용자 확인 시점 요약

| 크기 | 확인 횟수 | 확인 시점 | 이후 동작 |
|------|----------|----------|----------|
| S | 0회 | 없음 | 바로 구현 → 완료 보고 |
| M | 1회 | 간략 계획 작성 후 | 확인 즉시 구현 → 완료 보고 |
| L | 2회 | 계획서 확인 + 설계서 확인 | 확인 후 자동 진행 → 완료 보고 |

---

## 연동 스킬 목록

| 스킬 | 호출 조건 | 역할 |
|------|----------|------|
| `smart-pdca` | 항상 (크기 판단) | S/M/L 분류 |
| `iron-law` | 구현 단계 항상 | TDD + 증거 원칙 강제 |
| `brainstorming` | M(간략), L(상세) | 요구사항 구체화 |
| `writing-plans` | L만 | 계획서/설계서 문서화 |
| `executing-plans` | M, L | 서브에이전트 병렬 실행 |
| `team-orchestration` | L만 | CTO 팀 구성 및 역할 배정 |
| `review-pipeline` | L만 | 3단계 코드 리뷰 |
| `verification` | S, M, L 항상 | 최종 검증 게이트 |

## 스킬 호출 흐름 다이어그램

```
auto-detect
    │ (새 기능 모드 감지)
    ▼
new-feature (현재 스킬)
    │
    ▼
smart-pdca
    │
    ├── S ──────────────────────────────────→ 직접 구현
    │                                              │
    │                                         iron-law
    │                                              │
    │                                        verification
    │                                              │
    │                                         완료 보고
    │
    ├── M ──────── brainstorming(간략) ──→ 간략 계획
    │                                         [확인 1회]
    │                                              │
    │                                    executing-plans
    │                                    (서브에이전트 1~2개)
    │                                         iron-law
    │                                              │
    │                                        verification
    │                                              │
    │                                         완료 보고
    │
    └── L ──────── brainstorming(상세) ──→ writing-plans
                                            [확인 1회]
                                         상세 설계서 작성
                                            [확인 2회]
                                        team-orchestration
                                        executing-plans
                                        (서브에이전트 다수)
                                          iron-law
                                        review-pipeline
                                        (3단계 리뷰)
                                        verification
                                              │
                                         완료 보고
```

---

## 중요 규칙

- **이 스킬은 오케스트레이터 역할**이다. 직접 코드를 작성하지 않고, 다른 스킬을 순서대로 호출하여 전체 흐름을 제어한다.
- **iron-law는 항상 적용**된다. 크기와 무관하게 구현 단계에서 반드시 iron-law 원칙을 따른다.
- **사용자 확인 횟수를 초과하지 않는다.** L이더라도 계획서/설계서 확인 2회 이후에는 사용자 승인 없이 자동으로 진행한다.
- **완료는 verification 통과 후에만 선언한다.** 달성률 90% 미만이면 완료를 선언하지 않고 수정 후 재검증한다.
