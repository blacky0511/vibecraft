# 오류 시뮬레이션

## 핵심 요약

1. **코드 수정 직후** 자동으로 잠재 오류를 분석한다
2. **최대 3회** 반복 — 발견된 문제를 수정하고 다시 분석
3. **S 작업은 스킵** — 단순 수정에 시뮬레이션은 낭비
4. **발견 → 수정 → 재분석** 사이클로 코드 완성도를 높인다
5. 시뮬레이션 통과 후 verification 단계로 넘어간다

---

## 왜 필요한가

AI가 코드를 수정하면 "동작하는 코드"는 만들지만, 아래 문제를 놓치는 경우가 많다:

- 엣지 케이스 (빈 값, null, 배열 범위 초과 등)
- 기존 코드와의 호환성 문제
- 타입 불일치, 인터페이스 위반
- 비동기 처리 누락 (await 빠짐, 콜백 에러 처리 등)
- 환경 차이 (OS, 브라우저, Node 버전)

코드를 작성한 직후에 "이 코드에서 어떤 오류가 발생할 수 있는가?"를 스스로 물어보면 대부분 잡을 수 있다.

---

## 적용 기준 (smart-pdca 연동)

| 작업 크기 | 시뮬레이션 | 이유 |
|----------|-----------|------|
| S (소) | **스킵** | 파일 1~2개, 단순 수정은 오히려 시간 낭비 |
| M (중) | **1~2회** | 여러 파일 수정 시 파일 간 연결 오류 가능 |
| L (대) | **최대 3회** | 복잡한 구현은 엣지 케이스가 많음 |

**M에서 1회로 끝나는 경우**: 1회차에서 문제가 발견되지 않으면 바로 통과.
**L에서 3회 미만으로 끝나는 경우**: 연속 시뮬레이션에서 새로운 문제가 발견되지 않으면 조기 통과.

## 시뮬레이션 절차

### 1회차: 기본 오류 분석

수정된 코드를 대상으로 아래 관점에서 분석한다:

**분석 체크리스트:**

```
[ ] 입력값 엣지 케이스
    - null, undefined, 빈 문자열, 빈 배열, 0, 음수
    - 예상보다 긴 문자열, 특수문자 포함
    - 타입이 다른 값이 들어올 가능성

[ ] 에러 처리
    - try-catch가 필요한데 빠진 곳
    - async/await에서 에러 전파 누락
    - API 호출 실패 시 처리
    - 파일/DB 접근 실패 시 처리

[ ] 기존 코드 호환성
    - 수정한 함수를 호출하는 다른 코드에 영향
    - 인터페이스/타입 변경 시 의존 코드 확인
    - import/export 경로 변경 확인

[ ] 동시성/순서 문제
    - 비동기 호출 순서 의존성
    - 상태 변경 타이밍 이슈
    - 경쟁 조건(race condition) 가능성

[ ] 환경/설정 문제
    - 환경변수 누락
    - OS별 경로 차이 (Windows/macOS)
    - 버전 호환성 (Node, Java, Python 등)
```

**1회차 결과 형식:**

```
## 오류 시뮬레이션 1회차

### 발견된 문제
1. ❌ [파일명:라인] — 문제 설명
   → 수정 방안: ...
2. ❌ [파일명:라인] — 문제 설명
   → 수정 방안: ...

### 문제 없음 항목
- ✓ 입력값 엣지 케이스: 이상 없음
- ✓ 에러 처리: 적절함

### 조치
→ 발견된 N개 문제를 수정합니다.
```

---

### 2회차: 수정 코드 재분석

1회차에서 발견한 문제를 수정한 후, **수정한 코드 자체**를 다시 분석한다.

**2회차에서 추가로 보는 것:**

```
[ ] 1회차 수정이 새로운 문제를 만들지 않았는가?
[ ] 수정 과정에서 다른 코드에 부작용(side effect)이 생기지 않았는가?
[ ] 수정이 원래 요구사항을 여전히 충족하는가?
```

---

### 3회차: 최종 안정성 확인 (L 작업만)

2회차까지 수정된 코드의 전체 안정성을 확인한다.

**3회차에서 보는 것:**

```
[ ] 전체 흐름에서 데이터가 올바르게 전달되는가? (입력 → 처리 → 출력)
[ ] 성능 문제가 될 수 있는 부분이 있는가? (무한 루프, N+1 쿼리 등)
[ ] 보안 취약점이 없는가? (인젝션, XSS, 인증 우회 등)
```

---

## 조기 통과 조건

시뮬레이션을 끝까지 돌릴 필요 없는 경우:

1. **1회차에서 문제 0개** → 바로 통과, 2회차 스킵
2. **2회차에서 새로운 문제 0개** → 바로 통과, 3회차 스킵
3. **발견된 문제가 모두 경미** (코드 동작에 영향 없는 스타일 이슈) → 수정 후 바로 통과

## 시뮬레이션 완료 보고 형식

```
## 오류 시뮬레이션 완료

- 시뮬레이션 횟수: 2회 (조기 통과)
- 1회차 발견: 2개 → 수정 완료
- 2회차 발견: 0개 → 통과

### 수정 내역
1. auth.service.ts:45 — null 체크 추가 (토큰 없을 때 크래시 방지)
2. LoginForm.tsx:23 — 에러 상태 초기화 누락 수정

→ verification 단계로 진행합니다.
```

## smart-pdca 워크플로우에서의 위치

```
Do (실행)
    │
    ▼
error-simulation (현재 스킬)    ← 여기에 끼어들어감
    │
    ├── S → 스킵 → verification으로 바로 이동
    │
    ├── M → 1~2회 시뮬레이션 → 수정 → verification
    │
    └── L → 최대 3회 시뮬레이션 → 수정 → verification
    │
    ▼
Check (검증 = verification)
```

## 다른 스킬과의 관계

| 스킬 | 관계 |
|------|------|
| **smart-pdca** | 작업 크기(S/M/L)에 따라 시뮬레이션 횟수 결정 |
| **iron-law** | iron-law의 "증거 없이 완료 없다"를 보완 — 시뮬레이션도 증거의 일부 |
| **verification** | 시뮬레이션 통과 후 verification이 최종 게이트 역할 |
| **impact-analysis** | 시뮬레이션의 "기존 코드 호환성" 분석과 유사하지만, impact-analysis는 수정 전, error-simulation은 수정 후 |
| **test-strategy-advisor** | 시뮬레이션에서 발견된 엣지 케이스를 테스트로 추가할 때 연동 |

---

## 핵심 원칙

1. **추측으로 수정하지 않는다** — 시뮬레이션에서 "이것도 문제일 수 있다"는 추측은 기록만 하고, 실제 재현 가능한 문제만 수정한다
2. **과잉 수정 금지** — 시뮬레이션은 오류를 잡는 것이지, 리팩토링이 아니다. 동작하는 코드를 불필요하게 바꾸지 않는다
3. **S 작업은 반드시 스킵** — 토큰과 시간 절약이 목적. 단순 수정에 시뮬레이션을 돌리면 본말이 전도된다
