# Iron Law (철칙)

## 핵심 요약

1. **테스트 먼저 작성** → 실패 확인 → 구현 → 통과 확인
2. **증거 없이 완료 없다** → 테스트 결과, 동작 확인, 로그 중 하나 필수
3. **예외**: UI/CSS 변경, 설정 파일, 문서, 프로토타입은 TDD 면제
4. **S 작업**: TDD 선택, 증거 1개 필수 / **M·L 작업**: TDD 필수, 전체 검증 필수
5. **위반 감지 시**: 즉시 멈추고 올바른 순서로 재시작

---

## 두 가지 철칙

### 철칙 1: 테스트 먼저 (TDD)

> 코드를 작성하기 전에 반드시 테스트를 먼저 작성한다.

**순서:**

1. 실패하는 테스트 작성
2. 테스트 실행 → 실패 확인
3. 최소한의 코드로 테스트 통과
4. 테스트 실행 → 통과 확인
5. 리팩토링 (필요한 경우)

**왜 이 순서인가?**

테스트를 나중에 쓰면 이미 작성된 코드에 맞게 테스트를 짜는 경향이 생긴다.
테스트를 먼저 쓰면 "무엇을 만들어야 하는가"를 먼저 정의하게 되어, 코드가 더 명확해진다.

**예외 (테스트를 먼저 쓰지 않아도 되는 경우):**

- UI/CSS 변경 (시각적 확인으로 대체)
- 설정 파일 변경 (config, env 등)
- 문서 수정 (README, 주석 등)
- 프로토타입/실험 코드 (사용자가 명시한 경우)

---

### 철칙 2: 증거 없이 완료 없다

> 완료 선언 전 반드시 증거를 제시한다. 상세 체크리스트는 verification 스킬 참고.

---

## 적용 강도 (smart-pdca 연동)

| 작업 크기 | TDD 적용 | 검증 증거 |
|----------|----------|----------|
| S (소) | 선택 (단순 수정은 면제) | 필수 (최소 증거 1개) |
| M (중) | 필수 | 필수 (테스트 + 동작 확인) |
| L (대) | 필수 | 필수 (전체 리뷰 파이프라인) |

### S (소) 예시

```
# 버튼 색상 변경 같은 단순 수정
- TDD: 면제 (UI 변경이므로)
- 증거: 변경 전후 스크린샷 또는 "변경 확인됨" + 파일 경로
```

### M (중) 예시

```
# 검색 기능 개선
- TDD: 필수 → 검색 결과 반환 테스트 먼저 작성
- 증거: npm test 또는 pytest 실행 결과 캡처
```

### L (대) 예시

```
# 결제 기능 전체 구현
- TDD: 필수 → 각 서비스/컴포넌트마다 테스트 먼저
- 증거: 전체 리뷰 파이프라인 통과 (code-simplifier → external-reviewer → gap-detector)
```

## 위반 시 행동

AI가 iron-law를 위반하려 할 때:

1. **스스로 감지하고 멈춘다**
2. 위반 사실을 알린다:

   > "iron-law 위반 감지: 테스트 없이 코드를 작성하려 했습니다."
   > "올바른 순서로 다시 진행합니다. 먼저 테스트를 작성합니다."

3. 올바른 순서(테스트 먼저)로 다시 시작한다

**감지 상황 예시:**

| 위반 시도 | 감지 방법 | 올바른 행동 |
|----------|----------|-----------|
| 구현 코드부터 작성 | "테스트 파일 없이 구현 파일 생성 시도" | 멈추고 테스트 먼저 작성 |
| 증거 없이 완료 선언 | "테스트 실행 기록 없이 완료 언급" | 멈추고 테스트 실행 후 결과 제시 |
| 임시 코드로 완료 처리 | "TODO, 하드코딩, console.log 잔류" | 멈추고 정리 후 재검증 |

---

## 다른 스킬과의 관계

- **smart-pdca**: 작업 크기(S/M/L)에 따라 iron-law 강도를 결정받는다
- **verification**: iron-law의 "증거 없이 완료 없다"를 실제로 집행하는 게이트
- **test-writer 에이전트**: L 작업에서 iron-law에 의해 항상 호출됨

---

## 철칙 3: 수정 전 코드 상태 재확인

> 조건에 해당할 때만 파일을 다시 읽는다. 매번 읽지 않는다. (토큰 절약)

**재확인 조건 (하나라도 해당하면 Read 필수):**

1. 이 세션에서 **같은 파일을 이미 수정한 적 있을 때**
2. **auto-compact가 발생한 후** (session-context의 수정 파일 목록 참고)
3. 사용자가 **"이미 바꿨는데", "아까 수정했잖아"** 등 과거 수정을 언급할 때

**위 조건에 해당하지 않으면** → 기억 기반으로 바로 수정 (기존과 동일)

**왜 이 규칙이 필요한가?**

AI가 파일을 "읽었던 기억"에 의존하면, 실제 현재 코드와 다른 상태를 기준으로 수정할 수 있다.
특히 같은 파일을 여러 번 수정하거나, auto-compact 후에 이 문제가 자주 발생한다.

---

## 요약

```
코드 작성 전
  → 대상 파일 재확인 (조건 해당 시)
  → 테스트 먼저 작성 (예외가 아닌 경우)
  → 실패 확인
  → 구현
  → 통과 확인
  → 완료 선언 전 증거 제시
```

> iron-law(코드 품질) + evidence-first(추론 품질) + cto-mindset(소통 품질) — 항상 활성화 3종 세트
