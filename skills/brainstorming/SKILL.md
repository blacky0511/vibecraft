# 브레인스토밍

## 역할

사용자의 막연한 아이디어를 구체적인 설계 문서로 발전시킨다.
질문을 통해 요구사항을 명확히 하고, 복수의 접근 방식을 비교하여
실제로 구현 가능한 설계를 확정한다.

---

## 핵심 원칙

1. **한 번에 하나씩 질문한다** — 여러 질문을 동시에 쏟아내지 않는다
2. **선택지를 제공한다** — 열린 질문보다 객관식 선택지를 우선한다
3. **복수의 접근 방식을 제안한다** — 2~3가지를 비교하고, 추천을 명시한다
4. **섹션별로 확인받는다** — 설계를 한꺼번에 제시하지 않고, 섹션마다 사용자 확인을 받는다
5. **YAGNI 원칙을 지킨다** — 불필요한 기능은 과감히 제거한다
6. **설계 없이 구현에 들어가지 않는다** — 이 스킬은 HARD-GATE다

---

## 전체 흐름

```
1단계: 프로젝트 컨텍스트 파악
    ↓
2단계: 질문으로 요구사항 구체화
    ↓
3단계: 접근 방식 2~3가지 제안 + 추천
    ↓
4단계: 설계 섹션별 작성 + 사용자 확인
    ↓
5단계: 설계 문서를 docs/plans/에 저장
    ↓
6단계: writing-plans 스킬로 전환
```

---

## 1단계: 프로젝트 컨텍스트 파악

스킬 시작 시 현재 프로젝트를 먼저 파악한다.

- `package.json`, `build.gradle`, `pom.xml` 등 설정 파일 확인
- 기존 코드베이스 구조 파악 (디렉토리, 주요 파일)
- 이미 존재하는 관련 기능 확인

파악 후 사용자에게 요약하여 알린다:

```
현재 프로젝트를 확인했습니다.
- 기술 스택: Next.js + TypeScript
- 관련 기존 코드: (없음 / 있다면 파일명)

이제 아이디어를 들어볼게요.
```

---

## 2단계: 질문으로 요구사항 구체화

사용자의 아이디어를 한 가지씩 질문하여 구체화한다.

### 질문 순서 (우선순위 순)

1. **목적** — 이 기능/앱이 해결하는 문제가 무엇인가?
2. **사용자** — 누가 사용하는가? (개발자 본인 / 일반 사용자 / 특정 그룹)
3. **핵심 기능** — 반드시 있어야 하는 기능은 무엇인가?
4. **제외 기능** — 지금은 필요 없는 기능은 무엇인가? (YAGNI)
5. **규모** — 예상 사용자 수, 데이터 규모
6. **기술 제약** — 사용해야 하는 기술이 있는가? 피해야 하는 기술이 있는가?

### 질문 예시

```
어떤 문제를 해결하려고 하시나요?

(1) 반복적인 수작업을 자동화하고 싶다
(2) 데이터를 한눈에 보는 대시보드가 필요하다
(3) 팀원들과 정보를 공유하고 싶다
(4) 직접 입력해 주세요: ___
```

### 질문 중단 기준

아래 조건을 모두 충족하면 질문을 멈추고 3단계로 넘어간다:

- 목적이 명확하다
- 핵심 기능 3개 이상 확정됐다
- 기술 스택 방향이 잡혔다

---

## 3단계: 접근 방식 제안

수집된 요구사항을 바탕으로 2~3가지 접근 방식을 제안한다.

### 제안 형식

```
## 접근 방식 비교

### 접근 1: (이름)
- 개요: (한 줄 요약)
- 장점: (구체적으로)
- 단점: (솔직하게)
- 예상 구현 기간: (일 단위)

### 접근 2: (이름)
- 개요:
- 장점:
- 단점:
- 예상 구현 기간:

### 접근 3: (이름, 선택)
- 개요:
- 장점:
- 단점:
- 예상 구현 기간:

---

추천: 접근 (번호)
이유: (추천 이유를 2~3문장으로)

어떤 접근 방식으로 진행할까요?
```

### 추천 기준

- **단순함 우선** — 요구사항을 충족하는 가장 단순한 방법을 추천한다
- **기존 기술 스택 활용** — 새 기술 도입은 필요할 때만 제안한다
- **YAGNI** — "나중에 필요할 것 같은" 기능을 위해 복잡도를 높이지 않는다

---

## 4단계: 설계 섹션별 작성

접근 방식 확정 후, 설계를 섹션별로 작성하고 각 섹션마다 사용자 확인을 받는다.

### 섹션 1: 기능 목록 (Feature List)

```
## 기능 목록

### 핵심 기능 (MVP — 반드시 구현)
- [ ] 기능 A
- [ ] 기능 B
- [ ] 기능 C

### 추가 기능 (나중에 구현)
- [ ] 기능 D
- [ ] 기능 E

### 제외 기능 (이번에는 만들지 않음)
- 기능 F — 이유: 사용 빈도가 낮을 것으로 예상
- 기능 G — 이유: 핵심 가치와 거리가 있음

이 기능 목록으로 진행할까요?
```

### 섹션 2: 데이터 구조 (Data Model)

```
## 데이터 구조

(주요 엔티티와 관계를 설명)

예시:
- User: id, email, name, createdAt
- Post: id, title, content, userId, createdAt
- 관계: User 1 → N Post

이 데이터 구조로 진행할까요?
```

### 섹션 3: 화면 구성 (UI가 있는 경우)

```
## 화면 구성

1. 메인 페이지 — (역할 설명)
2. 상세 페이지 — (역할 설명)
3. 설정 페이지 — (역할 설명)

이 화면 구성으로 진행할까요?
```

### 섹션 4: 기술 스택 확정

```
## 기술 스택

| 분류 | 기술 | 선택 이유 |
|------|------|---------|
| 프론트엔드 | | |
| 백엔드 | | |
| 데이터베이스 | | |
| 인증 | | |
| 배포 | | |

이 기술 스택으로 진행할까요?
```

### 섹션 5: 단계별 구현 순서

```
## 구현 순서

1단계: 기반 구조 (예상 N일)
  - 작업 A
  - 작업 B

2단계: 핵심 기능 (예상 N일)
  - 작업 C
  - 작업 D

3단계: UI 완성 (예상 N일)
  - 작업 E
  - 작업 F

이 순서로 진행할까요?
```

---

## 5단계: 설계 문서 저장

모든 섹션이 확정되면 `docs/plans/` 디렉토리에 설계 문서를 저장한다.

### 파일명 형식

```
docs/plans/YYYY-MM-DD-{기능명 또는 프로젝트명}-design.md
```

예시: `docs/plans/2026-02-27-todo-app-design.md`

### 저장 완료 후 알림

```
설계 문서를 저장했습니다.
경로: docs/plans/2026-02-27-todo-app-design.md

이제 writing-plans 스킬로 넘어가서 단계별 구현 계획을 작성하겠습니다.
```

---

## 6단계: writing-plans 스킬로 전환

설계 문서 저장 후 `vibecraft:writing-plans` 스킬을 호출하여 구현 계획 작성 단계로 넘어간다.

---

## HARD-GATE 규칙

다음 조건을 모두 충족하기 전에는 절대로 코드를 작성하지 않는다:

- [ ] 요구사항이 구체화되었다 (2단계 완료)
- [ ] 접근 방식이 확정되었다 (3단계 완료)
- [ ] 기능 목록이 확정되었다 (섹션 1 완료)
- [ ] 데이터 구조가 확정되었다 (섹션 2 완료)
- [ ] 기술 스택이 확정되었다 (섹션 4 완료)
- [ ] 설계 문서가 저장되었다 (5단계 완료)

조건 미충족 시:
```
아직 설계가 완료되지 않았습니다.
(미완료 항목)을 먼저 확정해 주세요.
설계 없이 구현에 들어가면 나중에 큰 수정이 필요할 수 있습니다.
```

| 단계 | 확인 내용 |
|------|----------|

| 섹션 1 | 기능 목록 확정 |
| 섹션 2 | 데이터 구조 확정 |

| 섹션 4 | 기술 스택 확정 |
| 섹션 5 | 구현 순서 확정 |
| 5단계 완료 시 | 저장된 설계 문서 경로 안내 |
