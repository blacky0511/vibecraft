# 구현 계획 작성 스킬

## 역할

research 또는 brainstorming 단계에서 확정된 내용을 받아,
실제 코드 작성에 바로 사용할 수 있는 단계별 구현 계획 문서를 생성한다.

이 계획서는 `executing-plans` 스킬이 서브에이전트에 전달할 작업 지시서가 된다.

---

## 서브에이전트 위임 (컨텍스트 절약)

M/L 크기의 plan.md 작성은 메인 세션에서 직접 하지 않는다.
doc-writer 서브에이전트에 위임하여 메인 컨텍스트를 보존한다.

### 위임 절차

1. **지시서 준비** (메인에서 수행, 짧게):
   - 기능명, 목표, 기술 스택, 성공 기준
   - research.md 경로 (서브에이전트가 직접 읽음)
   - 작업 크기 (S/M/L)
   - 특수 지시 (사용자가 강조한 사항, 제외 범위 등)

2. **doc-writer 서브에이전트 스폰 (opus)**:

   ```
   Agent({
     subagent_type: "vibecraft:doc-writer",
     prompt: <지시서>,
     model: "opus",
     run_in_background: true,
     isolation: "worktree"
   })
   ```

   **plan.md 작성은 반드시 opus로 실행한다.** 초안 품질이 높으면 plan-critic 리뷰에서 잡아야 할 것이 줄어들어 전체 계획 품질이 올라간다.

3. **결과 수신** (메인에 들어오는 것):
   - plan.md 저장 경로
   - Step 목록 요약 (번호 + 제목 + 예상 시간, 1줄씩)
   - 총 Step 수, 총 예상 시간
   - 영향 파일 목록

4. **plan-critic 리뷰**:
   - 기존대로 plan-critic 에이전트를 스폰하여 plan.md를 리뷰
   - plan-critic도 서브에이전트이므로 메인 컨텍스트 소비 없음

5. **사용자 확인**:
   - 메인이 Step 목록 요약 + plan-review.md 변경 요약만 보여줌
   - 사용자가 상세 내용을 보고 싶으면 → plan.md 경로 안내 ("에디터에서 열어보세요")

### plan 작성 지시서 형식

doc-writer에 전달하는 프롬프트:

```
## plan.md 작성 지시서

### 기본 정보
- 기능명: {기능명}
- 저장 경로: docs/plans/{feature}/plan.md
- 작업 크기: {S/M/L}

### 목표
{한 문장으로 이 기능이 뭘 하는지}

### 성공 기준
{검증 가능한 조건 목록}

### 기술 스택
{프로젝트의 핵심 기술}

### 참조 문서
- research.md: docs/plans/{feature}/research.md (이 파일을 읽고 기반으로 작성할 것)
- 기존 코드 패턴: {참고할 파일 경로}

### 특수 지시
{사용자가 강조한 사항, 제외 범위, 제약 조건}

### 작성 규칙
- writing-plans 스킬의 "핵심 작성 원칙" 5가지를 따른다
- TDD 순서(테스트 → 실패 확인 → 구현 → 통과 확인 → 커밋)를 준수한다
- 각 Step은 2~5분 완료 가능한 크기로 분해한다
- 코드 블록에 생략(...) 없이 전체 코드를 작성한다
- templates/plan.md 형식을 참고하되, Step 구조는 writing-plans 스킬의 형식을 따른다
```

### 위임하지 않는 경우

| 상황 | 이유 |
|------|------|
| S 크기 | plan.md를 안 만들거나 아주 짧음 (Step 1~3개). 메인에서 직접 써도 컨텍스트 부담 없음 |
| 사용자가 "여기서 바로 써줘" 요청 | 사용자 선호 존중 |

**크기별 위임 규칙:**

| 크기 | plan 작성 방식 |
|------|--------------|
| S | 메인에서 직접 (기존과 동일) |
| M | doc-writer 서브에이전트 위임 (opus) |
| L | doc-writer 서브에이전트 위임 (opus) |

## 선행 조건 검증 (Hard Gate)

plan.md를 작성하기 전에, 반드시 아래를 확인한다.

### research.md 존재 확인

`docs/plans/{feature}/research.md`가 있는지 확인한다.

- **있음** → 정상 진행. research.md의 Part 2(기술 관점)를 기반으로 plan.md를 작성한다.
- **없음 + S 크기** → 정상. S 크기는 research가 필요 없으므로 바로 plan을 작성한다.
- **없음 + project-kickoff 경유** → **정상**. 새 프로젝트는 코드가 없으므로 research 불필요. brainstorming의 설계 문서(design.md)를 기반으로 plan.md를 작성한다.
- **없음 + M/L 크기 (기존 프로젝트)** → **차단**. 아래 안내를 출력하고 plan 작성에 들어가지 않는다.

```
research.md가 없습니다.
M/L 크기 작업은 코드베이스 리서치가 선행되어야 합니다.
먼저 vibecraft:research 스킬을 실행할까요?
```

> 이 게이트는 사용자가 "계획 짜줘"로 바로 진입했을 때 R 단계를 건너뛰는 것을 방지한다.

## 핵심 작성 원칙

1. **코드베이스 무지 가정**: 이 계획을 읽는 엔지니어(또는 서브에이전트)가 프로젝트에 대해 아무것도 모른다고 가정하고 작성한다. 파일 경로, 함수명, 명령어를 생략하지 않는다.
2. **bite-sized 단위**: 각 Step은 2~5분 안에 완료할 수 있는 작업이어야 한다. 하나의 Step에 여러 책임을 몰아넣지 않는다.
3. **TDD 순서 준수**: 모든 구현 Step은 아래 순서를 따른다.
   - 실패하는 테스트 작성 → 테스트 실행(실패 확인) → 최소한의 구현 → 테스트 실행(통과 확인) → 커밋
4. **완전한 정보 포함**: 파일 경로, 전체 코드 블록, 정확한 실행 명령어를 포함한다. "적당히 추가하세요" 같은 모호한 표현을 금지한다.
5. **DRY / YAGNI / 자주 커밋**: 중복 없이, 지금 필요한 것만, 작은 단위로 커밋한다.

---

## 정본 규칙

- **정본은 항상 plan.md 1개**. plan-final.md는 만들지 않는다.
- plan-critic 리뷰 결과를 반영할 때 plan.md를 직접 업데이트한다.
- plan-review.md는 "왜 바꿨는지" 기록용. executing-plans가 읽는 파일이 아니다.
- plan.md가 없으면 실행 불가 (hard gate).

## 계획 문서 형식

저장 위치: `docs/plans/{feature}/plan.md`

### 문서 헤더

```markdown
# [기능명] 구현 계획

**목표**: 한 문장으로 이 기능이 무엇을 하는지 설명
**아키텍처**: 2~3문장으로 전체 구조와 데이터 흐름 설명
**기술 스택**: 이 기능에 사용되는 핵심 기술 (예: Next.js App Router, Prisma, PostgreSQL)
**작성일**: YYYY-MM-DD
**예상 소요 시간**: 전체 Step 합산

---
```

### 파일 목록

계획 시작 전에 새로 생성하거나 수정할 파일을 목록으로 정리한다.

```markdown
## 영향 파일 목록

### 새로 생성
- `경로/파일명.ts` — 역할 한 줄 설명

### 수정
- `경로/파일명.ts` — 어떤 부분을 수정하는지 한 줄 설명
```

---

### Step 구조

각 Step은 아래 형식을 따른다.

```markdown
## Step N: [작업 이름]

**예상 시간**: 2~5분
**파일**: `경로/파일명.ts`

### 1. 테스트 작성

\`\`\`typescript
// 경로/파일명.test.ts
describe('[테스트 대상]', () => {
  it('[예상 동작]', () => {
    // 테스트 코드 (전체 작성)
  });
});
\`\`\`

### 2. 테스트 실행 (실패 확인)

\`\`\`bash
# 실행 명령어
npm test -- 파일명
\`\`\`

예상 출력: `FAIL — [테스트명]`

### 3. 구현

\`\`\`typescript
// 경로/파일명.ts
// 전체 구현 코드 작성 (생략 없음)
\`\`\`

### 4. 테스트 재실행 (통과 확인)

\`\`\`bash
npm test -- 파일명
\`\`\`

예상 출력: `PASS — [테스트명]`

### 5. 커밋

\`\`\`bash
git add 경로/파일명.ts 경로/파일명.test.ts
git commit -m "[타입] 커밋 메시지"
\`\`\`

---
```

## 테스트가 불가능한 경우

UI 컴포넌트, 설정 파일 등 자동화 테스트 작성이 어려운 경우:

- **테스트 작성** 단계를 "동작 확인 방법" 단계로 대체한다.
- 어떤 URL에 접속하고, 무엇을 클릭하고, 무엇이 보여야 하는지 구체적으로 기술한다.

```markdown
### 1. 동작 확인 방법

1. `npm run dev` 실행 후 `http://localhost:3000/경로` 접속
2. [버튼명] 버튼 클릭
3. "[예상 텍스트]" 문구가 화면에 표시되어야 함
```

## 계획 초안 작성 후: 주석 리뷰 사이클

계획서는 한 번에 완성되지 않는다.
**초안 → plan-critic 자동 리뷰 → 사용자 확인 → 반영**을 통해 계획의 정확도를 높인다.

이 사이클이 vibecraft의 핵심 품질 메커니즘이다.

### 사이클 흐름

```
계획 초안 작성 → docs/plans/{feature}/plan.md 저장
    ↓
plan-critic 에이전트 자동 호출 (전 라운드 opus)
    ↓
반복 수정 사이클: 각 라운드가 수정본 기반 리뷰 + 초안 참조
    ↓
plan-review.md 생성 + plan.md 업데이트 완료
    ↓
사용자에게 변경 요약만 제시
    ↓
승인? ─ NO → plan.md 추가 수정 (사용자 메모 or plan-critic 재실행)
  │
  YES
  ↓
executing-plans로 전환
```

### 초안 저장 후 리뷰 요청

```
구현 계획 초안을 저장했습니다: docs/plans/{feature}/plan.md

plan-critic 에이전트가 계획서를 리뷰합니다...
(서브에이전트 리뷰 + Codex MCP 외부 리뷰)

리뷰 결과: docs/plans/{feature}/plan-review.md

변경 요약:
| Step | 최종 판정 | 이유 |
|------|----------|------|
(plan-review.md의 변경 요약 표시)

이대로 진행할까요?
- "좋아" → plan.md 기준으로 실행 시작
- "3번 수정은 빼줘" → plan.md 재수정 후 다시 확인
- 직접 메모를 달고 싶으면 에디터에서 plan.md를 수정해 주세요

아직 구현하지 않습니다.
```

### 메모 반영 규칙

plan-critic 리뷰 외에, 사용자가 직접 메모를 추가할 수도 있다 (선택 사항).
사용자가 "메모 추가했어" (또는 유사 표현)라고 하면:

1. 계획서 파일을 다시 읽는다
2. 사용자가 추가한 모든 메모를 찾는다 (수정 메모 + 질문 메모)
3. **질문 메모** → 해당 개념을 쉽게 설명한다 (계획은 아직 수정하지 않음)
4. **수정 메모** → 각 메모를 반영하여 계획을 업데이트한다
5. **절대 구현에 들어가지 않는다** — 명시적 승인 전까지 계획 수정만 한다
6. 업데이트 내역을 요약하여 보여준다

```
메모 N개를 처리했습니다.

질문 답변:
- Step 3의 "JWT가 뭐야?" → JWT는 로그인 후 서버가 주는 "출입증"입니다.
  매 요청마다 이 출입증을 보여줘야 "이 사람은 로그인한 사람이다"를 증명할 수 있어요.
  → 이 Step을 유지할지 빼실지 알려주세요.

반영 내역:
- Step 4: 캐싱 로직 제거
- Step 7: 삭제 (범위 축소)

추가로 수정할 부분이 있으면 다시 메모를 추가해 주세요.
만족하시면 "좋아" 또는 "실행해"라고 알려주세요.
아직 구현하지 않습니다.
```

### 사용자 메모 유형

사용자가 계획서에 다는 메모는 다양한 형태가 있다:

| 유형 | 메모 예시 | AI 행동 |
|------|----------|---------|
| **질문** | "이거 뭐야?" | 해당 개념을 쉽게 설명한 후, 사용자의 판단을 기다린다 |
| **이유 질문** | "왜 이렇게 해야 해?" | 이유를 설명하고, 대안이 있으면 함께 제시한다 |
| **영향 질문** | "이거 안 하면 어떻게 돼?" | 해당 Step을 빼면 생기는 영향을 솔직히 설명한다 |
| **단순화 요청** | "더 쉬운 방법 없어?" | 더 간단한 대안을 제시한다 (있으면) |
| 범위 축소 | "이건 빼줘" / "나중에 해" | 해당 Step 삭제 또는 후순위로 이동 |
| 방향 결정 | "이건 필요 없어" | 해당 로직을 계획에서 제거 |
| 잘못된 가정 수정 | "이건 PUT이 아니라 PATCH여야 해" | 해당 Step의 HTTP 메서드 변경 |
| 도메인 지식 주입 | "visibility는 리스트에 있어야 해" | 스키마/구조를 재설계 |
| 제약 조건 추가 | "이 함수 시그니처는 절대 바꾸지 마" | 해당 제약을 계획 전체에 반영 |
| 기술 선택 변경 | "그 라이브러리 말고 이거 써" | 관련 Step 전체 수정 |

**질문 메모 처리 규칙**:
- 질문에 답변할 때는 **비유를 활용**하여 개발 경험이 없어도 이해할 수 있게 설명한다
- 설명 후 바로 계획을 수정하지 않는다 — 사용자가 이해한 뒤 판단을 내릴 수 있게 기다린다
- 질문이 많은 것은 좋은 신호다 — 사용자가 계획을 이해하려는 것이므로 절대 서두르지 않는다

### 안전장치: "아직 구현하지 마"

이 사이클에서 가장 중요한 규칙이다.

**메모 반영 후 매번** "아직 구현하지 않습니다"를 명시한다.
사용자가 명시적으로 "좋아", "실행해", "진행해" 등 승인 의사를 표현하기 전까지
절대로 코드를 작성하지 않는다.

이 문장이 없으면 AI가 "이 정도면 충분하다"고 자체 판단하여
코드를 쓰기 시작하는 문제가 발생한다. 주도권은 항상 사용자에게 있다.

---

## 승인 후: 실행 방식 선택

사용자가 계획을 승인하면 실행 방식을 제안한다.

```
계획이 확정되었습니다: docs/plans/{feature}/plan.md

어떤 방식으로 진행할까요?

1. [이 세션에서 바로 실행] — executing-plans 스킬로 지금 바로 구현을 시작합니다.
   → 빠르게 진행하고 싶을 때 선택

2. [새 세션에서 실행] — 계획서를 저장해 두고, 나중에 새 세션에서 독립적으로 실행합니다.
   → 지금 당장 실행하지 않고 계획만 확정할 때 선택

어떤 방식을 원하시나요?
```

사용자가 **1번**을 선택하면 → `executing-plans` 스킬을 호출한다.
사용자가 **2번**을 선택하면 → 계획서 저장 경로를 안내하고 종료한다.

---

## 계획 품질 체크리스트

계획서 작성 완료 전 아래 항목을 스스로 점검한다.

- [ ] 모든 파일 경로가 프로젝트 루트 기준 절대 경로로 표기되어 있는가?
- [ ] 각 Step의 코드 블록에 생략(`...`, `// 나머지 코드`)이 없는가?
- [ ] 모든 실행 명령어가 그대로 복붙하면 실행되는 수준인가?
- [ ] 각 Step이 2~5분 이내 완료 가능한 크기인가?
- [ ] TDD 순서(테스트 → 실패 확인 → 구현 → 통과 확인 → 커밋)를 따르고 있는가?
- [ ] 커밋 메시지가 프로젝트 CLAUDE.md의 커밋 메시지 규칙을 따르는가?

## 연동 흐름

```
research (코드베이스 파악)
    │
    ▼
brainstorming (요구사항 확정, L만)
    │
    ▼
writing-plans (현재 스킬: 계획 문서 생성)
    │
    ▼
plan-critic (에이전트: 자동 리뷰)
    │
    ▼
사용자 확인
    │
    ├── 1번 선택 → executing-plans (서브에이전트 실행)
    │
    └── 2번 선택 → 종료 (docs/plans/{feature}/에 계획서 저장)
```
