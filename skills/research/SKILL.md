# 코드베이스 리서치

## 역할

코드베이스를 **깊이** 읽고, 비즈니스 관점과 기술 관점을 분리한 리서치 문서를 생성한다.
brainstorming에서 분리된 독립 스킬로, RPDCA의 R(Research) 단계를 담당한다.

---

## 서브에이전트 위임 (컨텍스트 절약)

M/L 크기의 research는 메인 세션에서 직접 하지 않는다.
code-analyzer 서브에이전트에 위임하여 메인 컨텍스트를 보존한다.

### 위임 절차

1. **지시서 준비** (메인에서 수행, 짧게):
   - 기능명, 작업 목표
   - 탐색 대상 범위 (디렉토리, 파일 패턴)
   - 기술 스택 (이미 알고 있는 것)
   - 특별히 확인해야 할 것 (사용자가 언급한 파일, 제약 조건)

2. **code-analyzer 서브에이전트 스폰**:

   ```
   Agent({
     subagent_type: "vibecraft:code-analyzer",
     prompt: <리서치 지시서>,
     run_in_background: true
   })
   ```

   > code-analyzer 에이전트는 sonnet으로 실행된다. research는 "넓게 읽는" 작업이라 sonnet의 속도가 효율적이고, opus는 plan 작성/리뷰에 집중한다.

3. **결과 수신** (메인에 들어오는 것):
   - research.md 저장 경로
   - Part 1 비즈니스 관점 전문 (사용자에게 바로 보여줄 수 있게)
   - 관련 파일 수, 핵심 패턴, 결정 필요 사항 요약

4. **사용자 확인** (L 크기만):
   - Part 1을 사용자에게 보여주고 확인받음
   - 상세 기술 내용은 "research.md를 에디터에서 확인하세요" 안내

### 위임하지 않는 경우

| 상황 | 이유 |
|------|------|
| S 크기 | research 자체를 스킵 |
| 파일 5개 이하의 소규모 조사 | 메인에서 직접 읽는 게 빠름 |

### 크기별 위임 규칙

| 크기 | research 방식 |
|------|-------------|
| S | 스킵 |
| M | code-analyzer 서브에이전트 위임 |
| L | code-analyzer 서브에이전트 위임 |

---

## 핵심 원칙

1. **깊이 읽는다** — 함수 시그니처만 보지 않고, 내부 로직까지 이해한다
2. **매우 상세히 파악한다** — "대충 이런 구조구나"에서 멈추지 않는다
3. **모든 세부 사항을 기록한다** — 계획에 영향을 줄 수 있는 것은 전부 적는다
4. **두 독자를 동시에 만족시킨다** — 비개발자(Part 1) + AI/개발자(Part 2)

## research.md 구조

```markdown
# {feature} 코드베이스 리서치

---

## Part 1: 비즈니스 관점 (사용자용)

### 이 기능이 하는 일
한 문단으로 쉬운 말로 설명한다.
전문 용어 없이, 이 기능이 사용자에게 어떤 가치를 주는지 중심으로 작성한다.

예: "네이버 플레이스에서 키워드별 순위를 가져와서 DB에 저장하고,
변동이 있으면 텔레그램으로 알려주는 기능"

### 데이터 흐름 (쉬운 버전)
1. 사용자가 ___한다
2. 시스템이 ___한다
3. 결과로 ___가 된다

### 이미 있는 것 / 새로 필요한 것
- **있음**: (이미 구현된 기능)
- **필요**: (새로 만들어야 하는 것)

### 결정이 필요한 것
- 질문 1? (선택지가 있으면 함께 제시)
- 질문 2?

---

## Part 2: 기술 관점 (AI·개발자용)

### 관련 파일
| 파일 경로 | 역할 | 비고 |
|----------|------|------|

### 기존 패턴
프로젝트가 따르고 있는 코딩 패턴을 정리한다.
- 에러 처리: (예: AppError → errorHandler 미들웨어)
- DB 접근: (예: Repository 패턴)
- API 구조: (예: Controller → Service → Repository)
- 네이밍: (예: camelCase, 파일은 kebab-case)

### 영향 범위
이 기능을 추가/수정하면 영향받을 수 있는 코드를 나열한다.

### 열린 질문
각 항목을 **[사실] (E1/E2) / [가설] (E3) / [결정 대기] (E0)**로 구분한다.
- [사실] 현재 인증은 JWT 기반이다 → 코드에서 확인됨
- [가설] 리프레시 토큰이 필요할 것으로 보인다 → 확인 필요
- [결정 대기] 소셜 로그인도 지원할 것인가? → 사용자 결정 필요

### 신뢰도 요약
- E1/E2 (확인됨): N개 항목
- E3 (추론): N개 항목 — 계획 전에 확인 필요
- E0 (미확인): N개 항목 — 반드시 확인 후 진행

> E3/E0 비율이 전체의 50%를 넘으면 리서치가 불충분하다. 추가 조사 후 진행한다.

### 계획 입력값
다음 단계(설계/계획)에 넘길 핵심 정보를 요약한다.
- 기술 스택: (확인된 스택)
- 재사용 가능한 기존 코드: (파일명, 함수명)
- 반드시 지켜야 할 제약: (기존 패턴, 인터페이스 등)
- 절대 건드리면 안 되는 코드: (있다면)
```

## 스마트 아카이브 참조

리서치 시작 시 과거 작업을 효율적으로 참고한다.

1. `docs/plans/archive/`에서 같은 파일을 다룬 과거 리서치가 있는지 **파일명만 검색**
2. 관련 과거 문서가 있으면 → 그때만 읽어서 참고
3. 없으면 → 스킵 (토큰 절약)

## 리서치 완료 후 안내

### M 크기
```
코드베이스 리서치를 완료했습니다.
리서치 문서: docs/plans/{feature}/research.md

주요 발견:
- 관련 파일 N개 확인
- 기존 패턴: (핵심 요약)
- 결정 필요 사항 N개

다음 단계: vibecraft:writing-plans 스킬을 호출하여 구현 계획을 작성합니다.
```

### L 크기
```
코드베이스 리서치를 완료했습니다.
리서치 문서: docs/plans/{feature}/research.md

Part 1 (비즈니스 관점)을 확인해 주세요.
특히 "결정이 필요한 것" 섹션에 답변을 주시면 설계에 반영하겠습니다.

다음 단계: 확인 후 vibecraft:brainstorming 스킬을 호출하여 요구사항을 구체화합니다.
```

## 리서치 범위

- `package.json`, `build.gradle`, `pom.xml` 등 설정 파일 확인
- 기존 코드베이스 구조 파악 (디렉토리, 주요 파일)
- 사용자의 요청과 **관련된 기존 코드를 깊이 읽는다**
- 기존 패턴(에러 처리, DB 접근, API 구조 등)을 파악한다
- 변경 시 영향받을 수 있는 파일을 추적한다

---

## 호출 방식

| 호출 방식 | 설명 |
|----------|------|
| 직접 호출 | 사용자가 "리서치해줘"로 직접 요청 |
| new-feature 내부 | smart-pdca가 M/L 판별 후 자동 호출 |
| systematic-debugging 내부 | M/L 버그에서 자동 호출 |

---

## 연동 스킬

| 스킬 | 연동 시점 | 역할 |
|------|----------|------|
| smart-pdca | 이 스킬 호출 전 | 크기 판별 후 M/L일 때 research 호출 |
| brainstorming | 이 스킬 완료 후 (L만) | research.md 기반으로 요구사항 구체화 |
| writing-plans | 이 스킬 완료 후 | research.md 기반으로 plan.md 작성 |
