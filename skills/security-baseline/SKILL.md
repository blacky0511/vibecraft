# 보안 기본 원칙 (Security Baseline)

## 역할

기술 스택에 관계없이 모든 코드 작성 시 AI가 자동으로 적용하는 보안 규칙.
사용자에게 "보안 검사할까요?"라고 묻지 않는다. 무조건 적용한다.

---

## 핵심 원칙

> "안전하지 않은 코드를 만들려면 오히려 더 노력해야 하는 구조"를 만든다.

---

## 1. 비밀값 관리

- 비밀번호, API 키, 토큰, DB 접속 정보는 **절대 코드에 직접 넣지 않는다**.
- 환경변수(`.env`)로 관리하고, `.env`는 `.gitignore`에 반드시 포함한다.
- `.env.example` 파일을 만들어 필요한 환경변수 목록을 문서화한다 (값은 비움).
- 프론트엔드 환경변수는 브라우저에 노출됨을 인지한다. 진짜 비밀값은 서버에서만 사용한다.

## 2. 입력 검증

- 사용자 입력값은 **서버에서 반드시 검증**한다. 클라이언트 검증만으로 신뢰하지 않는다.
- SQL 쿼리는 파라미터 바인딩을 사용한다. 문자열 결합으로 쿼리를 만들지 않는다 (SQL 인젝션 방지).
- HTML에 사용자 입력을 직접 삽입하지 않는다 (XSS 방지). 프레임워크의 이스케이프 기능을 활용한다.

## 3. 인증과 비밀번호

- 비밀번호는 **반드시 해싱**하여 저장한다. 평문 저장 절대 금지.
  - Java/Spring: `BCryptPasswordEncoder`
  - Python: `bcrypt` 또는 `passlib`
  - Node.js: `bcrypt` 또는 `argon2`
- JWT 사용 시 시크릿 키는 환경변수로 관리하고, 적절한 만료 시간을 설정한다.
- 인증이 필요한 API 엔드포인트에는 반드시 인증 체크를 포함한다.

## 4. 에러 처리

- 에러 응답에 **시스템 내부 정보를 노출하지 않는다**.
  - 스택 트레이스 노출 금지
  - DB 테이블/컬럼 구조 노출 금지
  - 내부 파일 경로 노출 금지
- 사용자에게는 일반적인 에러 메시지만 반환하고, 상세 내용은 서버 로그에만 기록한다.
- 프로덕션 환경에서는 디버그 모드를 반드시 끈다.

## 5. CORS와 네트워크

- CORS 설정 시 와일드카드(`*`) 대신 허용할 도메인을 명시적으로 지정한다.
- 프로덕션에서는 HTTPS를 사용한다.
- 쿠키에 민감 정보를 저장할 때는 `HttpOnly`, `Secure`, `SameSite` 플래그를 설정한다.

---

## 자동 감지 트리거

AI는 아래 상황을 감지하면 해당 보안 규칙을 자동으로 적용한다.

| 감지 패턴 | 자동 행동 |
|-----------|----------|
| 로그인/회원가입 코드 작성 | 비밀번호 해싱, 토큰 관리 규칙 적용 |
| DB 쿼리 작성 | 파라미터 바인딩 여부 확인 |
| 환경변수가 아닌 곳에 시크릿 발견 | 즉시 환경변수로 이동 |
| API 엔드포인트 추가 | 인증/인가 필요 여부 확인 |
| 에러 핸들러 작성 | 내부 정보 노출 여부 확인 |
| 파일 업로드 기능 | 파일 타입/크기 제한 확인 |

---

## verification과의 연동

verification 스킬의 "보안 확인" 체크리스트와 연동된다.
이 스킬이 코드 작성 시점의 가드레일이라면, verification은 완료 시점의 최종 점검이다.
