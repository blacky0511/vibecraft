# 코드 리뷰 피드백 처리

## 역할

리뷰어의 피드백을 받았을 때, 감정이 아닌 기술적 근거로 각 항목을 평가한다.
타당한 피드백은 반영하고, 동의하기 어려운 피드백에는 근거 있는 반론을 제시한다.
"알겠습니다, 수정하겠습니다"로 일괄 동의하거나 "제 방식이 맞습니다"로 일괄 거부하지 않는다.

---

## 피드백 처리 원칙

### 핵심 규칙
1. **감정 배제**: 피드백을 개인적인 공격으로 받아들이지 않는다. 코드에 대한 의견일 뿐이다.
2. **무조건 동의 금지**: 모든 피드백이 옳지는 않다. 기술적으로 검증한다.
3. **무조건 거부 금지**: 반론이 있더라도 리뷰어의 관점에서 이유를 먼저 이해한다.
4. **증거 기반 판단**: "느낌상 맞는 것 같다"가 아니라 공식 문서, 벤치마크, 실제 동작으로 판단한다.
5. **반론 시 근거 필수**: 동의하지 않을 경우 "저는 이렇게 생각합니다"가 아닌 구체적 근거를 제시한다.

---

## 피드백 분류 기준

피드백을 받으면 아래 기준으로 분류한다.

| 분류 | 설명 | 처리 방식 |
|------|------|----------|
| **반드시 수정** | 버그, 보안 취약점, 명백한 오류 | 즉시 수정, 감사 표현 |
| **수용 권고** | 가독성 개선, 더 나은 패턴 제안 | 검토 후 수용, 이유 이해 |
| **취향/스타일** | 팀 컨벤션이 없는 코딩 스타일 차이 | 팀 기준이 없으면 협의, 있으면 기준 따름 |
| **근거 부족** | "이렇게 하세요"만 있고 이유가 없음 | 이유를 물어본다 |
| **동의 불가** | 기술적으로 틀렸거나 더 나쁜 방향 | 근거를 들어 정중히 반론 |

---

## 피드백 처리 절차

### 1단계 — 피드백 목록 정리

피드백 항목을 아래 형식으로 정리한다.

```
## 피드백 처리 목록

| # | 피드백 내용 | 분류 | 처리 방향 |
|---|------------|------|----------|
| 1 | (피드백 원문 요약) | 반드시 수정 / 수용 권고 / 취향 / 근거 부족 / 동의 불가 | 수정 / 협의 / 반론 / 질문 |
```

### 2단계 — 항목별 기술 검증

분류가 불명확한 항목은 아래 절차로 검토한다.

1. **리뷰어의 의도 파악**: 왜 이렇게 제안했는지 이해한다.
2. **기술적 사실 확인**: 공식 문서, 언어 스펙, 성능 벤치마크로 확인한다.
3. **현재 코드와 비교**: 제안된 방식이 현재보다 실제로 나은가?
4. **트레이드오프 분석**: 개선되는 점과 포기하는 점을 함께 검토한다.

### 3단계 — 반론 작성 (필요한 경우)

동의하기 어려운 항목에는 아래 형식으로 반론을 작성한다.

```
[피드백 #번호에 대한 반론]

피드백 내용: (원문 요약)

현재 방식을 유지하는 이유:
- (근거 1: 공식 문서 링크 또는 설명)
- (근거 2: 실제 동작 결과 또는 벤치마크)
- (근거 3: 트레이드오프 분석)

대안 검토:
- 제안된 방식의 장점: (인정할 부분)
- 제안된 방식의 단점 또는 현재 상황과 맞지 않는 이유:

결론:
- 현재 방식 유지 / 부분 수용 / 추가 논의 필요
```

### 4단계 — 수정 실행

수용하기로 결정한 항목만 수정한다.

수정 원칙:
- 한 번에 하나씩 수정하고, 각 수정 후 동작을 확인한다.
- 수정 내용을 코드 리뷰 답변에 반드시 기록한다.
- 수정이 완료되면 `vibecraft:verification` 스킬로 검증한다.

---

## 리뷰 답변 작성 형식

수정 완료 후 리뷰어에게 보내는 답변 형식이다.

```
## 코드 리뷰 반영 결과

감사합니다. 피드백을 검토하고 아래와 같이 처리했습니다.

### 수정 완료
- [ ] #1: (피드백 요약) → (수정 내용 간략 설명)
- [ ] #3: (피드백 요약) → (수정 내용 간략 설명)

### 협의 필요
- #2: (피드백 요약)
  → (이유 또는 질문)

### 반론
- #4: (피드백 요약)
  → (반론 내용 요약)
  → (근거: ...)
  → 추가 논의를 원하신다면 말씀해 주세요.

### 미반영 항목
- #5: (피드백 요약)
  → (미반영 이유: 팀 컨벤션과 충돌 / 다른 트레이드오프 선택 / 등)
```

## 자주 발생하는 상황별 대응

### "이렇게 하는 게 더 낫지 않나요?" (근거 없는 제안)
```
→ "왜 이 방식이 더 나은지 조금 더 설명해 주실 수 있을까요?
   현재 방식과 비교하여 어떤 부분에서 개선이 되는지 이해하고 싶습니다."
```

### "이 변수명이 이상합니다" (스타일 의견)
```
→ 팀 컨벤션이 있다면: "컨벤션 문서 기준으로 수정하겠습니다."
→ 컨벤션이 없다면: "팀 기준을 정하는 게 좋을 것 같습니다. 어떤 네이밍 규칙을 선호하시나요?"
```

### "이 로직은 버그가 있습니다" (오류 지적)
```
→ 즉시 검증한다. 맞으면: "발견해 주셔서 감사합니다. 바로 수정하겠습니다."
→ 틀리면: "확인해 보니 (조건 X)에서는 정상 동작합니다. (Y 케이스)에서 발생한다는 말씀인가요?"
```

---

## 핵심 규칙 요약

- 피드백은 코드에 대한 것이지, 사람에 대한 것이 아니다.
- 모든 피드백을 수용하는 것은 좋은 개발자가 아니다. 비판적 사고를 유지한다.
- 반론은 정중하게, 근거는 구체적으로.
- 수정 후에는 반드시 동작을 검증한다.
