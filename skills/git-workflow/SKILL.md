# Git 워크플로우

## 역할

사용자가 Git 관련 작업을 요청하거나, 브랜치/커밋/PR 관련 키워드가 감지되면 이 스킬을 활성화한다.
Git을 잘 모르는 사용자도 안전하게 버전 관리를 할 수 있도록 AI가 단계별로 안내한다.

---

## 브랜치 전략

```
main (안전한 완성본 — 항상 동작하는 코드만 유지)
  └── feature/기능이름 (새 기능 작업용)
  └── fix/버그이름 (버그 수정용)
```

### 브랜치 네이밍 규칙

- 영어 소문자 + 하이픈(kebab-case) 사용
- 예시: `feature/user-login`, `feature/payment-integration`, `fix/login-error`, `fix/image-upload`

---

## 커밋 메시지 규칙

> 커밋 메시지 형식, 타입 종류, 예시의 상세 내용은 **전역 CLAUDE.md의 "커밋 메시지 가이드" 섹션**을 참고한다.

**핵심 요약**:
- 형식: `[타입] 변경 내용 요약` (한국어, 50자 이내)
- 본문: 변경 파일 목록 + 이유 필수
- 타입: `[기능]`, `[수정]`, `[개선]`, `[스타일]`, `[문서]`, `[설정]`, `[테스트]`, `[삭제]`

---

## AI가 반드시 해야 할 일

### 1. 새 작업 시작 시 — 브랜치 생성 제안

작업 요청을 받으면 바로 코드를 수정하기 전에, 먼저 브랜치 생성을 제안한다.

```
새 작업을 시작하기 전에 브랜치를 만들까요?

제안 브랜치명: feature/user-login

브랜치(branch)란? main의 복사본을 만들어서 그곳에서 작업하는 것입니다.
작업이 잘못되어도 main은 안전하게 유지됩니다.

만들까요? (예/아니오)
```

### 2. 작업 중 — 의미 있는 단위로 커밋 안내

컴포넌트 1개 완성, 기능 1개 완성 등 의미 있는 단위마다 커밋을 제안한다.

```
로그인 폼 컴포넌트 작성이 완료되었습니다.
지금 커밋(저장)해 두는 것이 좋겠습니다.

커밋이란? 현재 상태를 사진 찍듯 저장하는 것입니다.
나중에 문제가 생기면 이 시점으로 되돌릴 수 있습니다.

커밋 메시지 (안):
[기능] 로그인 폼 컴포넌트 추가

커밋할까요? (예/아니오)
```

### 3. 작업 완료 시 — PR 생성 제안

작업이 완료되면 main에 합치기 위한 PR 생성을 제안한다.

```
작업이 완료되었습니다!
main 브랜치에 합치기 위해 PR(Pull Request)을 만들까요?

PR이란? "내가 작업한 내용을 main에 합쳐도 될까요?" 라고 요청하는 것입니다.
코드 검토 후 안전하게 합칠 수 있습니다.

PR을 만들까요? (예/아니오)
```

### 4. Git 명령어 설명 의무

어떤 Git 명령어를 실행하든, 반드시 그 전에 한국어로 쉽게 설명한다.

```
다음 명령어를 실행합니다:
  git checkout -b feature/user-login

설명: 'feature/user-login'이라는 이름의 새 브랜치를 만들고, 그 브랜치로 이동하는 명령입니다.
```

## 사용자 확인 필수 사항

아래 작업은 **반드시 먼저 물어보고** 사용자의 동의를 받은 후 실행한다.
절대로 사용자 확인 없이 단독으로 실행하지 않는다.

| 작업 | 이유 |
|------|------|
| 브랜치 생성 / 삭제 | 되돌리기 어려울 수 있음 |
| main으로 합치기 (merge / PR) | 운영 코드에 영향을 줌 |
| 원격 저장소에 push | 외부에 공개되거나 팀원에게 영향을 줌 |
| 이미 커밋된 내용 수정 (amend) | 히스토리가 바뀌어 되돌리기 어려움 |

---

## 단계별 워크플로우

### 일반 작업 흐름

```
1. 브랜치 생성 제안 및 생성
      │
      ▼
2. 코드 작성 / 수정
      │
      ▼
3. 의미 있는 단위로 커밋 안내
      │
      ▼
4. 작업 완료 → PR 생성 제안
      │
      ▼
5. PR 승인 후 main에 merge
```

### 긴급 버그 수정 흐름 (hotfix)

```
1. fix/버그이름 브랜치 생성
      │
      ▼
2. 버그 수정
      │
      ▼
3. 커밋
      │
      ▼
4. main에 빠르게 merge (사용자 확인 후)
```

---

## 브랜치 마무리

작업 완료 시:
1. PR 생성 제안 ("main에 합칠 PR을 만들까요?")
2. 사용자 확인 후 PR 생성
3. 머지 후 브랜치 삭제 제안
모든 단계에서 사용자 확인 필수

## 자주 사용하는 Git 명령어 설명집

| 명령어 | 한국어 설명 |
|--------|------------|
| `git status` | 현재 어떤 파일이 바뀌었는지 확인 |
| `git add 파일명` | 커밋할 파일을 선택 (스테이징) |
| `git commit -m "메시지"` | 선택한 파일을 저장 (커밋) |
| `git checkout -b 브랜치명` | 새 브랜치를 만들고 이동 |
| `git checkout 브랜치명` | 다른 브랜치로 이동 |
| `git push origin 브랜치명` | 원격 저장소(GitHub 등)에 올리기 |
| `git pull` | 원격 저장소의 최신 내용 가져오기 |
| `git log --oneline` | 커밋 히스토리 간략하게 보기 |
| `git merge 브랜치명` | 다른 브랜치의 내용을 현재 브랜치에 합치기 |

## 잘못된 상황 대응

### 실수로 main에 직접 커밋한 경우

```
main 브랜치에 직접 커밋이 되었습니다.
되돌리기 위한 방법을 안내해 드립니다.
이 작업은 히스토리에 영향을 줍니다. 진행해도 될까요? (예/아니오)
```

### 충돌(Conflict)이 발생한 경우

충돌 내용을 사용자에게 보여주고, 어느 쪽 내용을 유지할지 함께 결정한다.

```
파일 충돌이 발생했습니다: src/components/Header.tsx

충돌이란? 두 브랜치에서 같은 부분을 다르게 수정했을 때 발생합니다.
어느 내용을 사용할지 선택해야 합니다.

[내 변경사항]
  <내용 표시>

[main의 내용]
  <내용 표시>

어느 것을 사용할까요? (내 것 / main 것 / 둘 다 합치기)
```
