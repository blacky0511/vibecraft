# 브랜치 마무리

## 역할

작업이 끝난 브랜치를 안전하게 정리하는 과정을 안내한다.
무작정 머지하지 않고, 상황에 맞는 선택지를 제안하고 사용자가 결정한다.
브랜치 삭제, 머지 등 되돌리기 어려운 작업은 반드시 사용자 확인 후 진행한다.

---

## 현재 상태 확인

먼저 현재 상황을 파악한다.

```bash
# 현재 브랜치 및 커밋 상태 확인
git status
git log --oneline -10
git diff main...HEAD --stat
```

확인 항목:
- 현재 브랜치명
- main과의 커밋 차이
- 커밋되지 않은 변경 사항 여부
- 원격 저장소(GitHub 등)에 push되어 있는지 여부

---

## 선택지 제안

상태 확인 후 아래 3가지 선택지를 사용자에게 제안한다.

```
작업이 완료되었습니다. 브랜치를 어떻게 마무리할까요?

[1] PR 생성
    → 리뷰 후 main에 합치는 방식 (팀 작업, 코드 리뷰가 필요할 때)

[2] main에 바로 머지
    → PR 없이 바로 합치는 방식 (혼자 작업, 빠르게 반영할 때)

[3] 보류
    → 아직 합치지 않고 브랜치만 정리하거나 그대로 둠

어떻게 진행할까요?
```

---

## 선택 1 — PR 생성

### PR 생성 전 준비

PR을 만들기 전에 아래 항목을 확인한다.

- [ ] 모든 변경 사항이 커밋되어 있는가?
- [ ] 원격 저장소(GitHub)에 push되어 있는가?
- [ ] 코드가 정상적으로 동작하는가?
- [ ] 불필요한 디버그 코드나 콘솔 로그가 제거되었는가?

### 원격에 push

```bash
# 현재 브랜치를 원격에 올리기 (처음 push할 경우)
git push -u origin 브랜치명

# 이미 연결된 경우
git push
```

### PR 생성

```bash
# GitHub CLI로 PR 생성
gh pr create \
  --title "PR 제목" \
  --body "변경 내용 설명" \
  --base main \
  --head 현재브랜치명
```

### PR 설명 작성 형식

```
## 변경 사항 요약
- (주요 변경 사항 1)
- (주요 변경 사항 2)

## 변경 이유
(왜 이 작업이 필요했는지)

## 테스트 확인
- [ ] 로컬 동작 확인
- [ ] 주요 케이스 테스트

## 리뷰 요청 포인트
- (특별히 봐줬으면 하는 부분)

## 관련 이슈
관련: #이슈번호
```

### PR 생성 후 안내

```
PR이 생성되었습니다.

다음 단계:
1. 팀원에게 리뷰 요청 (GitHub에서 Reviewers 지정)
2. 리뷰 피드백 반영 → /vibecraft:code-review-receive 스킬 사용
3. 승인 후 Merge 버튼 클릭

PR 링크: (생성된 URL)
```

## 선택 2 — main에 바로 머지

혼자 작업하거나 소규모 수정의 경우 PR 없이 바로 머지한다.

### 머지 전 최종 확인

반드시 사용자에게 확인한다.

```
main에 바로 머지하면 PR 리뷰 과정이 생략됩니다.

현재 브랜치: feature/기능이름
머지 대상: main

변경된 파일:
- (파일 목록)

main에 바로 머지할까요? (예/아니오)
```

### 머지 실행

사용자가 동의한 경우에만 실행한다.

```bash
# main으로 이동
git checkout main

# 최신 상태로 업데이트
git pull origin main

# 작업 브랜치를 머지
git merge feature/기능이름

# 충돌이 없으면 원격에 push
git push origin main
```

### 충돌 발생 시

```
충돌(Conflict)이 발생했습니다.

충돌이란? 두 브랜치에서 같은 파일의 같은 부분을 다르게 수정했을 때 발생합니다.
어느 내용을 사용할지 직접 선택해야 합니다.

충돌 파일 목록:
- (파일명)

충돌 해결 후 다시 커밋하면 머지가 완료됩니다.
도움이 필요하면 알려주세요.
```

---

## 선택 3 — 보류

작업을 아직 합치지 않을 경우의 선택지이다.

```
[1] 브랜치를 그대로 둔다
    → 나중에 다시 작업하거나 PR을 생성할 수 있음

[2] 작업 내용을 임시 저장하고 브랜치를 닫는다 (stash)
    → git stash로 변경 사항을 보관하고 브랜치 삭제

[3] 작업 전체를 취소한다
    → 브랜치 삭제 (되돌릴 수 없음, 반드시 확인)
```

---

## 머지 완료 후 — 브랜치 정리

머지가 완료된 후 작업 브랜치를 삭제한다. 삭제 전 반드시 확인한다.

```
머지가 완료되었습니다.

작업 브랜치 'feature/기능이름'을 삭제할까요?

삭제 후에는 이 브랜치로 되돌아갈 수 없습니다.
(커밋 내용은 main에 포함되어 있으므로 데이터 손실은 없습니다)

삭제할까요? (예/아니오)
```

사용자 동의 후 삭제 실행:

```bash
# 로컬 브랜치 삭제
git branch -d feature/기능이름

# 원격 브랜치 삭제 (GitHub 등)
git push origin --delete feature/기능이름
```

## 작업 완료 요약 보고

브랜치 정리가 끝나면 아래 형식으로 완료 보고를 출력한다.

```
## 브랜치 마무리 완료

- 작업 브랜치: feature/기능이름
- 처리 방법: PR 생성 / main 직접 머지 / 보류
- 머지 커밋: (커밋 해시 또는 PR 링크)
- 브랜치 삭제: 완료 / 유지

### 다음 단계
- [ ] 배포가 필요하면 /vibecraft:deploy-guide 스킬을 사용하세요.
- [ ] 새 작업을 시작하려면 새 브랜치를 만드세요.
```

---

## 핵심 규칙

- 브랜치 삭제, 머지, push는 **반드시 사용자 확인 후** 진행한다.
- 커밋되지 않은 변경 사항이 있으면 머지 전에 먼저 처리한다.
- 충돌 발생 시 사용자와 함께 해결한다. 임의로 선택하지 않는다.
- main 브랜치에 push할 때는 항상 신중히 확인한다.
