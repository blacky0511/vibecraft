# 배포 가이드

## 역할

코드를 서버나 배포 환경에 올릴 때, 빠뜨리는 것 없이 안전하게 배포할 수 있도록
단계별로 안내한다. `deploy-manager` 에이전트와 연동하여 배포 작업을 수행한다.

배포는 되돌리기 어려운 작업이다. 반드시 아래 순서를 지킨다.

---

## 배포 전 필수 정보 확인

배포를 시작하기 전에 아래 항목을 확인한다.

- 어떤 환경에 배포하나요? (개발 서버 / 스테이징 / 운영)
- 현재 작업 브랜치는 무엇인가요?
- 배포할 변경 사항이 main (또는 배포 브랜치)에 머지되어 있나요?
- 이번 배포에 DB 스키마 변경이 포함되어 있나요?
- 이번 배포에 환경 변수 추가/변경이 있나요?

---

## 1단계 — 배포 전 체크리스트

배포를 실행하기 전에 아래 항목을 모두 확인한다. 하나라도 미완료이면 배포를 보류한다.

### 코드 품질 확인
- [ ] 모든 변경 사항이 코드 리뷰를 통과했는가?
- [ ] 자동화 테스트(CI)가 통과되었는가?
- [ ] 로컬 및 스테이징 환경에서 동작을 직접 확인했는가?
- [ ] 빌드가 에러 없이 완료되는가?

### 환경 설정 확인
- [ ] 배포 환경의 환경 변수(.env)가 최신 상태인가?
- [ ] 새로 추가된 환경 변수가 서버에도 등록되었는가?
- [ ] DB 연결 정보가 올바른가?
- [ ] 외부 API 키가 올바른 값으로 설정되어 있는가?

### DB 마이그레이션 확인 (해당하는 경우)
- [ ] 마이그레이션 스크립트가 준비되어 있는가?
- [ ] 마이그레이션이 롤백 가능한 구조인가?
- [ ] 스테이징 DB에서 마이그레이션 테스트를 완료했는가?

### 배포 계획 확인
- [ ] 배포 시간이 적절한가? (트래픽 적은 시간대 권장)
- [ ] 팀원에게 배포 사실을 공유했는가?
- [ ] 롤백 방법을 알고 있는가?

---

## 2단계 — 환경별 배포 설정

### 개발 서버 (dev)
- 용도: 기능 테스트, 팀 내부 확인
- 배포 주기: 자주 (하루 여러 번 가능)
- 주의 사항: 운영 데이터 없음, 실패해도 괜찮음
- 승인 필요: 없음

### 스테이징 서버 (staging)
- 용도: 운영 환경과 동일한 조건에서 최종 검증
- 배포 주기: 운영 배포 직전
- 주의 사항: 운영 DB 복사본 사용 가능, 실제 데이터 주의
- 승인 필요: 팀 리더 확인 권장

### 운영 서버 (production)
- 용도: 실제 사용자 서비스
- 배포 주기: 충분히 검증된 후에만
- 주의 사항: 실제 사용자에게 영향. 신중하게 진행
- 승인 필요: **반드시 팀 리더 또는 담당자 승인 후 진행**

## 3단계 — 배포 명령어 가이드

배포 방법은 프로젝트 기술 스택에 따라 다르다.
프로젝트의 `package.json`, `Dockerfile`, `deploy.sh` 등을 먼저 확인한다.

### 일반적인 배포 명령어 패턴

**Node.js / Next.js**
```bash
# 빌드
npm run build

# 운영 서버 실행
npm start

# PM2 사용 시
pm2 restart app-name
```

**Java / Spring Boot**
```bash
# 빌드 (Maven)
./mvnw clean package -DskipTests

# 빌드 (Gradle)
./gradlew build -x test

# 실행
java -jar target/app.jar --spring.profiles.active=prod
```

**Docker**
```bash
# 이미지 빌드
docker build -t app-name:버전 .

# 컨테이너 실행
docker run -d --name app-name -p 8080:8080 app-name:버전
```

**GitHub Actions / CI-CD 파이프라인**
```bash
# main 브랜치 푸시로 자동 배포
git push origin main
```

> 실제 배포 명령어는 프로젝트 루트의 README.md 또는 deploy 스크립트를 확인하세요.

## 4단계 — 배포 후 확인

배포가 완료되면 아래 항목을 즉시 확인한다.

- [ ] 서비스가 정상적으로 실행되고 있는가? (헬스 체크 엔드포인트 확인)
- [ ] 주요 기능이 정상 동작하는가?
- [ ] 에러 로그가 발생하고 있지는 않은가?
- [ ] 응답 속도가 정상 범위인가?
- [ ] DB 연결이 정상인가?

확인 방법:
```bash
# 서버 로그 확인
tail -f /var/log/app/app.log

# PM2 로그 확인
pm2 logs app-name

# Docker 로그 확인
docker logs -f app-name
```

## 5단계 — 롤백 방법

배포 후 문제가 발생하면 즉시 롤백한다. 롤백은 빠를수록 좋다.

### Git을 이용한 롤백

```bash
# 이전 배포 커밋 확인
git log --oneline

# 이전 버전으로 되돌리기 (사용자 확인 필수)
git revert HEAD
git push origin main

# 또는 이전 태그 버전으로 체크아웃
git checkout v1.2.3
```

### Docker를 이용한 롤백

```bash
# 이전 이미지로 교체
docker stop app-name
docker run -d --name app-name app-name:이전버전
```

### DB 롤백 (마이그레이션이 있었던 경우)

DB 롤백은 데이터 손실 위험이 있다. 반드시 백업 후 진행한다.

```
주의: DB 롤백은 데이터가 삭제될 수 있습니다.
백업이 있는지 먼저 확인하고, 팀 리더와 상의 후 진행하세요.
```

## 배포 보고서 양식

배포 완료 후 팀에 공유하는 보고서 형식이다.

```
## 배포 완료 보고

- 배포 시간: (날짜 및 시간)
- 배포 환경: 개발 / 스테이징 / 운영
- 배포 버전: (태그 또는 커밋 해시)
- 담당자: (이름)

### 배포 내용 요약
- (변경 사항 1)
- (변경 사항 2)

### 확인 결과
- [ ] 서비스 정상 동작 확인
- [ ] 에러 로그 없음 확인
- [ ] 주요 기능 테스트 완료

### 특이 사항
- (없음 / 있으면 기재)
```

---

## deploy-manager 에이전트 연동

배포 작업을 `deploy-manager` 에이전트에게 위임할 때 아래 정보를 함께 전달한다.

- 배포 환경 (dev / staging / production)
- 배포 브랜치 또는 버전
- DB 마이그레이션 포함 여부
- 특별 배포 지시사항 (서비스 중단 시간, 순차 배포 등)

---

## 핵심 규칙

- 운영 배포는 **반드시 팀 확인 후** 진행한다.
- 체크리스트를 건너뛰지 않는다. 급할수록 더 꼼꼼히 확인한다.
- 롤백 방법을 모르면 배포하지 않는다.
- 배포 후 최소 10분은 로그를 모니터링한다.
