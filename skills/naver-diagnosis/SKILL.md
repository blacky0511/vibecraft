# 네이버 진단

## 역할

네이버 서비스 자동화 문제를 감지하면 이 스킬이 호출된다.
스킬은 **라우터**로만 동작한다. 증상 수집이나 원인 분석은 하지 않는다.
"어디로 보낼지"만 판단하고, "왜 안 되는지"는 에이전트가 판단한다.

## new-feature 크기 판단 우회

```
네이버 자동화 문제는 도메인 특화 진단이 필요하므로 new-feature의 크기 판단을 우회한다.

일반 작업 흐름:
  new-feature(S/M/L 판단) → 크기별 워크플로우

네이버 작업 흐름:
  naver-diagnosis 스킬 (크기 판단 우회)
    → 스킬 내부에서 자체 크기 판단:
      - 단순 (URL 변경 등): 간이 진단 → 바로 위임
      - 복합 (차단+변경 동시): 전체 진단 → 계획 확인 → 위임

우회 이유:
  - new-feature의 S/M/L 기준은 "코드 변경량" 기반
  - 네이버 진단의 크기는 "원인 복잡도" 기반 → 판단 기준이 다름
  - 네이버 고유 참조 문서(docs/naver-knowledge/)가 필요하여 범용 R(Research)와 다름
```

## RPDCA 매핑

```
Phase 1 = R(Research) + P(Plan):
  - 스킬이 이력 확인 (R)
  - naver-logic-analyzer 에이전트가 5렌즈 분석 + 해결 계획 수립 (R+P)

Phase 2 = P(Plan) 확정:
  - 사용자에게 해결 계획 확인 요청
  - 방안 A/B 중 선택

위임 실행 = D(Do):
  - executing-plans 스킬: 구현 계획이 Task 목록인 경우
  - debugger 스킬: 기존 코드 버그 수정인 경우

검증 = C(Check) + A(Act):
  - 위임 실행 후 vibecraft의 기존 verification/gap-detector가 자동 실행
  - naver-diagnosis 스킬이 별도로 Check-Act를 구현하지 않음
```

## 스킬 vs 에이전트 책임 분리

```
스킬 = 라우터 (분석 로직 없음)
에이전트 = 분석 엔진 (증상 수집 + 5렌즈 + 하드 게이트 + 계획)

원칙: 스킬은 "어디로 보낼지"만 판단하고, "왜 안 되는지"는 에이전트가 판단한다.
증상 수집(초기 질문)은 에이전트의 1단계에서만 수행한다. 스킬은 수집하지 않는다.
```

---

## 5단계 흐름

### [1] 라우팅 판단

사용자 입력에서 키워드로 네이버 관련 문제인지 판단한다.
구체적 증상 수집, 차단/변경 분류, 에러 분석은 에이전트가 수행한다.

```
판단 항목:
- 네이버 관련 문제인가? (키워드 매칭)
- 어떤 서비스인가? (블로그/카페/플레이스/검색/트래픽/스마트스토어)
- 긴급도는? (서비스 중단 여부)

네이버 관련이 아닌 경우:
  → systematic-debugging 스킬로 전달 (일반 디버깅)
```

### [2] 이력 확인

```
1. docs/naver-diagnosis/ 폴더 존재 확인
2. 동일 서비스의 최근 진단 이력 검색
   - 파일명 패턴: {YYYY-MM-DD}-{서비스}-{증상}.md
3. 이전 이력이 있으면 → 로드하여 에이전트에 전달
4. "이전엔 됐는데 이번에 안 돼" → 이전 이력과 비교하여 변경점 파악
5. 이력이 없으면 → "첫 진단"으로 표시
```

### [3] 에이전트 호출

naver-logic-analyzer 에이전트를 호출한다.

```
호출 시 전달하는 정보:
- 사용자의 원본 입력 (증상 설명)
- 추정 서비스 (스킬이 키워드로 추정한 것)
- 이전 진단 이력 (있으면)
- code-analyzer 결과 (있으면)
- 참조 문서 로딩 지시: "docs/naver-knowledge/api-{서비스}.md를 먼저 읽어라"

에이전트가 수행하는 것:
- 증상 수집 (초기 질문 프로토콜)
- 차단/변경/복합 분류
- 빠른 경로로 렌즈 분석
- 하드 게이트 통과
- 해결 전략 + 구현 계획 + 리스크 맵 작성
```

### [4] 결과 저장

```
1. 진단 결과를 docs/naver-diagnosis/ 에 저장
   - 파일명: {YYYY-MM-DD}-{서비스}-{증상요약}.md
   - 폴더가 없으면 자동 생성

2. 보고서 형식 자동 선택:
   - 단일 원인 명확 → 간이 보고서 (에이전트 본문 내 템플릿)
   - 복합 문제 → 전체 보고서 (templates/naver-diagnosis.md 사용)
```

### [5] 위임 연결

해결 계획의 유형에 따라 적절한 스킬로 위임한다.

```
executing-plans 위임 (구현 계획이 Task 목록인 경우):
  1. 5단계 구현 계획의 Task 목록을 plan.md 형식으로 변환
  2. docs/plans/naver-fix-{날짜}/ 폴더에 plan.md 저장
  3. "plan.md가 준비됐으니 실행해" 형태로 executing-plans 트리거

debugger 위임 (기존 코드 버그 수정인 경우):
  1. 진단 보고서의 확정 원인 + 대상 파일 경로 전달
  2. "이 원인으로 이 파일을 수정해야 한다" 형태로 debug 트리거
  3. debugger가 참조할 네이버 지식 파일 경로 함께 전달

위임 후:
  - verification/gap-detector는 vibecraft 기본 흐름이 자동 처리
  - 이 스킬이 별도 Check-Act를 구현하지 않음
```

## 사용자에게 보여주는 흐름

```
사용자: "네이버 블로그 자동 포스팅이 안 돼요"

[1] 스킬: 네이버 블로그 문제로 판단 → 이력 확인
[2] 스킬: naver-logic-analyzer 에이전트 호출
[3] 에이전트: 증상 수집 → 5렌즈 분석 → 하드 게이트 → 해결 계획
[4] 스킬: 진단 결과 저장 (docs/naver-diagnosis/)
[5] 스킬: 사용자에게 계획 확인 요청
[6] 스킬: 확인 후 executing-plans 또는 debugger로 위임
[7] vibecraft: verification/gap-detector 자동 실행
```
