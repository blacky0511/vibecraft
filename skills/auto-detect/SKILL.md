# 자동 상황 감지

## 역할

사용자의 입력을 분석하여 아래 5가지 모드 중 적절한 것을 자동 선택하고,
해당 모드의 스킬을 호출한다.

## 모드 판별 규칙

### 0. 환영/인사 모드 (최우선)

**키워드**: "안녕", "하이", "hi", "hello", "시작", "뭐 할 수 있어", "도움", "help", "처음"

**조건**: 짧은 인사 또는 탐색성 질문 (구체적인 작업 요청이 아닌 경우)

**동작**: vibecraft:welcome-guide 스킬 호출

> "안녕 로그인 만들어줘"처럼 인사 + 작업 요청이 함께 있으면 인사는 스킵하고 작업 모드로 진행한다.

### 1. 새 기능 모드

**키워드**: "만들어줘", "추가해줘", "구현해줘", "넣어줘", "기능", "feature"

**동작**: vibecraft:new-feature 스킬 호출

### 2. 디버깅 모드

**키워드**: "안 돼", "에러", "버그", "오류", "안됨", "실패", "크래시", "fix", "bug", "error"

**동작**: vibecraft:systematic-debugging 스킬 호출

### 3. 프로젝트 시작 모드

**키워드**: "만들자", "시작하자", "앱", "사이트", "프로젝트", "init", "새 프로젝트"

**동작**: vibecraft:project-kickoff 스킬 호출

### 4. 코드 리뷰 모드

**키워드**: "리뷰", "봐줘", "검토", "review", "코드 봐"

**동작**: vibecraft:code-review-request 스킬 호출

### 5. 단순 수정 모드

**키워드**: "크기", "간격", "폰트", "색상", "패딩", "마진", "키워줘", "줄여줘", "늘려줘", "굵게", "얇게", "밝게", "어둡게", "~로 바꿔"

**조건**: 수치/스타일 값만 바꾸는 1~3줄 이내의 단순 변경

**동작**: vibecraft:simple-tweak 스킬 호출

> 이 모드는 다른 모드보다 **우선 판별**한다. 단순 수정인데 새 기능 모드로 빠지면 과도한 워크플로우가 실행되기 때문이다.

### 6. 배포 모드

**키워드**: "배포", "릴리즈", "deploy", "release", "서버에 올려"

**동작**: vibecraft:deploy-guide 스킬 호출

## Ralph Loop 제안 판단

모드를 판별한 후, 해당 작업이 **ralph-loop에 더 적합한지** 추가로 판단한다.

### ralph-loop이 더 좋은 상황

다음 조건을 **대부분** 만족하면 ralph-loop을 먼저 제안한다:

- **완료 기준이 명확함**: "테스트 전부 통과", "린트 에러 0개", "빌드 성공" 등
- **반복 개선형 작업**: 점진적으로 나아지는 성격 (리팩토링, 테스트 커버리지 올리기)
- **중간에 사람 판단이 불필요**: 디자인 선택, 방향 결정 없이 AI가 혼자 돌려도 됨
- **명확한 스펙이 이미 있음**: 설계 문서나 구현 계획이 이미 존재

**구체적 예시:**
- "테스트 전부 통과시켜줘" → ralph-loop 추천
- "이 파일들 전부 TypeScript로 마이그레이션해줘" → ralph-loop 추천
- "린트 에러 다 고쳐줘" → ralph-loop 추천
- "성능 최적화해서 Lighthouse 90점 이상 만들어줘" → ralph-loop 추천
- "이 설계 문서대로 구현해줘" (docs/plans/에 문서 있을 때) → ralph-loop 추천

### vibecraft가 더 좋은 상황

- **방향 결정이 필요**: "뭘 만들지", "어떤 구조로 할지" 논의가 필요
- **학습이 목적**: 코드를 이해하고 배우면서 진행하고 싶을 때
- **디자인/UX 판단 필요**: 사용자 경험에 대한 선택이 있을 때
- **디버깅**: 원인 파악에 사람의 맥락 정보가 필요할 때
- **요구사항이 불명확**: "적당히 해줘", "좋게 만들어줘" 같은 요청

### 제안 방식

ralph-loop이 적합하다고 판단되면 선택지를 제공한다:

```
이 작업은 완료 기준이 명확하고 반복 개선형이라,
ralph-loop으로 돌리면 더 효율적일 수 있습니다.

1. "ralph-loop으로 해줘" - AI가 자동 반복하며 완료까지 진행
2. "같이 하자" - vibecraft 워크플로우로 단계별 진행 (학습 가능)
```

**중요**: ralph-loop을 강요하지 않는다. 사용자가 학습 목적이면 vibecraft가 더 낫다.
제안만 하고 선택은 사용자에게 맡긴다.

## 감지 후 행동

1. 모드를 판별한다
2. ralph-loop 적합 여부를 판단한다
3. 사용자에게 감지된 모드를 알린다:
   > "새 기능 추가 요청으로 감지했습니다. vibecraft 워크플로우를 시작합니다."
   또는 (ralph-loop 적합 시):
   > "이 작업은 ralph-loop으로 돌리면 효율적일 수 있습니다. 어떻게 진행할까요?"
4. vibecraft:smart-pdca 스킬을 호출하여 작업 크기를 판단한다
5. 크기에 따라 적절한 워크플로우를 실행한다

## 모드 판별이 애매한 경우

사용자에게 물어본다:
- "어떤 작업인지 좀 더 알려주세요"
- 선택지: (1) 새 기능 추가 (2) 버그 수정 (3) 새 프로젝트 (4) 코드 리뷰 (5) 배포

## 모델 추천 가이드

모드 판별 시, 작업 성격에 맞는 모델을 사용자에게 안내한다.

| 작업 성격 | 추천 모델 | 안내 멘트 |
|-----------|----------|----------|
| 설계, 아키텍처, 브레인스토밍 | Opus | "이 작업은 깊은 판단이 필요해서 Opus가 적합합니다" |
| 코드 구현, 기능 개발 | Sonnet | "구현 작업은 Sonnet이면 충분합니다 (빠르고 비용 효율적)" |
| 단순 수정, 포맷팅, 문서 | Haiku | "간단한 작업이라 Haiku로도 충분합니다 (가장 빠르고 저렴)" |
| ralph-loop 반복 작업 | Sonnet | "반복 실행은 Sonnet 추천합니다 (Opus로 수십 번 돌리면 비용이 큽니다)" |
| 디버깅 (복잡한 버그) | Sonnet~Opus | "복잡한 버그면 Opus, 단순 에러면 Sonnet이 적합합니다" |

**안내 규칙:**
- 현재 사용 중인 모델과 추천 모델이 다를 때만 안내한다
- 강제하지 않는다. "추천입니다"로 표현한다
- 사용자가 무시해도 그대로 진행한다

## 중요 규칙

- 모드 판별은 **한국어 키워드 우선**으로 한다
- 영어 키워드도 보조적으로 지원한다
- 판별 결과를 사용자에게 항상 알려서, 잘못된 판별이면 수정할 수 있게 한다
- 단순한 질문이나 대화에는 모드를 강제하지 않는다
- ralph-loop 제안은 강요가 아닌 선택지 제공이다
