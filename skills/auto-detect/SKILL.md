# 자동 상황 감지

## 역할

사용자의 입력을 분석하여 아래 5가지 모드 중 적절한 것을 자동 선택하고,
해당 모드의 스킬을 호출한다.

## 모드 판별 우선순위

키워드가 여러 모드에 겹칠 때, 아래 우선순위 순서대로 판별한다.
숫자가 낮을수록 먼저 판별한다.

| 우선순위 | 모드 | 판별 기준 | 예시 |
|:---:|------|---------|------|
| 0 | 환영/인사 | 인사만 단독으로 있을 때 (작업 요청 없음) | "안녕", "도움" |
| 1 | 단순 수정 | 수치/스타일 키워드 + 1~3줄 변경 | "폰트 키워줘", "색상 바꿔" |
| 1.5 | 레퍼런스 디자인 | UI/디자인 키워드 + 페이지/사이트 키워드 동시 감지 | "랜딩페이지 만들어줘", "이 사이트 참고해서 UI 만들어" |
| 2 | 디버깅 | 에러/버그/실패 키워드 존재 | "에러 났어", "안 돼" |
| 3 | 분석 | 데이터 분석/조회/통계 키워드 (코드 변경 아님) | "누락률 분석해줘", "DB 데이터 뽑아줘" |
| 4 | 코드 리뷰 | 리뷰/검토 키워드 | "리뷰해줘", "봐줘" |
| 5 | 배포 | 배포/릴리즈 키워드 | "배포해줘", "서버에 올려" |
| 6 | 새 기능 | "만들어줘/추가해줘/구현해줘" + 기존 프로젝트 맥락 | "로그인 만들어줘" |
| 7 | 프로젝트 시작 | "만들자/시작하자" + 프로젝트가 아직 없는 맥락 | "블로그 만들자" |

**복수 매칭 판별 규칙:**

1. **인사 + 작업**: 작업 모드 우선 ("안녕 로그인 만들어줘" → 새 기능)
2. **새 기능 vs 프로젝트 시작**: 현재 프로젝트에 코드 파일이 이미 있으면 "새 기능", 비어있거나 없으면 "프로젝트 시작"
3. **디버깅 + 기능 요청**: 디버깅 우선 ("로그인 에러 고쳐줘" → 디버깅)
4. **판별 불가**: 사용자에게 선택지 제시

## 모드 판별 규칙

### 0. 환영/인사 모드 (최우선)

**키워드**: "안녕", "하이", "hi", "hello", "시작", "뭐 할 수 있어", "도움", "help", "처음"

**조건**: 짧은 인사 또는 탐색성 질문 (구체적인 작업 요청이 아닌 경우)

**동작**: vibecraft:welcome-guide 스킬 호출

> "안녕 로그인 만들어줘"처럼 인사 + 작업 요청이 함께 있으면 인사는 스킵하고 작업 모드로 진행한다.

### 1. 레퍼런스 디자인 모드

**키워드**: "랜딩페이지", "UI", "디자인", "레퍼런스", "참고 사이트", "페이지 만들어", "웹사이트"

**조건**: UI/디자인 관련 키워드와 페이지/사이트 관련 키워드가 동시에 감지될 때. URL이 포함되어 있으면 모드 A(크롤링), 없으면 모드 B(분위기 선택)로 진입.

**동작**: vibecraft:reference-design 스킬 호출

> "버튼 색상 바꿔줘"처럼 단순 수정에 해당하면 단순 수정 모드(우선순위 1)가 먼저 적용된다.
> "로그인 기능 만들어줘"처럼 UI가 아닌 기능 자체가 중심이면 새 기능 모드가 적용된다.

### 2. 새 기능 모드

**키워드**: "만들어줘", "추가해줘", "구현해줘", "넣어줘", "기능", "feature"

**동작**: vibecraft:new-feature 스킬 호출

### 3. 디버깅 모드

**키워드**: "안 돼", "에러", "버그", "오류", "안됨", "실패", "크래시", "fix", "bug", "error"

**동작**: vibecraft:systematic-debugging 스킬 호출

### 4. 프로젝트 시작 모드

**키워드**: "만들자", "시작하자", "앱", "사이트", "프로젝트", "init", "새 프로젝트"

**동작**: vibecraft:project-kickoff 스킬 호출

### 5. 코드 리뷰 모드

**키워드**: "리뷰", "봐줘", "검토", "review", "코드 봐"

**동작**: vibecraft:code-review-request 스킬 호출

### 6. 단순 수정 모드

**키워드**: "크기", "간격", "폰트", "색상", "패딩", "마진", "키워줘", "줄여줘", "늘려줘", "굵게", "얇게", "밝게", "어둡게", "~로 바꿔"

**조건**: 수치/스타일 값만 바꾸는 1~3줄 이내의 단순 변경

**동작**: vibecraft:simple-tweak 스킬 호출

> 우선순위 1번. 수치/스타일 키워드가 감지되면 새 기능이나 디버깅보다 먼저 이 모드를 적용한다.

### 7. 분석 모드

**키워드**: "분석", "분석해줘", "데이터 뽑아", "DB 조회", "쿼리", "로그 분석", "통계", "리포트", "패턴 분석", "추출", "집계", "현황", "트렌드", "비교해줘"

**조건**: 프로젝트 코드를 변경하는 것이 아닌, 데이터를 조회/분석하는 요청

**동작**: vibecraft:analysis-delegation 스킬 호출

> "분석" 키워드가 있어도 목적이 코드 이해("이 함수 분석해줘")면 코드 리뷰로,
> 버그 수정("에러 로그 분석해줘")이면 디버깅으로 라우팅한다.

### 8. 배포 모드

**키워드**: "배포", "릴리즈", "deploy", "release", "서버에 올려"

**동작**: vibecraft:deploy-guide 스킬 호출

## Ralph Loop 제안 판단

모드를 판별한 후, 해당 작업이 **ralph-loop에 더 적합한지** 추가로 판단한다.

### ralph-loop이 더 좋은 상황

다음 조건을 **대부분** 만족하면 ralph-loop을 먼저 제안한다:

- **완료 기준이 명확함**: "테스트 전부 통과", "린트 에러 0개", "빌드 성공" 등
- **반복 개선형 작업**: 점진적으로 나아지는 성격 (리팩토링, 테스트 커버리지 올리기)
- **중간에 사람 판단이 불필요**: 디자인 선택, 방향 결정 없이 AI가 혼자 돌려도 됨
- **명확한 스펙이 이미 있음**: 설계 문서나 구현 계획이 이미 존재

**구체적 예시:**
- "테스트 전부 통과시켜줘" → ralph-loop 추천
- "이 파일들 전부 TypeScript로 마이그레이션해줘" → ralph-loop 추천
- "린트 에러 다 고쳐줘" → ralph-loop 추천
- "성능 최적화해서 Lighthouse 90점 이상 만들어줘" → ralph-loop 추천
- "이 설계 문서대로 구현해줘" (docs/plans/에 문서 있을 때) → ralph-loop 추천

### vibecraft가 더 좋은 상황

- **방향 결정이 필요**: "뭘 만들지", "어떤 구조로 할지" 논의가 필요
- **학습이 목적**: 코드를 이해하고 배우면서 진행하고 싶을 때
- **디자인/UX 판단 필요**: 사용자 경험에 대한 선택이 있을 때
- **디버깅**: 원인 파악에 사람의 맥락 정보가 필요할 때
- **요구사항이 불명확**: "적당히 해줘", "좋게 만들어줘" 같은 요청

### 제안 방식

ralph-loop이 적합하다고 판단되면 선택지를 제공한다:

```
이 작업은 완료 기준이 명확하고 반복 개선형이라,
ralph-loop으로 돌리면 더 효율적일 수 있습니다.

1. "ralph-loop으로 해줘" - AI가 자동 반복하며 완료까지 진행
2. "같이 하자" - vibecraft 워크플로우로 단계별 진행 (학습 가능)
```

**중요**: ralph-loop을 강요하지 않는다. 사용자가 학습 목적이면 vibecraft가 더 낫다.
제안만 하고 선택은 사용자에게 맡긴다.

## 에이전트팀 제안 판단

모드를 판별한 후, 해당 작업이 **에이전트팀(CTO 팀)으로 처리하면 더 효율적인지** 추가로 판단한다.

### 에이전트팀이 더 좋은 상황

다음 조건을 **대부분** 만족하면 에이전트팀을 먼저 제안한다:

- **작업 범위가 넓음**: 파일 6개 이상, 여러 레이어(프론트+백엔드+DB 등) 동시 변경
- **병렬 처리 가능**: 서로 독립적인 작업이 여러 개 있음
- **전문 영역이 다양**: 프론트엔드 + 백엔드 + 테스트 등 다른 역할이 필요
- **계획이 이미 있음**: 설계 문서나 구현 계획이 준비된 상태
- **단순 반복이 아님**: 각 작업이 판단력을 요구함 (ralph-loop과 차이)

**구체적 예시:**
- "로그인 + 회원가입 + 마이페이지 만들어줘" → 에이전트팀 추천
- "프론트엔드 리팩토링 + API 변경 + 테스트 업데이트" → 에이전트팀 추천
- "이 설계서대로 전체 구현해줘" (다중 레이어) → 에이전트팀 추천
- "풀스택 기능 3개 동시에 만들어줘" → 에이전트팀 추천

### 에이전트팀보다 다른 방식이 나은 상황

- **작업이 작음**: 파일 1~5개 수준 → vibecraft 단독 (S/M 사이즈)
- **단순 반복**: 같은 패턴을 여러 파일에 반복 → ralph-loop
- **방향 미정**: 설계가 안 되어있고 논의가 필요 → vibecraft brainstorming 먼저
- **학습 목적**: 과정을 이해하면서 직접 하고 싶을 때 → vibecraft 단독

### 제안 방식

에이전트팀이 적합하다고 판단되면 선택지를 제공한다:

```
이 작업은 여러 레이어에 걸쳐 있고 병렬 처리가 가능해서,
에이전트팀(CTO 팀)을 구성하면 더 빠르게 완료할 수 있습니다.

1. "/team으로 해줘" - CTO가 전문가 팀을 구성하여 병렬 실행
2. "같이 하자" - vibecraft 워크플로우로 단계별 진행 (학습 가능)
3. "ralph-loop으로 해줘" - AI가 자동 반복하며 완료까지 진행
```

**중요**: 에이전트팀을 강요하지 않는다. 비용이 더 들 수 있으므로 사용자가 선택하게 한다.
제안 시 "팀 구성 시 에이전트 N개가 병렬로 작업하므로 속도는 빠르지만, 토큰 사용량이 늘어납니다"를 안내한다.

### ralph-loop vs 에이전트팀 판별 기준

| 기준 | ralph-loop | 에이전트팀 |
|------|-----------|----------|
| 작업 성격 | 같은 패턴 반복 | 다른 전문 영역 병렬 |
| 완료 기준 | 수치화 가능 (테스트 통과, 점수) | 기능 완성 |
| 판단 필요 | 거의 없음 (기계적 반복) | 각 영역별 판단 필요 |
| 파일 범위 | 많지만 같은 유형 | 다양한 유형 (UI + API + DB) |
| 비용 | 중간 (1개 에이전트 반복) | 높음 (여러 에이전트 동시) |

## 모드별 활성 스킬 맵

모드가 판별되면, 해당 모드에서 **참조해야 할 스킬만 집중**한다.
목록에 없는 스킬은 현재 모드에서 무시해도 된다.

| 모드 | 핵심 스킬 | 보조 스킬 (필요 시만) |
|------|----------|---------------------|
| 환영/인사 | welcome-guide | - |
| 단순 수정 | simple-tweak | - |
| 분석 | analysis-delegation, deep-analysis | session-context |
| 레퍼런스 디자인 | reference-design, smart-pdca, iron-law, verification | writing-plans, team-orchestration |
| 새 기능 (S) | smart-pdca, iron-law, verification | impact-analysis |
| 새 기능 (M) | smart-pdca, iron-law, brainstorming, executing-plans, verification | impact-analysis, pre-flight-check, git-workflow |
| 새 기능 (L) | smart-pdca, iron-law, brainstorming, writing-plans, team-orchestration, executing-plans, verification | impact-analysis, pre-flight-check, naming-consultant, test-strategy-advisor, git-workflow |
| 디버깅 | systematic-debugging, iron-law, verification | session-context |
| 코드 리뷰 | code-review-request, code-review-receive | external-reviewer, consistency-enforcer |
| 배포 | deploy-guide | rollback-strategy |
| 프로젝트 시작 | project-kickoff, brainstorming, writing-plans | dependency-auditor |

**항상 활성화 (모든 모드 공통)**: cto-mindset, session-context

**프리셋 (기술 스택별 자동)**: preset-nextjs / preset-react / preset-spring / preset-python / preset-general

> 이 맵의 목적은 41개 스킬 전체를 매번 참조하지 않고, **현재 모드에 관련된 스킬에만 집중**하여 컨텍스트를 효율적으로 사용하는 것이다.

## 감지 후 행동: 신뢰도 기반 분기

모드를 판별할 때, **신뢰도(높음/낮음)**를 함께 측정하여 행동을 결정한다.

### 신뢰도 판정 기준

**높음 (바로 실행):**
- 키워드가 1개 모드에만 명확히 매칭
- 맥락(현재 프로젝트 상태, 이전 대화)과 키워드가 일치
- 우선순위 규칙으로 명확히 결정 가능

**낮음 (선택지 제시):**
- 키워드가 2개 이상 모드에 걸침
- 키워드는 있지만 의도가 불명확
- 모드별 키워드에 해당하지 않는 표현

### 신뢰도별 행동 흐름

```
사용자 입력
    │
    ▼
모드 판별 + 신뢰도 측정
    │
    ├── 신뢰도 높음 ──→ 모드 안내 + 바로 실행
    │                    "새 기능 추가 요청으로 감지했습니다."
    │                    + ralph-loop/에이전트팀 적합 시 제안
    │
    └── 신뢰도 낮음 ──→ 후보 모드 + 선택지 제시
                         "이 요청을 어떤 방식으로 처리할까요?"
```

### 신뢰도 높음 → 바로 실행

1. 모드를 판별한다
2. **스킬 맵에서 해당 모드의 핵심 스킬을 확인한다**
3. ralph-loop / 에이전트팀 적합 여부를 판단한다
4. 사용자에게 감지된 모드를 알린다
5. vibecraft:smart-pdca 스킬을 호출하여 작업 크기를 판단한다
6. 크기에 따라 적절한 워크플로우를 실행한다

### 신뢰도 낮음 → 선택지 제시

후보 모드를 분석하여, **해당 입력에 관련 있는 모드만** 선택지로 제시한다.
항상 같은 선택지를 보여주는 것이 아니라, 입력에 따라 다른 선택지를 제공한다.

**예시 1**: "이 데이터 좀 봐줘"

```
이 요청을 어떤 방식으로 처리할까요?

1. 데이터 분석 — 통계, 패턴, 원인을 찾고 싶다
2. 디버깅 — 데이터가 이상해서 원인을 고치고 싶다
3. 코드 리뷰 — 데이터 처리 코드를 검토하고 싶다
```

**예시 2**: "이거 좀 고쳐줘"

```
이 요청을 어떤 방식으로 처리할까요?

1. 디버깅 — 에러/버그를 찾아서 수정
2. 단순 수정 — 값이나 스타일만 바꾸기
3. 새 기능 — 기존 기능을 개선/확장
```

**예시 3**: "성능 좀 봐줘"

```
이 요청을 어떤 방식으로 처리할까요?

1. 데이터 분석 — 성능 수치를 측정하고 병목 원인 분석
2. 디버깅 — 느린 부분을 찾아서 수정
3. 코드 리뷰 — 성능 관점에서 코드 전체 검토
```

**선택지 구성 규칙:**
- 최대 4개까지만 제시한다 (선택 피로 방지)
- 각 선택지에 "왜 이걸 선택하는지" 한 줄 설명을 붙인다
- 가장 가능성 높은 모드를 1번에 놓는다
- 사용자가 선택하면 해당 모드로 즉시 진입한다

## 모델 추천 가이드

모드 판별 시, 작업 성격에 맞는 모델을 사용자에게 안내한다.

| 작업 성격 | 추천 모델 | 안내 멘트 |
|-----------|----------|----------|
| 설계, 아키텍처, 브레인스토밍 | Opus | "이 작업은 깊은 판단이 필요해서 Opus가 적합합니다" |
| 코드 구현, 기능 개발 | Sonnet | "구현 작업은 Sonnet이면 충분합니다 (빠르고 비용 효율적)" |
| 단순 수정, 포맷팅, 문서 | Haiku | "간단한 작업이라 Haiku로도 충분합니다 (가장 빠르고 저렴)" |
| 데이터 분석, DB 조회, 통계 | Sonnet | "분석 작업은 서브에이전트로 위임됩니다. Sonnet이면 충분합니다" |
| ralph-loop 반복 작업 | Sonnet | "반복 실행은 Sonnet 추천합니다 (Opus로 수십 번 돌리면 비용이 큽니다)" |
| 디버깅 (복잡한 버그) | Sonnet~Opus | "복잡한 버그면 Opus, 단순 에러면 Sonnet이 적합합니다" |

**안내 규칙:**
- 현재 사용 중인 모델과 추천 모델이 다를 때만 안내한다
- 강제하지 않는다. "추천입니다"로 표현한다
- 사용자가 무시해도 그대로 진행한다

## 중요 규칙

- 모드 판별은 **한국어 키워드 우선**으로 한다
- 영어 키워드도 보조적으로 지원한다
- 판별 결과를 사용자에게 항상 알려서, 잘못된 판별이면 수정할 수 있게 한다
- 단순한 질문이나 대화에는 모드를 강제하지 않는다
- ralph-loop 제안은 강요가 아닌 선택지 제공이다
