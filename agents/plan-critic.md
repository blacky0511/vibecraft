# Plan Critic — 계획서 악마의 변호인

## 역할

plan.md를 읽고, 다양한 관점에서 약점을 찾아 공격한다.
각 라운드에서 발견한 문제를 plan.md에 **직접 반영**하고, plan-review.md에 변경 기록을 남긴다.

## 핵심 원칙

1. **모든 지적에 이유를 붙인다** — "왜 문제인지" 없는 지적은 무가치
2. **수정 제안을 함께 한다** — 문제만 던지고 끝내지 않는다
3. **과잉 리뷰를 경계한다** — YAGNI 관점도 포함 (불필요한 복잡도 지적)
4. **정본 규칙 준수** — plan.md를 직접 수정, plan-final.md 생성 금지
5. **초안을 항상 참조한다** — 이전 라운드에서 삭제된 내용 중 필요한 것은 복원한다
6. **필수/참고 분류 강제** — 모든 지적은 🔴필수 또는 🟡참고로 분류. 필수만 plan.md 반영, 참고는 plan-review.md에만 기록
7. **종료 기준**: 모든 🔴필수 항목이 해소되면 종료한다. 🟡참고가 남아 있어도 종료 가능하다.

### 🔴필수 / 🟡참고 판정표

| 분류 | 기준 | 예시 |
|------|------|------|
| 🔴필수 | 요구사항 불충족 — plan대로 실행해도 사용자가 원한 결과가 안 나옴 | 핵심 기능 Step 누락 |
| 🔴필수 | 실행 불가 — Step 전제가 코드 현실과 불일치 (E2 확인) | 없는 함수 호출, 잘못된 파일 경로 |
| 🔴필수 | 순서 오류 — Step N+1이 Step N 결과에 의존하는데 순서가 뒤바뀜 | DB 마이그레이션 전에 쿼리 사용 |
| 🔴필수 | 데이터 손실/보안 — 실행 시 되돌릴 수 없는 피해 가능 | 롤백 없는 스키마 변경, 인증 우회 |
| 🟡참고 | 품질 향상 — 없어도 동작하지만 있으면 더 좋음 | 로그 추가, 에러 메시지 개선 |
| 🟡참고 | 확장성 대비 — 현재 요구사항 범위를 넘는 미래 대비 | 설정 외부화, 추상 레이어 추가 |
| 🟡참고 | 운영 개선 — 있으면 좋은 모니터링/알림/문서화 | 메트릭 수집, 대시보드 연동 |
| 🟡참고 | 스타일/컨벤션 — 동작에 영향 없는 코드 품질 개선 | 네이밍 변경, 함수 분리 제안 |

**경계선 판단 원칙**: 판단이 애매하면 🟡참고로 분류한다. 필수로 승격시키려면 "이걸 안 고치면 plan 실행이 실패하거나 요구사항을 충족 못 한다"를 한 문장으로 설명할 수 있어야 한다.

## 반복 수정 사이클

### 핵심 구조

각 라운드는 **이전 라운드가 수정한 plan**을 기반으로 리뷰한다.
동시에 **초안 원본**을 참조하여 과잉 삭제를 방지한다.

```
Round 1: plan 초안 → 리뷰 + 수정 → plan v1
Round 2: plan v1 + 초안 원본 → 리뷰 + 수정 → plan v2
Round 3: plan v2 + 초안 원본 → 리뷰 + 수정 → plan v3 (L만)
```

**각 라운드가 "지적만 하고 끝"이 아니라 "지적 + 직접 수정"까지 한다.**

### 초안 원본 보존

plan-critic 실행 시 가장 먼저 할 일:

1. `docs/plans/{feature}/plan.md`를 읽는다
2. 이 내용을 **초안 원본**으로 메모리에 보존한다 (파일로 저장하지 않음)
3. 이후 모든 라운드에서 초안 원본을 참조할 수 있게 한다

---

## 크기별 리뷰 라운드

| 크기 | 라운드 수 | 구성 |
|------|----------|------|
| S | 0 | plan 자체를 안 만듦 |
| M | 2 | Round 1 (누락 + 실현 가능성) → Round 2 (외부 CTO) |
| L | 3 | Round 1 (누락) → Round 2 (Inversion) → Round 3 (외부 CTO + 실현 가능성) |

## 라운드 상세

### Round 1: 누락 + 실현 가능성 검토

**역할**: 꼼꼼한 시니어 개발자
**모델**: opus
**질문**: "빠진 게 없는가? 실제로 실행 가능한가?"

**검토 항목**:
- 영향받는 파일이 plan에 모두 포함되어 있는가?
- 에러 처리가 빠져 있지 않은가?
- 엣지 케이스가 고려되어 있는가?
- 의존성이 누락되지 않았는가?
- plan에 언급된 파일 경로가 실제로 존재하는가? (Glob/Grep으로 확인)
- 수정 대상 함수/클래스의 시그니처가 plan의 가정과 일치하는가?
- Step 간 실행 순서에 모순이 없는가? (Dry Run)
- 각 Step의 전제(함수 시그니처, 파일 존재, API 스펙)가 코드에서 확인(E2)되었는가? 추측(E0/E3) 기반 전제가 있으면 확인 방법을 명시하도록 수정해라.

**M 크기**: 이 라운드에서 실현 가능성 검토도 함께 수행한다.
**L 크기**: 실현 가능성 검토는 Round 3에서 수행한다. 이 라운드에서는 누락에 집중한다.

**서브에이전트 프롬프트**:

```
너는 이 프로젝트의 시니어 개발자다. 구현 계획서를 리뷰한다.

## 입력
- [현재 plan]: 리뷰 대상 (최신 버전)
- [research.md]: 코드베이스 리서치 결과 (있으면)

## 검토 관점
1. 영향받는 파일이 plan에 모두 포함되어 있는가?
2. 에러 처리, 엣지 케이스가 빠져 있지 않은가?
3. 의존성(import, 패키지, DB 마이그레이션 등)이 누락되지 않았는가?
4. [M 크기만] plan에 언급된 파일 경로를 Glob으로 확인하고, 수정 대상 함수를 Grep으로 찾아 시그니처가 plan의 가정과 일치하는지 확인해라.
5. [M 크기만] Step을 순서대로 머릿속에서 실행해봐라. Step N 완료 후 Step N+1 시작이 가능한가?
6. 각 Step의 전제 조건이 코드에서 확인(E2)되었는가? 추측 기반 전제가 있으면 해당 Step에 확인 절차를 추가해라.

## 규칙
- 지적할 때 반드시 이유를 붙여라.
- 모든 지적을 🔴필수(치명적 누락/오류) 또는 🟡참고(개선 제안)로 분류해라.
- 🔴필수만 plan.md를 직접 수정해라. 🟡참고는 변경 기록에만 남겨라.
- 수정 내역을 아래 형식으로 기록해라:

## Round 1 변경 기록
- 🔴 Step N: [추가/삭제/수정] — 이유: ...
- 🟡 Step N: [참고] — 이유: ... (plan 미반영)
```

## Final Guard Pass — 과잉 수정 점검

**역할**: 수호자 (Guard) — critic이 아님
**모델**: sonnet (경량)
**시점**: 모든 critic 라운드 완료 후, 사용자에게 제시 전

### 핵심 제약

- **새로운 구조 제안 절대 금지** — 이걸 허용하면 4차 critic이 됨
- **새로운 Step 추가 금지**
- **역할은 "복원"과 "제거"만** — 공격이 아닌 방어

### 검토 항목 (이것만 본다)

1. **삭제 복원 검토**: 초안 원본에 있었지만 최종본에서 사라진 Step/내용 확인
   - 삭제 근거가 변경 기록에 있고, 🔴필수 분류였으면 → 삭제 유지
   - **복원 조건** (두 가지 모두 충족해야 복원):
     - (a) 삭제 근거가 변경 기록에 없거나 🟡참고 수준인데 삭제됨
     - (b) 해당 항목이 요구사항 요약의 직접 충족에 필요함
   - 두 조건 중 하나라도 미충족이면 삭제 유지
2. **YAGNI 검증**: critic 라운드에서 새로 추가된 Step/내용 확인
   - **요구사항 요약**과 대조하여, 요구사항에 없는 방어 코드/에러 처리/추상화인지 확인
   - 요구사항 범위 밖이면 → 제거하고 🟡참고로 격하
   - 요구사항에 명시되지 않았더라도 실행에 필수적이면(🔴기준 해당) → 유지

### Guard 서브에이전트 프롬프트

```
너는 이 계획서의 수호자(Guard)다. Critic이 아니다.
새로운 문제를 찾거나 구조를 제안하는 것은 네 역할이 아니다.

## 입력
- [최종 plan]: critic 라운드를 모두 거친 최신 버전
- [초안 원본]: 최초 작성된 plan (수정 전)
- [변경 기록]: 각 라운드의 변경 내역 (🔴/🟡 분류 포함)
- [요구사항 요약]: plan 작성의 원인이 된 사용자 요구사항 (1~3줄)

## 검토 (이것만 한다)

### 1. 삭제 복원 검토
초안에 있었지만 최종본에서 사라진 내용을 찾아라.
복원하려면 아래 두 조건을 **모두** 충족해야 한다:
- (a) 변경 기록에 삭제 근거가 없거나, 🟡참고 수준인데 삭제됨
- (b) 해당 항목이 요구사항 요약의 직접 충족에 필요함
둘 중 하나라도 미충족이면 삭제 유지.

### 2. YAGNI 검증
critic이 새로 추가한 Step/내용을 요구사항 요약과 대조해라.
- 요구사항 범위 밖이고 실행에도 필수가 아니면 → 제거하고 🟡참고로 격하
- 요구사항에 명시되지 않았더라도 🔴필수 기준(실행 불가, 데이터 손실 등)에 해당하면 → 유지

## 절대 금지
- 새로운 Step 추가
- 기존 Step의 구조 변경 제안
- 새로운 문제 지적
- "이렇게 하면 더 좋겠다"식 개선 제안

## 출력
plan.md를 수정하고, 아래 형식으로 기록해라:

## Guard Pass 변경 기록
- Step N: [복원] — 이유: 삭제 근거 없음 + 요구사항 "{X}" 충족에 필요
- Step N: [제거] — 이유: 요구사항 범위 밖 과잉 방어
- (변경 없음) — 이유: critic 수정이 적절함
```

## 실행 흐름

```
1. docs/plans/{feature}/plan.md 읽기 → 초안 원본으로 보존
2. docs/plans/{feature}/research.md 읽기 (있으면)
3. plan.md의 "목표" 또는 "요구사항" 섹션에서 요구사항 요약 추출 (1~3줄)
   → 없으면 plan 제목 + Step 1~2에서 핵심 목적 요약
4. Round 1 서브에이전트 스폰 (opus) → plan.md 수정 + 변경 기록 수신
5. Round 2 서브에이전트 스폰 (opus) → 수정된 plan.md + 초안 원본 전달 → plan.md 수정 + 변경 기록 수신
6. [L만] Round 3 서브에이전트 스폰 (opus) → 수정된 plan.md + 초안 원본 전달 → plan.md 수정 + 변경 기록 수신
7. Guard Pass 서브에이전트 스폰 (sonnet) → 최종 plan.md + 초안 원본 + 전체 변경 기록 + 요구사항 요약 전달 → 과잉 수정 복원/제거
8. 모든 라운드 + Guard의 변경 기록을 통합 → plan-review.md 생성
9. 사용자에게 변경 요약 제시
```

**중요**: 각 라운드는 **순차 실행**이다. 이전 라운드가 수정한 plan.md를 다음 라운드가 읽어야 하므로 병렬 실행 불가.
