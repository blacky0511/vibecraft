# 코드 리뷰 체크리스트 (Code Review Checklist)

> **작성 가이드**: 코드를 작성한 후, 또는 다른 사람의 코드를 검토할 때 사용합니다.
> 모든 항목이 통과되어야 코드를 병합(merge)할 수 있습니다.
> 체크하지 못한 항목은 반드시 이유를 적어두세요.

## 1. 가독성 (코드를 쉽게 이해할 수 있는가)

> **기준**: 처음 보는 사람도 코드를 읽고 무엇을 하는지 이해할 수 있어야 합니다.

- [ ] 함수/메서드 길이가 적절하다 (너무 길지 않다, 일반적으로 50줄 이하 권장)
- [ ] 하나의 함수는 하나의 역할만 한다
- [ ] 복잡한 로직에는 주석이 달려 있다
- [ ] 코드의 흐름이 위에서 아래로 자연스럽게 읽힌다
- [ ] 불필요한 주석(주석 처리된 코드)이 없다
- [ ] 매직 넘버(이유 없이 나타나는 숫자)가 상수로 정의되어 있다

**특이 사항**:

## 2. 네이밍 (이름이 명확한가)

> **기준**: 변수명, 함수명, 클래스명만 봐도 무엇을 하는지 알 수 있어야 합니다.

- [ ] 변수명이 역할을 명확히 설명한다 (`data` → `userList` 처럼)
- [ ] 함수명이 동작을 명확히 표현한다 (`process` → `calculateTotalPrice` 처럼)
- [ ] 프로젝트에서 정한 네이밍 규칙(camelCase, snake_case 등)을 따른다
- [ ] boolean 변수는 `is`, `has`, `can` 등으로 시작한다 (예: `isLoggedIn`)
- [ ] 약어 사용을 최소화하고, 사용 시 팀 내에서 통용되는 약어만 사용했다

**특이 사항**:

---

## 3. 중복 코드 (같은 코드가 반복되지 않는가)

> **기준**: 같은 코드가 2곳 이상 반복된다면 함수나 공통 모듈로 분리해야 합니다.

- [ ] 동일하거나 유사한 코드 블록이 반복되지 않는다
- [ ] 반복되는 패턴이 있다면 함수/유틸리티로 분리되었다
- [ ] 기존에 있는 유틸리티 함수를 새로 만들지 않고 재사용했다
- [ ] 상수값이 여러 곳에 하드코딩되지 않고 한 곳에서 관리된다

**특이 사항**:

---

## 4. 에러 처리 (오류 상황을 올바르게 처리하는가)

> **기준**: 예외 상황에서 앱이 죽거나 사용자에게 알 수 없는 오류를 보여주면 안 됩니다.

- [ ] try-catch / try-except 등 예외 처리가 필요한 곳에 구현되어 있다
- [ ] catch 블록에서 에러를 그냥 무시하지 않는다 (최소한 로그는 남긴다)
- [ ] null / undefined 가능성이 있는 값에 대한 방어 코드가 있다
- [ ] API 호출 실패 시 사용자에게 적절한 메시지를 보여준다
- [ ] 에러 메시지가 사용자가 이해할 수 있는 언어로 작성되어 있다

**특이 사항**:

---

## 5. 보안 (보안 취약점이 없는가)

> **기준**: 악의적인 사용자가 시스템을 공격할 수 없어야 합니다.

- [ ] 사용자 입력값을 그대로 SQL 쿼리에 넣지 않는다 (SQL 인젝션 방지)
- [ ] 사용자 입력값을 그대로 HTML에 출력하지 않는다 (XSS 방지)
- [ ] API 키, 비밀번호 등이 코드에 하드코딩되어 있지 않다
- [ ] 민감한 정보(비밀번호, 개인정보)가 로그에 출력되지 않는다
- [ ] 인증이 필요한 API에 인증 확인 로직이 있다
- [ ] 권한 없는 사용자가 다른 사용자의 데이터에 접근할 수 없다

**특이 사항**:

---

## 6. 성능 (성능 문제가 없는가)

> **기준**: 불필요하게 느리거나 서버/클라이언트에 부담을 주는 코드가 없어야 합니다.

- [ ] 반복문(loop) 안에서 DB 쿼리나 API 호출을 하지 않는다 (N+1 문제)
- [ ] 큰 데이터를 한 번에 불러오지 않고 페이지네이션을 사용한다
- [ ] 결과가 바뀌지 않는 연산을 매번 반복하지 않는다 (캐싱 고려)
- [ ] 이미지 등 정적 자원이 최적화되어 있다
- [ ] 필요 없는 의존성(라이브러리)을 추가하지 않았다

**특이 사항**:

---

## 7. 테스트 (테스트가 충분한가)

> **기준**: 새로 추가한 기능이 올바르게 동작한다는 것을 검증할 수 있어야 합니다.

- [ ] 새로 추가된 기능에 대한 테스트 코드가 있다
- [ ] 기존 테스트가 모두 통과된다
- [ ] 엣지 케이스(빈 값, 최대값, 특수문자 등)를 테스트한다
- [ ] 수동 테스트를 직접 실행해서 동작을 확인했다
